# 신호가 지금 장애와 관련 있는지 판단

## 한 줄 설명

재시작 기록·경고 이벤트·개선 권고가 보일 때, 그것이 지금 장애의 원인인지 아니면 무관한 잡음인지 가를 때 쓴다.

## 진입 조건

- 조사 중에 재시작 횟수, 경고 이벤트, 개선 권고(H 규칙) 같은 신호를 원인 후보로 올리려 할 때
- 이 지침은 원인을 찾는 지침이 아니라 다른 지침과 함께 쓰는 판단 요령이다

## 먼저 확인할 사실 (가설 없이)

| 확인할 사실 | 진단 API | 이 결과가 의미하는 것 |
|---|---|---|
| 증상이 시작된 시각 | `run_api_scenario`, 증상 입력 | 원인은 이 시각 직전·동시에 있어야 한다 |
| 신호의 마지막 발생 시각 | `get_events` (BackOff·Killing 등의 마지막 시각), `get_pod_logs` (previous의 로그 시각) | 증상 시작보다 한참 전이면 관련성이 낮다 |
| 신호가 지금도 이어지는지 | `get_resource` (현재 상태), 반복 조회 | 지금 Running·Ready면 이미 회복 |
| 신호가 난 서비스가 실패 경로에 있는지 | `get_topology` | 실패한 요청이 지나지 않는 서비스면 무관 |

## 판단 요령

| 신호 | 원인으로 볼 때 | 잡음으로 볼 때 |
|---|---|---|
| 재시작 횟수 | 증상 시각과 겹치고 지금도 반복 | 오래전 1회, 지금 Running 안정 |
| 경고 이벤트 | 증상 시각 직전, 실패 경로의 리소스 | 다른 리소스, 증상 이전에 해소 |
| 개선 권고 (probe·resources 설정) | 판별에 쓰는 사실과 직접 연결될 때만 (예: TCP probe 때문에 오류 Pod가 Ready로 남음) | 원인으로 단독 지목하지 않는다 |
| 오래된 로그 오류 | 증상 구간에도 같은 오류가 계속 남음 | 증상 구간에는 없음 |

- 판정 기준: 시각이 맞고, 실패 경로에 있고, 지금도 이어지는 신호만 원인 후보로 올린다. 나머지는 보고서의 "배제한 신호"에 이유와 함께 적는다.

## 흔한 함정

- 재시작 횟수는 누적 값이다. 숫자가 크다고 지금 문제인 것은 아니다.
- 눈에 띄는 신호가 하나 있으면 그것으로 결론을 내고 싶어진다. 증상과 시각·경로가 맞는지 먼저 본다.
- 개선 권고는 장애가 없어도 늘 나온다 (정상 기준선에서도 나옴).

## 확정하지 못할 때

- 이벤트는 보존 기간(기본 약 1시간)이 지나면 사라진다. 시각을 확인할 수 없으면 "시각 확인 불가"로 적는다.

## 권장 조치 방향

| 신호 | 조치 방향 | 재검증 방법 |
|---|---|---|
| 잡음으로 판단한 신호 | 이번 장애 조치에 넣지 않고 개선 항목으로 따로 적는다 | — |
