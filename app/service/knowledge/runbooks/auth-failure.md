# 로그인·인증 실패

## 한 줄 설명

로그인이 실패하거나, 로그인 후 요청이 인증 오류(401·403)로 거부될 때 쓴다.

## 진입 조건

- 사용자 시나리오의 로그인 단계가 실패하거나, 이후 단계가 401·403을 받는다
- 해당하지 않음: 로그인 요청이 연결 단계(502·503)에서 실패 → service-unreachable 먼저

## 먼저 확인할 사실 (가설 없이)

| 확인할 사실 | 영역 | 진단 API | 이 결과가 의미하는 것 |
|---|---|---|---|
| 로그인 응답 코드와 오류 문구 | 연결 | `run_api_scenario` | 401은 자격 증명·토큰, 500은 인증 서비스 내부(저장소 등) |
| 토큰 검증을 맡는 서비스의 로그 | 로그 | `get_pod_logs` | 검증 실패 사유(만료·서명·세션 없음·저장소 연결) |
| 세션·토큰 저장소의 상태 | 구동 | `get_resource`, `get_pod_logs` | 저장소 Pod 상태, 연결 오류 |
| 시계 관련 오류 | 로그 | `get_pod_logs` | 토큰 `nbf`·`exp` 관련 오류 |

## 원인 후보와 판별법

| 원인 후보 | 지지 근거 | 배제 근거 | 확인에 쓸 진단 API | 확정에 필요한 영역 |
|---|---|---|---|---|
| 세션·토큰 저장소(캐시) 연결 문제 | 인증 서비스 로그의 캐시 연결 오류, 로그인 500 | 저장소 연결 성공 로그 | `get_pod_logs` | 로그 + 구동 |
| 서명 키 불일치 | 토큰 서명 검증 실패, 최근 Secret 교체 | 발급·검증 서비스가 같은 키 참조 | `get_resource`, `get_pod_logs` | 설정 + 로그 |
| 토큰 만료·시계 차이 | `expired`·`not yet valid` 문구 | 새로 발급한 토큰도 실패 | `get_pod_logs` | 로그 |
| 인증 설정 오류 (검증 주소 등) | 검증 요청 자체가 실패, 주소 엣지 `unresolved` | 검증 요청이 응답을 받음 | `get_topology`, `get_pod_logs` | 설정 + 연결 |
| 계정 비활성·권한 변경 | 특정 사용자만 실패 | 모든 사용자가 실패 | `run_api_scenario` | 연결 |

- 판정 기준: 서로 다른 출처의 근거 2개 이상으로 지지되고 나머지 후보가 배제되면 확정한다.

## 흔한 함정

- 인증 서비스 Pod가 Ready라고 배제하지 않는다. 인증 서비스가 의존하는 저장소·설정도 함께 본다.
- 401과 403은 다르다. 401은 인증(누구인지), 403은 권한(무엇을 할 수 있는지)이다.
- 과거의 인증 실패 로그(장애 시각 이전)를 지금 원인으로 삼지 않는다.

## 확정하지 못할 때

- Secret 값(서명 키 등)은 읽지 않는다. 같은 Secret을 참조하는지까지만 확인한다.
- 외부 ID 제공자를 쓰면 그쪽 상태는 확인할 수 없다.

## 권장 조치 방향

| 원인 후보 | 조치 방향 | 재검증 방법 |
|---|---|---|
| 저장소 연결 | 저장소 주소·네트워크 정책·저장소 Pod 상태 확인 후 복구 | 로그인 성공 |
| 서명 키 불일치 | 발급·검증 서비스가 같은 키를 쓰게 맞추고 재시작 | 발급한 토큰으로 이후 단계 성공 |
| 인증 설정 오류 | 검증 주소·설정값 수정 | 토폴로지 `declared`, 로그인 성공 |
