# Pod는 정상인데 특정 기능만 실패

## 한 줄 설명

Kubernetes 상태(Pod·Service·엔드포인트)는 모두 정상인데 특정 기능의 요청이 실패할 때 쓴다.

## 진입 조건

- 장애 신호 규칙은 모두 통과했는데 사용자 시나리오의 특정 단계가 실패한다 (게이트 경로 B)
- 응답이 오기는 한다 (5xx·429·4xx 또는 200인데 본문에 오류 문구)
- 해당하지 않음: 모든 요청이 연결 단계에서 실패 → service-unreachable, 일부 요청만 간헐 실패 → partial-failure, 로그인만 실패 → auth-failure

## 먼저 확인할 사실 (가설 없이)

| 확인할 사실 | 영역 | 진단 API | 이 결과가 의미하는 것 |
|---|---|---|---|
| 실패한 단계, 상태 코드, 응답 본문의 오류 문구 | 연결 | `run_api_scenario` | 429면 한도, 5xx면 하위 의존성, 200인데 오류 문구면 앱이 오류를 감싼 것 |
| 요청 경로의 각 서비스 로그 | 로그 | `get_pod_logs` | 어느 서비스에서 오류가 처음 생겼는지 (호출 체인을 거슬러 올라간다) |
| 앱이 제공하는 상태·한도 정보 | 연결 | `query_app_api` | 할당량 사용량, 외부 연동 상태 |
| 같은 시각의 이벤트 | 구동 | `get_events` | 재시작·축출 등 K8s 쪽 변화가 정말 없는지 |

## 원인 후보와 판별법

| 원인 후보 | 지지 근거 | 배제 근거 | 확인에 쓸 진단 API | 확정에 필요한 영역 |
|---|---|---|---|---|
| 외부 API 할당량·요금 한도 초과 | 429·quota 문구, 상태 API의 사용량이 한도 이상 | 사용량에 여유, 오류 문구가 다름 | `query_app_api`, `get_pod_logs` | 연결 + 로그 |
| 외부 API 키 만료·권한 오류 | 401·403 문구가 외부 호출 로그에 있음 | 외부 호출이 성공 | `get_pod_logs` | 로그 + 설정 |
| 하위 서비스의 DB·캐시 연결 문제 | 연결 시간 초과·거부 로그, 해당 저장소를 쓰는 기능만 실패 | 저장소를 쓰는 다른 기능은 성공 | `get_pod_logs`, `run_api_scenario` | 로그 + 구동 |
| 앱 설정값 오류 (모델 이름·기능 플래그 등) | 설정 관련 오류 문구, 최근 ConfigMap 변경 | 설정이 정상 값 | `get_resource`, `get_pod_logs` | 설정 + 로그 |
| 응답 시간 초과 | 시나리오가 시간 초과, 로그에 timeout | 응답이 빠르게 옴 | `run_api_scenario`, `get_pod_logs` | 연결 + 로그 |

- 판정 기준: 서로 다른 출처의 근거 2개 이상으로 지지되고 나머지 후보가 배제되면 확정한다.

## 흔한 함정

- HTTP 200이라고 성공이 아니다. 앱이 하위 오류를 본문 문구로 감싸 200으로 돌려줄 수 있다.
- 오류를 처음 낸 서비스와 오류를 보여 준 서비스는 다르다. 사용자에게 가까운 서비스 로그에는 "하위 호출 실패"만 보인다.
- Pod 재시작이 없으므로 재시작 기록을 원인으로 삼지 않는다 (noise-filtering).

## 확정하지 못할 때

- 외부 서비스(LLM API 등)의 실제 상태는 클러스터 밖이라 앱 로그·상태 API로만 간접 확인한다.
- 앱이 오류를 로그에 남기지 않으면 원인 후보까지만 좁히고 사람 확인 항목으로 남긴다.

## 권장 조치 방향

| 원인 후보 | 조치 방향 | 재검증 방법 |
|---|---|---|
| 할당량 초과 | 한도 상향·사용량 초기화 또는 다른 배포로 전환 | 상태 API 사용량 < 한도, 시나리오 성공 |
| 키 만료 | 키 갱신 후 Secret 교체·재시작 | 외부 호출 성공 로그 |
| DB·캐시 연결 | 연결 대상 주소·네트워크 정책·저장소 상태 확인 | 해당 기능 시나리오 성공 |
