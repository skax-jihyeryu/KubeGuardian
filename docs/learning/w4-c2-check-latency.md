# #76 C2의 140초와 경로 B

- 보관본 `eval/history/20261023T092756Z-C2/result.json`의 `checks[0]`에 `elapsed_s=140`, `gate_path=B`가 기록돼 있다. 당시 러너(`0991691:eval/run.py`)는 `inject.sh` 호출 직전에 단조 시계를 시작하고, `verify_symptom.sh`를 통과한 뒤 점검을 실행해 반환 직후 경과 초를 반올림한다. 따라서 140초에는 주입, 증상 확인, 점검과 러너 오버헤드가 모두 포함된다. 같은 날 B로 열린 C1의 12초(`20261023T092719Z-C1/result.json`)도 같은 지표다.
- 당시 러너의 `--symptom-timeout` 기본값 180초는 사전 증상 확인 스크립트가 반환된 뒤 재시도 여부를 판단하는 기준이다. C2 스크립트의 별도 로그인 요청은 `curl -m 150`으로 제한하며, HTTP 5xx 또는 상태 코드 `000`을 증상 후보로 받는다. [C2 시나리오 문서](../../scenarios/C2/README.md)는 gateway가 60초씩 두 번 시도한 뒤 약 120초에 504를 반환한다고 설명한다. 보관 결과의 `check_max_s=2700`은 반복 점검의 다음 시작 시각을 제한한다.
- C2의 보관 DB에서 `app_api` 증거 #7의 첫 단계는 timeout으로 분류되며 HTTP 상태와 `latency_ms`는 둘 다 null이다. 이 증거는 점검 내부 HTTP 요청에서 응답을 받기 전에 timeout이 발생한 기록이다. 당시 API 시나리오 단계의 `timeout_s`는 기본 10초였고 예제 설정은 로그인 단계에 60초를 지정했다. 보관 기록에서 해당 실행에 적용한 제한값, 사전 증상 확인 요청의 결과와 소요 시간, 140초의 구간별 소요 시간은 확인할 수 없다.
- 증상 단계의 HTTP 호출이 제한에 걸려 `HttpCallError`를 반환하면 실패 단계로 기록된다. 증상 검사기는 이를 `failed`로 분류하고, 이슈를 여는 규칙 신호가 없으면 게이트는 B를 선택한다. 기존 오프라인 테스트는 가짜 HTTP 클라이언트가 반환한 `ReadTimeout`의 실패 분류와 규칙 신호 없이 실패 증상으로 B를 여는 동작을 각각 확인한다. 파이프라인 테스트는 가짜 HTTP 500에서 B, 200에서 C를 확인한다. 단계를 단축했을 때 실제 C2에서 B가 유지되는지와 정상 요청이 오탐 없이 통과하는지는 미검증이다.

**판정은 부분 완료.** #76은 구간별 소요 시간과 제한 단축의 효과를 실측할 때까지 열린 상태로 둔다. 이번 조사는 보관 기록과 오프라인 테스트를 사용했다.

후속 실측에서는 주입, 사전 증상 확인, 점검 전체와 점검 내부 HTTP 단계를 단조 시계로 각각 측정한다. timeout 때도 경과 시간, 설정 제한값과 결과 분류를 남긴다. 동일 설정의 정상 H0와 C2에서 기존 제한과 단축 후보를 비교해 H0 통과, C2 경로 B 유지와 감소한 시간을 확인한다.
