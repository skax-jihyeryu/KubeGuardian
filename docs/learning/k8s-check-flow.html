서비스 점검 지도

서비스가 뜨기까지의 전 과정(환경 구축 → 설정 → 배포 → 구동 → 연결 → 사용자 요청 → 점검)을 한 줄로 놓고, 단계마다 생길 수 있는 문제와 확인할 조건, 그리고 KubeGuardian이 지금 점검하는 범위와 비어 있는 범위를 표시한 학습·점검용 문서다.

기준: origin/develop의 docs/05-rules.md·catalog.py·시나리오 정답 파일(2026-10-21 확인), 조사 방식은 docs/05-rules.md §0·기획서 §6.2·상세설계 §2, 진단 대상 kg-target/shared-infra/kubernetes 매니페스트. 일반 조건은 공개 자료에서 요약했고 출처는 §8에 모았다.

1. 한 장 요약

각 칸을 누르면 아래 상세 카드가 열린다. 막대는 그 단계에서 뽑은 문제 유형이 지금 어디에 있는지(매트릭스 §3 기준)를 보여 준다.

    읽는 법. 초록(구현됨)은 코드와 명세가 있다는 뜻이지 실제 클러스터 시나리오로 검증됐다는 뜻은 아니다. 검증 여부는 매트릭스의 "시나리오" 열에서 따로 본다. 실제 클러스터에서 AI 조건까지 통과를 확인한 것은 A1·A5(3/3)와 A3(2/3)뿐이다.

    2. 단계별 상세 카드

    각 카드는 (1) 생길 수 있는 문제, (2) 확인할 조건·방법·출처, (3) KubeGuardian의 점검, (4) 누락 순서로 읽는다.

    3. 커버리지 매트릭스

    행은 공개 자료(Kubernetes 공식 문서, learnk8s, kubernetes-mixin, Polaris)와 우리 명세에서 뽑은 문제 유형이다. 상태는 코드·명세 기준이고, 한 문제에 여러 근거가 있으면 가장 앞선 상태를 쓴다.

    열의 뜻. 규칙: 결정적 감지기가 있는가. 증상: API 시나리오·사용자 입력으로 드러나는가(○ = 증상 감지 #20이 아직 열려 있어 계획). AI: 조사 도구로 확인할 수 있는가(● = 실측 통과, ○ = 도구상 가능하나 실측 안 함, – = 도구로 볼 수 없음). 시나리오: 클러스터에서 주입해 검증한 것.

    4. 우리 규칙이 세워진 기준

    기준 순서

    1. 시나리오 우선. 먼저 MVP 시나리오(A1·A3·A5…)를 잡는 데 필요한 규칙을 정하고, 거기에 기본 상태 확인(노드·재시작·replicas)을 더했다. 그래서 13종이다.
    2. 상태 규칙은 mixin의 for를 따른다. 롤아웃 중 잠깐의 부족을 장애로 올리지 않기 위해서다. N01·P06·W01·W02·S02는 15분, P03는 1시간이다. 5분 주기라 관측 기록으로 같은 효과를 낸다.
    3. 선언 규칙은 K8s 문서(S01·S03·C01)를 근거로 spec만 보고 다음 점검에서 바로 판정한다. 트래픽이 없어도 잡힌다.
    4. 권고는 Polaris(H01·H02). 게이트를 열지 않고 알림도 없다.
    5. 결정적 판정. LLM을 쓰지 않는다. 같은 입력이면 같은 결과다.
    6. 수집 실패는 통과가 아니다. 못 읽으면 "확인하지 못함"으로 두고 지속 시간 기록은 유지한다.
    7. 근거가 약한 것은 약하다고 적는다. P07의 15분은 설계값, S04는 운영 사례(외부 표준 없음)다.
