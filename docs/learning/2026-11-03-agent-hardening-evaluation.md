# 조사 보강 평가 — #144·#147·#145

B1은 기준 0/3에서 M3·M4 모두 3/3으로 개선됐다. #145는 세 회차 모두 Pod별 확인과 실제 장애 Pod 특정을 충족했다. 반면 C1은 기준 2/3에서 두 배치 각각 0/3으로 회귀했다. C2는 여전히 F1(도구 한계)이다. 따라서 전체 조사 품질이 개선됐다고 선언하지 않는다.

A3는 2026-11-03 사용자 결정으로 재실행하지 않았다. 기존 A3 3/3은 참고값이며 현재 변경의 검증으로 세지 않는다. 이번 회귀 범위는 A3를 제외한 7개 시나리오다.

## 방법과 환경

| 배치 | 소스 | 목적 |
|---|---|---|
| `w4-final` | 기존 기준 이미지 `0ea4da20…` | 과거 비교 기준 |
| `w4-hardening-m3` | `8e8641d` | #147·#144 결합 상태의 B1·C1·C2 측정 |
| `w4-hardening-m4` | `08af96a` | #145 추가 후 B1과 제한 회귀 측정 |

- 시나리오마다 한 번의 장애 주입·점검 결과에서 AI 조사를 3회 반복했다. 독립 장애 주입 3회가 아니다. H0/H1은 게이트 C에 따른 조사 생략이며 실제 LLM 조사 3건으로 해석하지 않는다.
- 조사 모델은 `gpt-6.1-sol`, 결론·근거 judge는 `gpt-4.1`이다. 시간·토큰은 investigator usage이며 judge, 대상 앱 스모크, 주입·원복·점검 대기는 제외한다. 실제 요금으로 환산하지 않았다.
- M3에는 이미 병합된 #143 판단 규칙도 포함된다. 판단 수준 변화와 #147·#144의 조사 효과를 따로 귀속할 수 없다. M3·M4 사이에도 Pod·롤아웃·과거 로그가 달라 3회 표본의 차이를 일반 성능 향상으로 단정하지 않는다.
- 기존 runner·진단 서비스를 바꾸지 않고 전용 평가 Deployment를 사용했다. 각 시나리오 시작·종료의 설정 resourceVersion은 `1629788`로 동일했다.

## 재조사가 실제로 한 일

첫 `stop_check` 뒤 실제 수행한 도구 호출 수다. 상한 때문에 거부된 요청, 예산이 없어 시작하지 못한 재조사, 빈틈이 없어 건너뛴 경우를 구분했다.

| 시나리오 | 기준 0/1/2회차 | M3 | M4 |
|---|---|---|---|
| B1 | 1/0/0 | 0/5/5 | 0/0/5 |
| C1 | 0/0/0 | 5/5/5 | 5/5/5 |
| C2 | 0/3/0 | 0/5/0 | 0/1/1 |

M3 C2 0회차는 두 문제를 조사하다 첫 stop_check 전에 호출 예산을 소진해 `incomplete`였다. M3 C2 2회차는 빈틈이 없어 재조사하지 않았다. M4 C2는 3회 모두 `done`이며 1·2회차가 원인 후보 Pod의 설정을 각각 한 번 더 읽었다.

#144의 일회성 60초 연장·호출 상한 유지·멈춤 이유·재조사 실패 복구는 코드 리뷰와 테스트로, 실제 추가 호출은 위 단계 기록으로 확인했다. 추가 호출이 근본 원인을 항상 해결한다는 뜻은 아니다.

## B1 근거 수동 확인

M4는 3/3 `via=pod` 호출, 3/3 주입 대상 Pod 특정을 충족했다. 세 회차 모두 이름을 지정한 3개 Pod를 각각 확인했다. 장애 Pod는 0회차 3/3, 1·2회차 5/5 HTTP 500이었고 나머지는 모두 HTTP 200이었다.

| 지표 | 기준 | M3 | M4 |
|---|---|---|---|
| Pod probe 도구 호출 | 0/0/0 | 1/1/2 | 3/3/3 |
| 실제 Pod HTTP 요청 수 | 0/0/0 | 9/9/23 | 9/15/15 |

M3 2회차의 fleet probe는 2개 Pod만 포함했고, 앞선 건강한 Pod 단독 확인을 더해 총 23요청이다. M4는 각 Pod를 개별 확인했다.

새 Pod probe 누락 빈틈은 실제 3회에서는 발동하지 않았다. 모두 첫 stop_check 전에 확인을 끝냈다. 누락 시 재조사하는 경로는 별도 회귀 테스트로 검증했다. M4 2회차의 추가 5회는 설정 확인이며 최종 빈틈은 없다.

HTTPChaos는 앱 밖에서 응답을 바꿀 수 있다. 따라서 앱 로그의 성공만으로 외부 HTTP 500을 배제할 수 없다. 상태 경로 실패의 위치는 확인했지만 앱 내부 실패 메커니즘과 실패 채팅 요청의 정확한 Pod 대응은 미확정이다.

## C1: 반복된 위치 식별 실패

M3는 agent/agent/null, M4는 agent ×3을 원인 리소스로 기록했다. 두 배치 모두 cause_match 0/3, F3 ×3, candidate ×3이다. 실제로는 caller의 429와 llm-gateway의 주변 성공 기록을 관찰했지만 agent가 오류를 생성했다는 직접 근거는 없다. M3 2회차의 null은 이 모호함을 드러낸 판단 보류에 가깝다.

semantic judge는 M3 3/3, M4 1/3을 match로 평가했다. 이 채점은 결론 텍스트만 보므로 별도 cause_resource 비교를 대신하지 않는다. agent 귀속을 llm-gateway 원인과 같다고 설명한 judge 이유는 수동 검토가 필요하다.

세 배치의 C1 지침은 모두 `app-layer-failure`다. #145의 `partial-failure` 분기는 적용되지 않는다. M4의 실패 유형은 #145 직전 M3와 같지만, 원래 기준 대비 C1 회귀는 여전히 미해결이다.

정답 파일에도 HTTPChaos가 앱 처리 뒤 응답을 바꿔 llm-gateway 로그에 주입된 429가 남지 않는다고 명시돼 있다. 이것을 실제 quota 소진이나 agent 내부 변환으로 단정하지 않는다. #146의 조건부 후속 검토가 필요하다.

## C2: 실패 위치와 근본 원인의 구분

M3·M4 모두 F1 ×3이다. M4의 허용 리소스 일치는 3/3이지만 결론 judge는 0/3이다. M4 판단은 confirmed/confirmed/candidate이며 세 회차 모두 `service-unreachable` 지침을 선택했다. #145의 partial-failure 분기는 적용되지 않는다.

근거는 admin의 Service/Pod HTTP ReadTimeout을 확인하지만 admin→Redis 연결 차단이라는 근본 원인을 해결하지 못한다. confirmed는 즉시 실패 위치에 대한 판단이라 근본 원인의 확정으로 읽으면 안 된다. PostgreSQL·Redis 자체의 정상 상태도 admin에서의 연결이 정상이라는 증거가 아니다.

F1/tool_limited는 key_evidence.obtainable:false에 따른 정답 메타데이터이고 실제 런타임 예산과 다르다. 실제 incomplete는 M3 0회차이며 M4에서는 관찰되지 않았다. 시간·완료 상태 차이를 #145 효과로 귀속하지 않는다.

## 이슈별 결론

- **#145:** B1 직접 목표를 충족했고 A1·A5·H0·H1 제한 회귀를 통과했다. C1·C2는 직전 M3와 같은 기존 실패 유형이다. 사용자 승인으로 A3를 제외했음을 명시하고, 최종 기록 리뷰·CI 후 병합한다.
- **#144:** 필요한 재조사의 실제 추가 호출과 제한·기록·복구를 확인했다. 제한 회귀 비용과 A3 제외 결정을 기록해 측정 작업을 마무리한다. C1 원인 식별 개선을 뜻하지 않는다.
- **#147:** 코드·측정은 확인했지만 C1 회귀와 비용 증가가 남았다. 완료 조건의 회귀 없음을 충족했다고 선언하지 않고 열어둔다. 변경별 효과도 분리하지 못했다.
- **#146:** 재조사 뒤에도 F3가 남는 조건이 실제 충족됐다. 호출 체인·근거의 위치 식별과 판단 보류를 구분하는 후속 설계·검증이 필요하다. Report 스키마·프롬프트 변경을 이번 측정에 섞지 않았다.
