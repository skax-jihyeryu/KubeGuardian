# 1. 역량 및 기술 스택 확인 (상세본)

> 제출본은 [양식/01](양식/01-역량및기술스택확인.md)이다. 이 문서에는 제출본에 다 담지 못한 경험의 구체적인 내용과, 학습 계획이 실제로 어떻게 되었는지만 둔다.

## 1. 프로젝트 경험

SK Inc. AI Agent 구축 (AI 기반 보도와 기획 자료 자동화)에서는 AI Agent와 백엔드를 맡았다.

- LangGraph 에이전트와 자료 유형별 하이브리드 검색(BM25와 KNN을 RRF로 결합, 제목과 본문 필드별 가중 KNN)을 설계하고 구현했다. 의도 분류 노드로 작성, 수정, 질의응답, 검색 흐름을 나누고, Checkpointer로 세션을 관리하고, 대화 이력은 요약하고 잘라서 썼다.
- FastAPI와 PostgreSQL로 문서, 폴더, 가이드 관리와 채팅 세션, 이력 API를 개발했다.
- '26년 안정화 과제에서 운영 중인 질의응답 에이전트를 DeepAgent 구조로 전환하고, 운영 버그에 대응하고, GitHub Actions 배포와 AWS EKS, Nexus, Databricks 운영 인프라의 연결 관계를 정리했다. 이 운영 경험이 장애 시나리오의 출처다.

BeingAX AI Agent 개발 (PR 뉴스 모니터링)에서는 백엔드와 LLM 파이프라인을 맡았다.

- 명확한 조건은 규칙으로 먼저 거르고 문맥 판단이 필요한 기사만 LLM에 넘기는 구조로 비용과 일관성을 확보했다. KubeGuardian이 정상일 때 LLM을 부르지 않는 구조는 이 경험에서 왔다.
- 기존 Airflow 구조를 분석해 Prefect 워커와 FastAPI 백엔드를 나눈 구조로 재설계했다.

그 밖에 SK하이닉스 A.Biz 보안 환경 재구축에서 ArgoCD로 Airflow 이미지를 배포하고, 달라진 네트워크와 레지스트리, 설정 값에 맞춰 Kubernetes 매니페스트를 고쳐 다시 배포했다.

## 2. 학습 계획과 실제

보유 기술은 그대로 쓰고, 부족한 영역인 Kubernetes 장애 분석과 정량 평가에 학습 시간을 모았다. 계획한 기술 중 일부는 쓰지 않았다.

| 영역 | 계획 | 실제 |
|---|---|---|
| Kubernetes 장애 분석 | 규칙 점검 코드와 장애 재현으로 학습 | 14개 규칙을 코드로 만들고 시나리오 10개(장애 8개, 정상 기준선 2개)를 재현하며 학습했다. 학습 내용은 학습 노트에 남겼다 |
| 에이전트 정량 평가 | 정답 데이터, 지표, 자동 채점 러너 | 시나리오마다 정답 파일을 두고, 장애 주입, 점검, 채점, 원복을 한 번에 도는 러너를 만들었다 |
| 장애 주입 | Chaos Mesh로 Pod 단위 장애 재현 | 일부 시나리오는 Chaos Mesh로, 나머지는 kubectl 패치 스크립트로 주입했다 |
| 조사 지침 | 필요한 것만 불러오는 방식 | 지침 전체를 시스템 프롬프트에 넣는 방식만 구현했다 |
| UI | 대체 화면으로 Chainlit | 쓰지 않았다. FastAPI, Jinja2, HTMX 서버 렌더링으로 보고서 화면을 만들었다 |
| 도구 연결 | 함수 직접 호출과 MCP 비교 | MCP는 쓰지 않았다. 도구는 함수 호출만 구현했다 |
| 기록 | 학습 노트와 ADR 3건 이상 | 학습 노트를 남겼고 ADR은 2건이다 |
