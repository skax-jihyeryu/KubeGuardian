> 작성일: 2026-09-29 · 참고: [기획서](../01-project-proposal.md), [실행 계획서](../02-execution-plan.md)

## 1. 현재 보유 역량

- **Python 숙련도**: 중급
  - FastAPI 기반 백엔드 구조(`app/api`, `app/service`, `app/core`)를 이해하고 템플릿 코드를 수정·확장할 수 있는 수준
- **AI/ML 경험**:
  - 사내 AI 서비스 템플릿(agent-template-apps-lite) 기반 서비스 개발·운영 참여
  - 모델 학습보다는 **LLM을 활용한 서비스 개발과 운영** 중심의 경험
- **LLM 활용 경험**:
  - Azure OpenAI (GPT 계열) 기반 채팅 서비스 개발
  - LangChain / LangGraph 기반 backend-agent 템플릿 사용 경험
  - llm-gateway를 통한 LLM 호출·할당량 관리 구조 이해
- **RAG/Agent 구현 경험**: 유 (부분적)
  - 템플릿의 RAG 흐름(검색 → 프롬프트 구성 → LLM 호출)을 사용·운영
  - 도구 호출 루프, 구조화 출력, 근거 인용 강제 등 **에이전트를 처음부터 설계한 경험은 부족** → 본 프로젝트의 핵심 학습 대상
- **프로젝트 경험**:
  1. **Inc-PR 서비스 개발·운영** — 템플릿에서 출발한 AI 서비스. AKS 운영 중 공유 ConfigMap 충돌, agent OOMKilled, gateway 504 타임아웃, 스키마 드리프트 등의 장애를 겪음. *"Pod는 모두 정상인데 서비스가 안 되는"* 장애를 kubectl만으로 찾기 어려웠던 경험이 본 프로젝트의 문제의식이 됨
  2. **agent-template-apps-lite 활용** — `front → gateway → agent / admin / llm-gateway → PostgreSQL · Redis · Azure OpenAI` 구조의 템플릿 서비스 구조 파악 및 활용

## 2. 학습 필요 영역

| 영역 | 필요도 | 본 프로젝트에서의 학습 내용 | 시점 |
|---|---|---|---|
| **LangChain/LangGraph 기초** | 높음 | 상태 그래프로 `게이트 → 선별 → 조사 → 보고서 작성` 흐름을 설계. 직접 구현한 도구 호출 루프와 비교해 선택 (W3 스파이크) | W3 |
| **RAG 구현** | 중간 | 조사 지침(runbook)·환경 설명 문서를 필요한 것만 불러오는 **Skills 방식 지식 주입**. 지침 전체 주입 대비 정확도·토큰 비교 | W5 |
| **Multi-Agent 시스템 설계** | 중간 | 선별기 / 조사 루프 / 보고서 작성기의 역할 분리, 가설별 하위 조사(DeepAgents 등) 검토 | W3~W5 |
| **Vector DB 활용** | 낮음 | 지침 문서 규모가 작아 우선 키워드·설명 기반 검색으로 시작. 필요 시 Chroma/FAISS 적용 비교 | (선택) |
| **프롬프트 엔지니어링** | 높음 | 구조화 출력 스키마, 근거(evidence id) 인용 강제, 가설 기반 조사 프롬프트, 신호판 구성 | W3~W5 |
| **API 개발 (FastAPI)** | 중간 | 점검·조사·변경 검증·대화 API, SSE 진행 스트리밍 | W2~W6 |
| **UI 개발 (Streamlit)** | 중간 | 개발·디버깅용 화면은 **Chainlit**(Streamlit과 유사한 Python UI)로 구현 | W3~ |
| **Kubernetes** (추가) | 높음 | 리소스 모델, Service 라우팅, 설정 전파, 자원 제한, RBAC 최소 권한 — 규칙 점검과 장애 재현으로 학습 | W1~W6 |
| **MCP** (추가) | 중간 | 에이전트 도구 계층을 MCP 서버로 노출, 외부 에이전트에서 재사용 | W3 |
| **에이전트 평가** (추가) | 높음 | 장애 주입 → 정답 비교 방식의 eval, LLM-as-judge 루브릭 채점 | W3~W7 |

## 3. 기술 스택 선호도

| 영역 | 선택 기술 | 선택 이유 |
|---|---|---|
| 언어·API | **Python 3.12, FastAPI** | 템플릿 backend-agent와 같은 구조 |
| 에이전트 코어 | **LangGraph** (1순위) / 직접 구현 도구 호출 루프 / DeepAgents 중 W3 스파이크로 결정 | 흐름 제어를 명시적으로 설계. 도구 계층은 프레임워크 독립으로 만들어 비교 가능하게 함 |
| LLM | **Azure OpenAI** + 구조화 출력 | 사내 표준. 진단 대상 서비스와 경로 분리 |
| 도구 프로토콜 | **MCP (Python SDK)** | 도구를 표준으로 노출, 외부 에이전트(Claude Code 등) 재사용 |
| 지식 주입 | Skills 방식 조사 지침 (Markdown) | 필요한 지침만 로드해 토큰 절감 |
| K8s 접근 | `kubernetes` 공식 Python 클라이언트 | 읽기 전용 RBAC + in-cluster config |
| 저장소 | SQLite (PVC) | 단일 replica, 근거·스냅샷·보고서 저장 |
| 추적·관측 | **Phoenix** + OpenTelemetry GenAI 계측 | 도구 호출·프롬프트·토큰 추적, 템플릿 표준 |
| UI | **Chainlit** (개발용), React + TypeScript (제품 화면, 범위 축소) | 에이전트 단계·근거를 빠르게 시각화 |
| 실행 환경 | minikube + **Chaos Mesh** + k6 | 로컬 단일 노드에서 장애 주입·부하 재현 |

## 4. 프로젝트 관심 도메인

- **1순위 도메인**: IT 운영 / 클라우드 인프라 (Kubernetes 기반 AI 서비스 운영, AIOps·SRE)
- **2순위 도메인**: 사내 AI 서비스 플랫폼 (템플릿 기반 서비스 개발 생산성)
- **관심 사유**:
  - 실제로 운영 중인 사내 AI 서비스(Inc-PR)에서 **원인을 찾는 데 숙련자의 수작업이 오래 걸리는** 장애를 반복적으로 겪었다.
  - 상태를 보여주는 도구(kubectl, 대시보드)는 있지만, *"수많은 신호 중 지금 중요한 것이 무엇이고 왜 그런가"*를 판단하는 일은 규칙만으로 자동화하기 어렵다 — **AI 에이전트가 가치를 낼 수 있는 영역**이다.
  - 같은 템플릿으로 시작하는 서비스가 늘어나고 있어, 한 번 만든 진단 도구를 **여러 서비스에 재사용**할 수 있다.

## 5. 8주 목표 설정

- **기술 목표**: Kubernetes 환경을 읽기 전용으로 조사하는 **도구 호출 기반 AI 진단 에이전트** 구현 역량 확보
  - 규칙 점검 → AI 게이트 → 선별·가설 조사 → 근거 인용 보고서까지의 전체 흐름을 직접 설계·구현
  - 에이전트 구현 방식(LangGraph vs 직접 루프 등)을 같은 도구·시나리오로 비교하고 선택 근거(ADR) 작성
  - 장애 주입 기반 **정답 평가 체계**(eval) 구축
- **비즈니스 목표**: 템플릿 기반 서비스에 설정 파일 하나로 붙일 수 있는 **진단 애드온 PoC** 완성
  - 16개 장애 시나리오에서 원인 Top-1 정확도 70% 이상
  - 수동 진단 대비 원인 도달 시간 단축 효과를 수치로 제시
- **성장 목표**: Kubernetes 운영 이해와 AI 에이전트 개발 역량을 함께 갖춘 **Lv.3 Middle AI 개발자**로서의 역량 증명
  - 주간 학습 노트, 설계 결정 기록(ADR) 5건 이상, 평가 결과 보고서로 성장 과정을 기록
