## 1. 현재 보유 역량

- **Python 숙련도**: 고급
  - FastAPI 백엔드를 routes–service–repository 계층으로 설계하고, Pydantic 검증, async SQLAlchemy, 공통 에러 처리·로깅, 환경별 설정 분리까지 실무에서 구현
  - uv 기반 패키지 관리, httpx 기반 외부 API 연동(재시도·타임아웃 정책)
- **AI/ML 경험**:
  - 모델 학습보다 **LLM 기반 AI 서비스의 설계·구축·운영**을 전 주기로 수행
  - LLM 결합 데이터 파이프라인: 뉴스 수집 → HTML 정제 → Shingle 3-gram 유사도 중복 제거 → LLM 관련성 판정, Prefect로 주기별 병렬 실행
  - 운영 중인 에이전트의 응답 이슈를 운영 데이터(Databricks·AWS)로 원인 분석
- **LLM 활용 경험**:
  - Azure OpenAI(개발), AWS Bedrock(운영) — 환경별 LLM 분리 대응
  - LangGraph, LangChain, DeepAgents
  - Structured Output(Pydantic), 작성 가이드 프롬프트 주입, 근거 출처 표기
  - **룰 기반 선판정으로 LLM 호출을 줄이는 룰 + LLM 결합 구조**, temperature 0·재시도·타임아웃으로 일관성 확보
  - Arize Phoenix 트레이스로 노드·프롬프트 개선
- **RAG/Agent 구현 경험**: 유
  - **Agent**: LangGraph 기반 PR 보도자료 작성 에이전트 — 의도 분류(Router) 노드로 작성·수정·질의응답·검색 흐름 분기, 자료 유형별 검색 Tool Calling, Checkpointer 기반 세션 관리, 대화 이력 요약·트리밍
  - **Agent 고도화**: 운영 중인 질의응답 에이전트를 LangGraph 구조에서 DeepAgent 구조(계획 수립·하위 작업 위임)로 전환
  - **RAG**: 자료 유형별 하이브리드 검색 — BM25 + KNN을 RRF로 결합, 제목·본문 필드별 가중 KNN (AWS OpenSearch, Upstage 임베딩)
  - **부족한 부분**: 에이전트 결과를 **정답 기반으로 정량 평가**해 본 경험, Kubernetes 장애의 **원인을 분석**하는 도메인 지식
- **프로젝트 경험**:
  1. **SK Inc. AI Agent 구축 — AI 기반 보도/기획 자료 자동화** (AI Agent·백엔드 개발)
     LangGraph 에이전트와 하이브리드 RAG를 설계·구현하고, FastAPI·PostgreSQL 백엔드(문서·폴더·가이드 관리, 채팅 세션·이력 API)를 개발. 이후 **'26년 안정화 과제**에서 DeepAgent 구조 전환, 운영 버그 대응, GitHub Actions 배포, AWS EKS·Nexus·Databricks 운영 인프라의 연결 관계를 정리해 장애 대응 기반을 마련
  2. **BeingAX AI Agent 개발 — PR 뉴스 모니터링** (백엔드·LLM 파이프라인 개발)
     명확한 조건은 룰로 먼저 거르고 문맥 판단이 필요한 기사만 LLM에 넘기는 **룰 + LLM 판정 구조**로 비용과 일관성을 확보. 기존 Airflow 구조를 분석해 Prefect 워커–FastAPI 백엔드 분리 아키텍처로 재설계

  - 그 밖의 관련 경험: SK하이닉스 A.Biz 보안 환경 재구축 — ArgoCD로 Airflow 이미지를 배포하고, 달라진 네트워크·레지스트리·설정 값에 맞춰 Kubernetes 매니페스트를 수정·재배포

> **이 프로젝트와의 연결**: KubeGuardian의 "규칙으로 먼저 점검하고 필요할 때만 AI가 조사"하는 구조는 BeingAX의 룰 + LLM 판정 구조를 진단 영역으로 확장한 것이다. 문제의식은 Inc 안정화 과제에서 EKS 운영 환경의 장애를 수작업으로 추적했던 경험에서 나왔다.

## 2. 학습 필요 영역

보유 기술은 활용하고, **부족한 영역**(K8s 장애 분석, 정량 평가)에 학습 시간을 집중한다.

| 영역 | 현재 수준 | 이 프로젝트에서 할 것 | 비중 |
|---|---|---|---|
| **LangChain/LangGraph 기초** | 보유 (실무 에이전트 구축·DeepAgent 전환) | 기초 학습은 불필요. **가설 → 도구 검증 → 판정** 형태의 조사형 에이전트 설계로 심화 | 중 |
| **RAG 구현** | 보유 (하이브리드 RAG) | 비중 낮음. 조사 지침 문서를 필요한 것만 불러오는 수준으로만 사용 | 하 |
| **Multi-Agent 시스템 설계** | 보유 (DeepAgents 하위 작업 위임) | 단일 에이전트로 충분. 필요하면 가설별 하위 조사로 확장 | 하 |
| **Vector DB 활용** | 보유 (OpenSearch KNN) | 지침 문서 규모가 작아 사용하지 않음 | — |
| **프롬프트 엔지니어링** | 보유 | **사실 문장마다 수집 데이터(근거) 인용 강제**, 조사에 넘길 신호 정리 방식, 장애 유형별 조사 전략으로 심화 | 중 |
| **API 개발 (FastAPI)** | 보유 (고급) | 기존 역량 그대로 활용 | 하 |
| **UI 개발 (Streamlit)** | 미보유 | 같은 Python 계열인 **Chainlit**으로 개발·디버깅 화면만 구성 | 하 |
| **Kubernetes 장애 분석** (추가) | 배포·운영 경험은 있으나 원인 분석은 부족 | 리소스 모델, Service 라우팅, 설정 전파, 자원 제한, RBAC 최소 권한을 **규칙 점검 코드와 장애 재현**으로 학습. 주기 점검은 CronJob으로 운영 | **상** |
| **에이전트 정량 평가** (추가) | 경험 없음 | 정답 데이터셋 설계, 지표 정의, 자동 채점 러너, 기준선 대비 비교 | **상** |
| **장애 주입** (추가) | 경험 없음 | Chaos Mesh로 Pod 단위 장애 재현 | 중 |
| **MCP** (추가) | 경험 없음 | 비교 실험: 함수 직접 호출 vs MCP 서버 경유 | 하 |

## 3. 기술 스택 선호도

이미 실무에서 쓰던 스택을 기반으로 하고, 새로 배우는 기술은 학습 목표와 직접 연결되는 것만 넣는다.

| 영역 | 선택 기술 | 선택 이유 |
|---|---|---|
| 언어·API | **Python 3.12, FastAPI, Pydantic** | 실무 주력 스택 |
| 패키지·테스트 | **uv, pytest, ruff** | 레포 셋업에서 결정 |
| 에이전트 | **LangGraph** (기본) + 직접 구현 도구 호출 루프 비교 | LangGraph는 숙련된 도구. 직접 루프와 비교해 에이전트 루프 원리를 확인 |
| LLM | **Azure OpenAI** + Structured Output | 사내 표준, 실무 경험 |
| 도구 프로토콜 | 함수 직접 호출 (기본), MCP Python SDK (비교 실험) | 도구 계층을 프레임워크와 분리해 두고, MCP로 노출했을 때의 효과를 비교 |
| K8s 접근 | `kubernetes` 공식 Python 클라이언트 | 읽기 전용 RBAC |
| 저장소 | SQLite | 근거·보고서·알림 이력 저장 (같은 문제 중복 알림 방지에 사용) |
| 주기 실행 | **Kubernetes CronJob** | 5분 주기 점검. 별도 스케줄러 없이 클러스터 기능으로 실행 |
| 알림 | **Slack Incoming Webhook** | 팀 메신저. 요약은 본문, 전체 보고서는 스레드 |
| 추적 | **Arize Phoenix** | 실무 경험, 템플릿 표준 |
| UI | **CLI + Chainlit** | 에이전트 단계·근거 확인용. 제품 화면(React)은 범위에서 제외 |
| 실행 환경 | minikube + **Chaos Mesh** | 로컬에서 장애 주입·재현 |
| 평가 | 자체 eval 러너 (pytest 기반 채점) | 정답 기반 정량 평가 |

## 4. 프로젝트 관심 도메인

- **1순위 도메인**: 미디어/홍보(PR)
- **2순위 도메인**: 제조 (반도체)
- **관심 사유**:
  - KubeGuardian은 특정 산업에 국한되지 않는 IT 운영 도구다. 그래서 **진단 대상이 되는 서비스의 도메인**으로 연결한다.
  - **미디어/홍보(PR)**: 진단 대상 템플릿에서 출발한 대표 서비스가 SK Inc.의 **PR 보도/기획 자료 자동화 서비스**이고, 직접 구축·운영한 서비스다. PR 업무는 보도 시점과 위기 대응처럼 **시간에 민감**해서, AI 서비스가 멈추면 곧바로 업무가 멈춘다. 실제로 운영 중 LLM 할당량, 타임아웃, 공유 설정 충돌 같은 장애를 겪었고, 이 경험이 장애 시나리오의 출처다.
  - **제조(반도체)**: SK하이닉스 보안 환경 재구축에서 네트워크·레지스트리·설정 값이 달라져 매니페스트를 수정하며 배포했다. 폐쇄망·보안 환경처럼 **설정 차이로 생기는 배포 장애**는 KubeGuardian의 선언 기반 점검(서비스 주소·포트·설정 참조 불일치)이 가장 효과를 내는 영역이다.

## 5. 8주 목표 설정

- **기술 목표**: Kubernetes 환경을 읽기 전용으로 조사하는 **AI 조사·검증 에이전트** 구현
  - 5분 주기 점검 → AI 조사 여부 판정 → 가설 기반 조사·검증 → 근거를 붙인 조사 보고서 → Slack 알림까지 전체 흐름을 직접 설계·구현
  - K8s 상태로는 원인이 보이지 않는 장애(증상과 원인이 다른 서비스에 있는 경우)를 에이전트가 찾아내도록 만든다
- **비즈니스 목표**: 템플릿 기반 AI 서비스 환경에서 실제로 동작하는 **진단 에이전트 PoC** 완성
  - 대표 장애 시나리오(8개 내외)에서 원인 Top-1 정확도 70% 이상
  - 규칙만 쓸 때와 AI 조사를 더했을 때의 차이를 숫자로 제시
- **성장 목표**: **정량적으로 설계하고 숫자로 증명하는 AI 개발자** — Lv.3 Middle AI 개발자로서의 역량 증명
  - **측정 밑작업 설계**: 시나리오마다 정답 파일(원인·영향 서비스·기대 1순위)을 먼저 만들고, 지표의 정의와 계산식을 개발 전에 확정한다
  - **측정 자동화**: 장애 주입 → 실행 → 채점 → 원복을 한 번에 돌리는 eval 러너를 만들어, 변경할 때마다 같은 조건으로 다시 잰다
  - **숫자로 보고**: 원인 규명 커버리지, 원인 정확도, 장애 감지 시간, 확인 항목 감소율, 응답 시간, 토큰 비용을 기준선(규칙만) 대비로 비교하고, 난이도별 표와 실패 사례 분석으로 결과를 설명한다
  - **기록**: 주간 학습 노트(주 1건)와 설계 결정 기록(ADR 3건 이상)으로 판단 근거를 남긴다
