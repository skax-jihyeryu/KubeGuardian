## 슬라이드 2. 프로젝트 개요 (권장 2분)

- 목표 시간: 2분
- 핵심 한 줄: 장애를 먼저 감지해 알리고, 근거로 원인을 찾아 원인 파악을 3~5일에서 수 분으로 줄였다.

**[가리키기: 왼쪽 위 "1. 문제 정의"]**
먼저 문제입니다. 앱 여섯 개와 PostgreSQL, Redis가 엮인 PR 보도자료 MSA에서는 한 서비스의 문제가 다른 서비스의 증상으로 나타납니다. Pod는 모두 Ready인데 gateway는 502를 내고, 원인은 llm-gateway나 Redis에 있습니다. 그래서 원인 파악까지 약 3~5일이 걸립니다. 경험 기반 추정입니다. 시간에 민감한 업무라 서비스 중단이 곧 업무 중단입니다.

**[가리키기: 왼쪽 아래 "2. 핵심 기능" 1~5번]**
그래서 규칙 점검 14종과 기능 점검이 먼저 장애를 감지합니다. 규칙이 적발하면 AI 없이 끝내고, 규칙이 못 보는 기능 실패만 AI 조사 에이전트가 조사합니다. 코드가 근거를 검증하고, 결과는 Slack과 보고서 화면으로 전달합니다.

**[가리키기: 오른쪽 핵심 성과 카드 세 개]**
성과입니다. 첫 알림까지 19초입니다. 장애 6종 중 5종을 자동 감지해 83%이고, 정상 6회에 오알림은 없었습니다. 보고서 근거 일치율은 100%입니다.

**[가리키기: Key Message 상자]**
정리하면, 장애를 먼저 알리고 근거로 원인을 찾아 3~5일을 수 분으로 줄였습니다.

### 시간 여유 시 덧붙일 문장

- (문제) 저는 SK Inc. PR 보도자료 서비스를 대상으로 삼았습니다. 원인은 llm-gateway 할당량이나 Redis 연결 차단처럼 다른 서비스에 있고, 사용자 문의로 장애를 알게 됩니다.
- (기능) 규칙 점검과 기능 점검은 LLM 없이 코드로 정합니다. AI 조사는 사전 확인, 문제 선별, 가설 계획, 도구 검증, 보고서 순서입니다. 코드 검증은 근거 검증, 빈틈 재조사, 판단 수준입니다.
- (기술 스택) LangGraph, Azure OpenAI, Kubernetes, FastAPI, SQLite, Slack, Arize Phoenix, Chaos Mesh를 썼습니다.
- (성과) 19초는 6초에서 19초 사이였고, 기존에는 사용자 문의 뒤 약 3~5일이었습니다. 일부 Pod만 실패하는 장애는 점검 10회 중 1회 감지했습니다.

## 슬라이드 3. 기술 아키텍처 (권장 4분)

- 목표 시간: 4분 (그림 약 2분 30초, 고려 사항 약 1분 30초)
- 핵심 한 줄: 결정적 점검과 AI 조사를 나눠 두고, 에이전트는 조회 전용 도구와 정해진 출력 형식 안에서만 일한다.

**[가리키기: 맨 위 "점검 대상 서비스 (MSA)" 띠와 "조회 · 상태 / 로그 / API" 화살표]**
그림은 위에서 아래로 보겠습니다. 맨 위는 점검 대상 MSA입니다. KubeGuardian은 상태, 로그, API를 읽기만 하고 고치지 않습니다.

**[가리키기: "점검 (CronJob)"과 "AI 조사 실행 필요 시" 화살표]**
첫째, 점검 CronJob입니다. 매시 정각에 규칙 점검과 기능 점검을 하고, 이상이 있으면 Slack으로 알립니다. LLM은 쓰지 않습니다. 규칙이 못 보는 기능 실패만 조사 대기열로 넘어갑니다.

**[가리키기: worker의 "조사 에이전트"]**
조사는 worker 컨테이너가 합니다. 사전 확인, 계획, 근거 수집, 보고서, 검증과 판정 순서이고, 빈틈이 있으면 한 번 재조사합니다. 계획 단계의 RAG는 벡터 검색이 아니라 환경 설명과 런북 6종을 불러 쓰는 지식 참조입니다.

**[가리키기: web의 "이력 기반 질의 에이전트"]**
web 컨테이너에는 이력 기반 질의 에이전트가 있습니다. 운영자가 과거 장애를 채팅으로 물으면 이력을 조회해 답하고, 근거를 검증합니다. 보고서 화면도 여기서 보여 줍니다.

**[가리키기: listener와 아래 점선 "평가 러너"]**
listener는 Slack 확인 버튼을 받습니다. 세 컨테이너는 Pod 하나이고 SQLite만 공유합니다. 점선의 평가 러너는 Chaos Mesh로 장애를 넣고 채점합니다.

**[가리키기: 왼쪽 "운영자"와 맨 아래 도구 네 개]**
운영자는 알림을 받고, 보고서를 보고, 점검을 실행하고, 이력을 묻습니다. 아래 도구는 SQLite가 이력과 근거를 저장하고, Azure OpenAI가 조사와 보고서를 쓰고, Phoenix가 조사 단계를 추적하고, Slack이 알림을 보냅니다.

**[가리키기: 오른쪽 01]**
이 구조에는 세 가지 판단이 있습니다. 첫째, 서비스 점검 단계 기반 규칙 설계입니다. Pod가 Ready여도 서비스는 실패할 수 있어서, 생애 주기 10단계의 문제를 공개 기준에서 뽑아 규칙 14종으로 만들고 결정적으로 판정합니다.

**[가리키기: 02]**
둘째, 점검과 조사의 경계 분리입니다. 결정적 판정과 LLM 추론을 섞으면 비용, 시간, 재현성이 흔들려서, 규칙이 확정한 장애는 AI 없이 끝내고 1차 알림은 조사를 기다리지 않습니다.

**[가리키기: 03]**
셋째, 조회 전용 도구 7종과 출력 스키마입니다. 모든 결과를 근거 번호로 저장하고, 보고서 형식을 강제하며, 확정과 후보는 코드가 근거 수로 정합니다.

**[전환]** 이 구조로 풀어야 했던 난제를 보겠습니다.

### 시간 여유 시 덧붙일 문장

- (질의 에이전트) 질문 파악, 이력 조회, 답변 작성, 근거 검증 순서이고, 이력 조회 단계는 반복될 수 있습니다. 여기에도 같은 RAG가 쓰입니다.
- (01) 공개 기준은 kubernetes-mixin, Kubernetes 문서, Polaris입니다. 판정은 적발, 관찰 중, 통과, 확인 못 함입니다.
- (02) 규칙이 못 보는 기능 실패는 SQLite 조사 대기열을 거쳐 worker가 조사합니다.
- (03) 도구는 구동, 설정, 연결, 로그 영역마다 있습니다. LLM이 결론부터 내고 근거를 맞추지 않게 확인 수단과 답의 형식을 정했습니다. 보고서는 가설 판정, 4영역 확인 범위, 원인 호출 체인을 구조화 출력으로 받습니다.

## 슬라이드 4. 핵심 기술 과제 (권장 4분)

- 목표 시간: 4분 (난제 40초, 접근과 결과 2분 20초, 한계 40초, 마무리 20초)
- 핵심 한 줄: 실패한 세 가지 모습을 KPI별 설계로 하나씩 막았고, 그 결과를 수치로 확인했다.

**[가리키기: 위 네이비 "핵심 기술 난제" 상자]**
난제는 장애가 보이는 서비스와 원인 서비스가 다른 MSA에서 진짜 원인을 찾는 것입니다. 에이전트는 오류를 전달만 한 서비스를 지목하고, 일부 Pod만 실패하는 장애를 놓치고, 원인 서비스를 확인하지 않고 확정했습니다.

**[가리키기: "엔지니어링 접근 방법" 첫 줄]**
원칙은 하나입니다. 감지는 결정적 점검이, 원인 추적은 그래프와 코드 판정이 맡습니다.

**[가리키기: "점검과 조사의 분리" 줄, 이어서 오른쪽 83% 카드]**
감지율은 점검과 조사의 분리로 풀었습니다. 규칙 14종은 Kubernetes 객체의 결함을, 기능 점검은 실제 사용자 요청을 보내 Pod가 Ready여도 실패하는 장애를 잡습니다. 규칙이 확정한 장애는 AI 없이 1~3초에 진단하고, 정상 점검 51회에서는 조사 모델을 한 번도 부르지 않았습니다. 그 결과 6종 중 5종, 83%를 감지했습니다.

**[가리키기: "그래프 기반 사전 확인" 줄, 이어서 오른쪽 184초 카드]**
조사 시간은 그래프 기반 사전 확인으로 줄였습니다. 호출 구간마다 호출하는 쪽과 받는 쪽의 오류 기록을 LLM 없이 맞대어, 어디서 끊겼는지를 가설 전에 근거로 깝니다. 에이전트는 이 사실과 런북으로 확인할 곳부터 좁힙니다. C1 조사 시간은 26% 줄었습니다. 최종 중앙값은 184초, 20.8만 토큰으로 목표 200초와 25만 토큰 안입니다.

**[가리키기: "코드가 내리는 판단" 줄, 이어서 오른쪽 89% 카드]**
정확도는 코드가 내리는 판단으로 높였습니다. 모든 도구 결과는 근거 번호로 남고, 번호가 없는 문장은 추정으로 내립니다. 출처가 다른 근거 2종 이상과 끊기지 않은 호출 체인이 있을 때만 확정하고, 원인 서비스를 직접 조회하지 않았거나 Pod별 확인이 빠지면 검증기가 한 번 재조사시킵니다. B1 원인 Pod 특정은 0/3에서 3/3, 오확정률은 27%에서 21%가 됐고, 최종 정확도는 9회 중 8회, 89%입니다. 목표 70%를 넘었습니다.

**[가리키기: 오른쪽 아래 "한계와 다음 단계"]**
한계도 말씀드립니다. C2, Redis 차단은 Redis 연결이 호출 관계 그래프에 없어 원인을 규명하지 못했습니다. 확인 항목 감소율은 74.2%로 조정 목표 70%는 넘었지만, 운영자가 직접 확인할 정보가 아직 남습니다. 다음 과제는 의존성 상태 확인 API와 반복 조사 일치도입니다.

결정적 점검이 먼저 알리고, 원인은 근거와 코드 판정으로 찾고, AI는 필요한 곳에만 씁니다. 감사합니다.

### 시간 여유 시 덧붙일 문장

- (난제) 에이전트가 증거를 따라가 진짜 원인 서비스를 찾아내는 문제입니다.
- (감지율) 규칙 14종은 Kubernetes 객체에 흔적이 남는 장애를, 기능 점검은 Pod가 Ready여도 실패하는 장애를 감지합니다. 정상 6회에는 오알림이 없었고, B1은 점검 10회 중 1회 감지했습니다.
- (정확도) B1 3/3, C1 3/3, C2 2/3이고 규칙 진단은 3/3입니다. 정상 점검 51회는 정상 기준선 24회와 운영 정각 점검 27회를 합친 수입니다.
- (한계) 감소율 74.2%는 시나리오 6종 평균이고, 운영자가 직접 확인할 정보가 73개에서 21개로 줄었습니다.
- (레퍼런스) ReAct(Yao et al., ICLR 2023)와, 외부 검증 없는 자기 수정의 한계를 보인 Huang et al.(ICLR 2024)이 검증을 코드에 둔 근거입니다. 같은 방향의 연구로 그래프 기반 RCA 에이전트(GALA+)가 있습니다.

## 예상 질문과 답변

**1. RAG가 벡터 검색인가요?**
아닙니다. 벡터 색인을 쓰지 않습니다. 환경 설명과 런북 6종을 조사 계획이나 이력 조회 단계에서 불러 쓰는 지식 참조입니다. 이력 보고서를 벡터로 색인하는 안은 향후 과제로 두었습니다. (근거: `docs/01-project-proposal.md`)

**2. 왜 Pod 하나에 컨테이너가 세 개인가요?**
SQLite 파일 하나를 PVC에 두고 worker, web, listener가 같이 쓰기 때문입니다. 단일 노드(minikube)이고 PVC가 단일 노드용이어서 Pod 하나로 묶었습니다. 같은 이미지에 명령만 다릅니다. 분리 조건은 ADR-002에 적었습니다. (근거: `docs/02-execution-plan.md` §1.3, `docs/산출물/04-상세설계및개발환경구축.md`)

**3. 감지율 83%에서 빠진 1종은 무엇인가요?**
B1, 일부 Pod만 실패하는 장애입니다. 점검 10회 중 1회만 감지했습니다. 여러 Pod 중 일부만 실패하는 장애라 점검이 항상 걸리지는 않았습니다. 이 한계는 장표에도 적었습니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**4. C2를 못 잡은 이유는 무엇인가요?**
조사에서 C2는 9회 중 2회만 맞았습니다. 세 회차 모두 admin의 HTTP 응답 정지는 짚었지만 Redis 연결 차단은 규명하지 못했습니다. Redis 연결이 호출 관계 그래프에 없어서입니다. 의존성 상태 확인 API를 추가하는 것이 다음 과제입니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**5. 3~5일은 실제 측정값인가요?**
아닙니다. 사용자 문의 대기와 수작업 진단을 포함한 경험 기반 추정치입니다. 장표에도 그렇게 적었습니다. 19초와 6~19초는 장애 주입 후 Slack 알림까지 잰 값입니다. (근거: `docs/01-project-proposal.md` 효과 기준선)

**6. 오알림은 없었나요? 정상일 때 AI를 호출하나요?**
정상 상태 점검 6회에서 알림도 조사도 없었습니다. 정상 기준선 두 종(H0, H1)을 세 번씩 돌린 결과입니다. 표본이 작아서 운영 오알림률을 보장하는 값은 아닙니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**7. 비용, 토큰은 얼마나 드나요?**
유효 AI 조사 9회 중앙값이 184초, 20.8만 토큰입니다. 조사 모델 입력과 출력의 합입니다. 요금으로 환산하지 않았고 채점 모델 호출은 뺐습니다. C1은 토큰 중앙값이 목표를 넘었고 C2는 시간이 넘었습니다. 규칙이 확정한 장애는 AI를 호출하지 않아 비용이 없습니다. (근거: `docs/산출물/양식/07-E2E서비스개발.md` §2)

**8. 원인 정확도 89%는 원인 Pod까지 맞힌 건가요?**
아닙니다. 원인 지점 기준입니다. 원인 서비스 또는 호출 관계로 직접 연결된 서비스를 1순위로 지목하면 정답으로 봤습니다. 원인 Pod나 리소스를 정확히 특정하는 것은 다음 단계 과제입니다. 표본은 시나리오 세 종, 9회입니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**9. 운영 환경으로 확장하면 한계가 무엇인가요?**
SQLite 파일 하나와 단일 노드용 PVC를 쓰고, 프로젝트 하나만 지원합니다. 보고서 화면에는 인증이 없어서 port-forward 권한이 곧 접근 권한입니다. 확장하려면 DB를 Postgres로 옮기고 인증을 붙여야 합니다. (근거: `docs/산출물/양식/07-E2E서비스개발.md` 운영 한계)

**10. 왜 LLM에게 판단을 맡기지 않고 코드로 정했나요?**
외부 검증 없는 자기 수정은 한계가 있다는 연구(Huang et al., ICLR 2024)가 있습니다. C2 튜닝 비교에서도 내부 원인을 확인하지 못했는데 확정으로 표시한 회차가 있었습니다. 그래서 확정 조건을 코드로 정했고, LLM 출력 스키마에는 판단 수준을 넣지 않았습니다. (근거: `docs/01-project-proposal.md` 판단 수준, `docs/산출물/06-테스트및고도화.md` §5)
