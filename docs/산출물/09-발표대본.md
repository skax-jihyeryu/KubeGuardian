- 핵심 한 줄: 장애를 사용자보다 먼저 알리고, 근거가 붙은 보고서로 운영자가 직접 확인할 일을 74% 줄였다.

**[가리키기: 왼쪽 위 "1. 문제 정의"]**
저는 SK Inc. PR Agent 서비스를 운영하던 중에 이 에이전트의 필요성을 느껴서 개발을 하기 시작했습니다. 운영하다 보면 gateway는 502를 내는데 Pod는 모두 Ready인 일이 생깁니다. 원인은 llm-gateway의 할당량처럼 다른 서비스에 있어서, 사용자 문의로 장애를 알았고 원인 파악까지 약 3~5일이 걸렸습니다. 경험 기반 추정입니다. PR 업무는 서비스 중단이 곧 업무 중단이라서, 사용자보다 먼저 알고 원인까지 좁혀 전달해야 했습니다.

**[가리키기: 왼쪽 아래 "2. 핵심 기능" 1~4번]**
코드가 규칙 14종과 기능 점검으로 장애를 감지하고, 규칙이 잡은 장애는 바로 알립니다. 못 잡은 기능 실패만 조사 에이전트가 맡고, LLM은 여기서 가설을 세우고 조회 도구로 확인해 보고서를 씁니다. 다시 코드인 검증기가 보고서를 근거와 대조해 빈틈은 재조사시키고, 확정과 후보를 판정합니다. 결과는 Slack, 보고서 화면, 이력 질의 채팅으로 전달합니다.

**[가리키기: 오른쪽 핵심 성과 카드 세 개]**

정리하면, 장애를 사용자보다 먼저 알리고, 근거가 붙은 보고서로 운영자가 직접 확인할 일을 74% 줄였습니다.

## 슬라이드 3. 기술 아키텍처 (권장 4분)

- 목표 시간: 4분 (그림 약 2분 30초, 고려 사항 약 1분 30초)
- 핵심 한 줄: 결정적 점검과 AI 조사를 나눠 두고, 에이전트는 근거를 먼저 깔고 조회 전용 도구 안에서만 일하며, 판정은 코드가 한다.

**[가리키기: 맨 위 "점검 대상 서비스 (MSA)" 띠와 "조회 · 상태 / 로그 / API" 화살표]**
방금 그 장애를 그림 위에서 따라가 보겠습니다. 맨 위가 점검 대상 MSA입니다. KubeGuardian은 상태, 로그, API를 읽기만 하고 아무것도 고치지 않습니다.

**[가리키기: "점검 (CronJob)" 칩]**
읽는 첫 단계는 매시 정각의 점검 CronJob입니다. 규칙 점검과 기능 점검만 하고 LLM은 쓰지 않습니다.

**[가리키기: 오른쪽 01]**
여기서 규칙을 서비스 생애 주기 단계로 설계한 이유가 나옵니다. Pod가 Ready여도 서비스는 실패할 수 있어서, 무엇을 점검할지 기준이 필요했습니다. 그래서 서비스가 뜨는 10단계의 문제를 공개 기준에서 뽑아 규칙 14종으로 만들고, 결정적으로 판정합니다.

**[가리키기: 점검에서 Slack으로 가는 선과 "AI 조사 실행 필요 시" 화살표]**
규칙이 확정한 장애는 여기서 끝나고 1차 알림이 바로 나갑니다. gateway 502처럼 규칙이 못 보는 기능 실패만 조사 대기열로 넘어갑니다.

**[가리키기: 오른쪽 02]**
점검과 조사를 가른 이유는 이렇습니다. 결정적 판정과 LLM 추론을 섞으면 비용, 시간, 재현성이 흔들립니다. 갈라 두니 규칙이 잡은 장애는 AI 없이 끝나고, 알림도 조사를 기다리지 않습니다.

**[가리키기: worker의 "조사 에이전트"]**
대기열의 장애는 worker 컨테이너의 조사 에이전트가 받습니다. 사전 확인, 계획, 근거 수집, 보고서, 검증과 판정 순서입니다.

**[가리키기: 오른쪽 03]**
세 번째는 이 조사 에이전트의 설계입니다. ReAct만 쓰면 증상 서비스부터 가설을 세우고, 확인 없이 결론을 냅니다. 그래서 단계를 고정했습니다. 호출이 끊긴 구간은 코드가 먼저 찾아 근거로 깔고, LLM은 조회 전용 도구 7종으로 가설만 확인합니다. 보고서는 구조화 출력으로 받고, 확정할지와 재조사할지는 코드 검증기가 정합니다. 근거를 먼저 깔고 코드가 판정하는 구조입니다.

**[가리키기: SQLite와 왼쪽 "운영자", web의 "이력 기반 질의 에이전트"]**
근거와 이력은 SQLite에 저장됩니다. 운영자는 Slack 알림과 보고서 화면으로 결과를 받습니다. 나중에 비슷한 장애가 나면 web의 질의 에이전트에게 채팅으로 과거 장애를 물을 수 있고, 답의 근거도 검증합니다.

**[가리키기: listener와 아래 점선 "평가 러너"]**
listener는 Slack 확인 버튼을 받습니다. 점선의 평가 러너는 Chaos Mesh로 장애를 넣고 정답과 비교해 채점합니다.

**[전환]** 이 구조에서 가장 까다로웠던 부분이 원인 추적이었고, 그 난제를 보겠습니다.

### 시간 여유 시 덧붙일 문장

- (질의 에이전트) 질문 파악, 이력 조회, 답변 작성, 근거 검증 순서이고, 이력 조회 단계는 반복될 수 있습니다. 여기에도 같은 RAG가 쓰입니다.
- (01) 공개 기준은 kubernetes-mixin, Kubernetes 문서, Polaris입니다. 판정은 적발, 관찰 중, 통과, 확인 못 함입니다.
- (03) 도구는 구동, 설정, 연결, 로그 영역마다 있습니다. 보고서는 가설 판정, 영역별 확인 범위, 원인 호출 체인을 구조화 출력으로 받습니다.

## 슬라이드 4. 핵심 기술 과제 (권장 4분)

- 목표 시간: 4분 (난제 40초, 접근과 결과 2분 20초, 한계 40초, 마무리 20초)
- 핵심 한 줄: 실패한 세 가지 모습을 ①②③ 설계로 하나씩 막았고, 같은 번호의 결과 카드로 확인했다.

**[가리키기: 위 네이비 "핵심 기술 난제" 상자]**
이 구조를 만들면서 풀어야 했던 난제가 있었습니다. 장애가 보이는 서비스와 원인 서비스가 다른 MSA에서 진짜 원인을 찾는 일입니다. 에이전트는 세 가지로 틀렸습니다. 오류를 전달만 한 서비스를 원인으로 지목했고, 일부 Pod만 실패하는 장애를 놓쳤고, 확인 없이 원인을 확정했습니다.

**[가리키기: "엔지니어링 접근 방법" 첫 줄과 "① 점검과 조사의 분리", 이어서 오른쪽 ① 83% 카드]**
감지는 결정적 점검이, 원인 추적은 그래프와 코드 판정이 맡습니다. ①번은 점검과 조사의 분리입니다. LLM으로 상시 점검하면 비싸고 재현이 어렵고, Ready Pod의 실패는 상태로 안 보입니다. 그래서 규칙 14종과 실제 요청을 보내는 기능 점검으로 감지하고, 규칙 판정은 AI 없이 끝냈습니다. 오른쪽 ① 카드입니다. 장애 6종 중 5종, 83%를 자동 감지했고, 정상 점검 51회에 조사 호출은 0회였습니다. 규칙 진단은 1~3초입니다.

**[가리키기: "② 그래프 기반 사전 확인", 이어서 오른쪽 ② 184초 카드]**
②번은 그래프 기반 사전 확인입니다. ReAct만 쓰면 증상 서비스부터 가설을 세워서 오류를 전달만 한 서비스를 지목합니다. 그래서 호출 구간마다 양쪽 오류 기록을 코드로 맞대어 끊긴 구간을 먼저 근거로 깔고, 그 위에서 ReAct가 검증합니다. 오른쪽 ② 카드입니다. AI 조사 시간 중앙값은 184초로 목표 200초 안입니다.

**[가리키기: "③ 코드가 내리는 판단과 재조사", 이어서 오른쪽 ③ 89% 카드]**
③번은 코드가 내리는 판단과 재조사입니다. 외부 검증 없는 LLM 자기 수정은 추론을 고치지 못한다는 ICLR 2024 연구가 있습니다. 그래서 도구 결과에 근거 번호를 붙이고, 출처가 다른 근거 2종과 끊기지 않은 호출 체인이 있을 때만 코드가 확정하게 했습니다. 원인이나 Pod별 확인이 빠지면 재조사합니다. 오른쪽 ③ 카드입니다. B1의 원인 Pod 특정은 0/3에서 3/3이 됐고, 오확정률은 27%에서 21%로 줄었습니다. 원인 정확도는 AI 조사 8/9, 89%입니다.

**[가리키기: 오른쪽 아래 "한계와 다음 단계"]**
한계도 있습니다. C2, Redis 차단은 Redis 연결이 그래프에 없어서 원인을 규명하지 못했습니다. 그래서 다음 과제가 의존성 상태 확인 API입니다. 확인 항목 감소율은 74.2%로 목표 70%를 넘었습니다. 반복 조사 일치도 검증과 의미 기반 이력 검색도 남은 과제입니다.

세 접근은 하나의 원칙입니다. 감지는 결정적 점검이, 원인은 근거와 코드 판정이 맡고, AI는 필요한 곳에만 씁니다. 감사합니다.

### 시간 여유 시 덧붙일 문장

- (GALA+) ②의 사전 확인은 그래프 기반 RCA 연구인 GALA+와 같은 방향입니다.
- (토큰) AI 조사 중앙값은 20.8만 토큰으로 목표 25만 토큰 안입니다.
- (감소율) 74.2%는 시나리오 6종 평균이고, 합계로 보면 운영자가 직접 확인할 정보가 73개에서 21개로 줄었습니다.
- (정확도) 정확도 89%는 원인 지점 기준이고, 원인 Pod까지 특정하는 것은 다음 단계 과제입니다.

## 예상 질문과 답변

**1. RAG가 벡터 검색인가요?**
아닙니다. 벡터 색인을 쓰지 않습니다. 환경 설명과 런북 6종을 조사 계획이나 이력 조회 단계에서 불러 쓰는 지식 참조입니다. 이력 보고서를 벡터로 색인하는 안은 향후 과제로 두었습니다. (근거: `docs/01-project-proposal.md`)

**2. 왜 Pod 하나에 컨테이너가 세 개인가요?**
SQLite 파일 하나를 PVC에 두고 worker, web, listener가 같이 쓰기 때문입니다. 단일 노드(minikube)이고 PVC가 단일 노드용이어서 Pod 하나로 묶었습니다. 같은 이미지에 명령만 다릅니다. 분리 조건은 ADR-002에 적었습니다. (근거: `docs/02-execution-plan.md` §1.3, `docs/산출물/04-상세설계및개발환경구축.md`)

**3. 감지율 83%에서 빠진 1종은 무엇인가요?**
B1, 일부 Pod만 실패하는 장애입니다. 점검 10회 중 1회만 감지했습니다. 여러 Pod 중 일부만 실패하는 장애라 점검이 항상 걸리지는 않았습니다. 이 한계는 장표에도 적었습니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**4. C2를 못 잡은 이유는 무엇인가요?**
C2는 원인 지점 기준으로 3회 중 2회가 맞았습니다. 세 회차 모두 admin의 HTTP 응답 정지는 짚었지만 Redis 연결 차단은 규명하지 못했습니다. Redis 연결이 호출 관계 그래프에 없어서입니다. 의존성 상태 확인 API를 추가하는 것이 다음 과제입니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**5. 3~5일은 실제 측정값인가요?**
아닙니다. 사용자 문의 대기와 수작업 진단을 포함한 경험 기반 추정치입니다. 장표에도 그렇게 적었습니다. 6~19초는 장애를 주입한 뒤 Slack 첫 알림까지 잰 값입니다. (근거: `docs/01-project-proposal.md` 효과 기준선)

**6. 오알림은 없었나요? 정상일 때 AI를 호출하나요?**
정상 상태 점검 6회에서 알림도 조사도 없었습니다. 정상 기준선 두 종(H0, H1)을 세 번씩 돌린 결과입니다. 표본이 작아서 운영 오알림률을 보장하는 값은 아닙니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**7. 비용, 토큰은 얼마나 드나요?**
유효 AI 조사 9회 중앙값이 184초, 20.8만 토큰입니다. 조사 모델 입력과 출력의 합입니다. 요금으로 환산하지 않았고 채점 모델 호출은 뺐습니다. C1은 토큰 중앙값이 목표를 넘었고 C2는 시간이 넘었습니다. 규칙이 확정한 장애는 AI를 호출하지 않아 비용이 없습니다. (근거: `docs/산출물/양식/07-E2E서비스개발.md` §2)

**8. 원인 정확도 89%는 원인 Pod까지 맞힌 건가요?**
아닙니다. 원인 지점 기준입니다. 원인 서비스 또는 호출 관계로 직접 연결된 서비스를 1순위로 지목하면 정답으로 봤습니다. 원인 Pod나 리소스를 정확히 특정하는 것은 다음 단계 과제입니다. 표본은 시나리오 세 종, 9회입니다. (근거: `docs/산출물/06-테스트및고도화.md` §6)

**9. 운영 환경으로 확장하면 한계가 무엇인가요?**
SQLite 파일 하나와 단일 노드용 PVC를 쓰고, 프로젝트 하나만 지원합니다. 보고서 화면에는 인증이 없어서 port-forward 권한이 곧 접근 권한입니다. 확장하려면 DB를 Postgres로 옮기고 인증을 붙여야 합니다. (근거: `docs/산출물/양식/07-E2E서비스개발.md` 운영 한계)

**10. 왜 LLM에게 판단을 맡기지 않고 코드로 정했나요?**
외부 검증 없는 자기 수정은 한계가 있다는 연구(Huang et al., ICLR 2024)가 있습니다. C2 튜닝 비교에서도 내부 원인을 확인하지 못했는데 확정으로 표시한 회차가 있었습니다. 그래서 확정 조건을 코드로 정했고, LLM 출력 스키마에는 판단 수준을 넣지 않았습니다. (근거: `docs/01-project-proposal.md` 판단 수준, `docs/산출물/06-테스트및고도화.md` §5)

**11. 19초는 어떻게 쟀나요?**
평가 때 장애를 주입한 시점부터 Slack 첫 알림까지의 시간(M1)을 쟀습니다. A1 6.1초, C1 11.9초, B1 13.0초, A5 18.6초라서 6~19초입니다. A3는 30분 지속을 확인해야 알리는 조건이라 오래 걸리고, C2는 143초라서 이 범위에서 뺐습니다. 그래서 19초는 모든 장애의 값이 아니라 위 네 시나리오의 범위입니다. (근거: `eval/history/w5-final-kpi-f97c068/metrics.jsonl`의 `injection_seconds`)

**12. 74.2%는 어떻게 계산했나요?**
시나리오마다 `1 − (남은 정보 수 / 수작업 기준 정보 수)`로 감소율을 구하고, 장애 6종을 같은 비중으로 평균해 74.2%입니다. 평가 12회의 확인 항목을 합치면 73개에서 21개이고, 합계로 계산하면 71.2%입니다. 장표의 74.2%는 6종 평균입니다. (근거: `docs/산출물/06-테스트및고도화.md` 확인 항목 감소율)

**13. 시나리오 10종은 어떻게 구성되나요?**
장애 6종(A1, A3, A5, B1, C1, C2), 정상 2종(H0, H1), 시연 2종(A7, C8)입니다. 장애 6종과 정상 2종이 채점 대상이고, 시연 2종은 시연 겸 사전 시험이라 채점에 넣지 않았습니다. A6은 최종 평가 뒤에 추가돼서 10종에 세지 않았습니다. (근거: `docs/산출물/03-시나리오수립.md`)
