# 촬영 큐시트 — 내레이션과 클릭

원본: [08-시연영상스크립트.md](08-시연영상스크립트.md)(장면 R0~R13, §8 녹음 대본). **촬영은 무음(마이크 끔)이고, 내레이션은 편집이 끝난 영상에 맞춰 나중에 장면별로 후시 녹음한다.** 그래서 이 큐시트는 두 부분이다. 앞부분은 촬영 큐(화면에서 할 일과 머무는 시간), 맨 끝은 후시 녹음 큐(최종 영상 시각과 읽을 문장)다. 화면에 보이는 명령(데스크톱 2의 명령 터미널에서 치는 것)은 "명령 터미널에 입력: …" 행으로 넣었다(점검은 두 시나리오 모두 데스크톱 3의 브라우저 창 B의 "지금 점검" 버튼이고, 원복 뒤 정상 확인만 데스크톱 1의 창 A에서 한다). 서비스 주소명 오류의 원복과 정상 확인(R6)은 영상에 나오는 장면이다(명령 터미널에서 원복한 뒤, 데스크톱 1의 "지금 점검"으로 점검이 "정상"으로 돌아오고, 데스크톱 2의 Slack에 복구 알림이 도착한 것까지 보인다). LLM 배포명 변경의 원복과 정상 확인은 영상에서 뺐고 맨 끝 녹화 밖 정리로 옮겼다. 서비스 로그 터미널 교체 같은 나머지 준비만 "⏸ 녹화 밖" 한 줄로 표시했다. 영상에 나가는 말에는 시나리오 ID를 쓰지 않는다(S04는 규칙 이름이라 그대로 둔다). 라벨 카드·자막·확대·박스·배속·전후 분할은 모두 편집에서 넣으므로 촬영 때는 신경 쓰지 않는다(§4 각 장면 표).

**촬영 규칙 (무음)**
- 마이크를 끈다. 말하지 않는다. 틀려도 이어서 찍고 편집에서 자른다.
- 커서는 말할 문장이 아니라 **편집 때 박스를 붙일 대상** 위에 2초 이상 둔다(아래 "커서 N초"가 그 시간).
- 대기 구간(롤아웃, 점검 직후 조사 시작 전, 조사 로그가 안 올라오는 때, 답 생성 대기)은 그대로 두고 편집에서 자른다.
- 묶음 0(슬라이드 다섯 장), 1, 2 모두 녹화 시작 후 3초는 가만히 둔다(편집 여유).
- **Slack 알림 장면(R5-1, R8, R10, R6의 복구 알림)**: 알림은 점검 직후에 발송되므로 L3에서 작업하는 도중(R4·R5-2, R8, R9)에 배너가 뜬다. 배너가 떠도 누르지 않고 무시한 채 하던 일을 계속 찍는다. 알림 스타일이 "알림"이라 배너는 스스로 사라지지 않고 남으므로, 그 장면(R5-2, R8의 조사 중 확인, R9의 결과 훑기)을 마친 뒤 **배너가 보이는 채로** `⌃←`를 눌러 컷 없이 전환 애니메이션 그대로 Slack(데스크톱 2)으로 넘어간다(한 테이크. 편집에서 배너 → 전환 장면을 그 장면 끝에 붙인다). 배너가 이미 사라졌거나 뜨지 않았어도 Slack에는 알림이 남아 있으니 그냥 `⌃←`로 넘어가 알림을 보인다(배너 연출만 빠진다) [촬영 시 확인]. 배너를 클릭하지 않는다. R6의 복구 알림은 L1에서 점검한 직후 뜰 수 있고, 뜨면 같은 방식으로 `⌃→`로 넘어간다. 준비는 시연영상스크립트 §3 "Slack 알림 배너와 데스크톱 전환"이다(Slack 알림 허용, 집중 모드 끄기, 알림 미리보기 표시, 알림 스타일 "알림", 동작 줄이기 끄기).
- 확대와 박스는 모두 편집에서 넣는다. 촬영 때는 확대하려는 곳 위에 커서를 2초 이상 둔다.

**데스크톱 넘김**

| 키 | 데스크톱 | 레이아웃 |
|---|---|---|
| `⌃1` | 1 | L1 화면 전체 (브라우저 창 A 최대화. R1 화면 둘러보기, R6 정상 확인, R11 보고서, R11-7 이력 채팅) |
| `⌃2` | 2 | L2 운영 화면: 왼쪽 2/3 = Slack, 오른쪽 1/3 = 위 명령 터미널 / 아래 Pod 감시 터미널 (읽는 순서 명령 → Pod 변화 → Slack 알림) |
| `⌃3` | 3 | L3 로그 화면: 왼쪽 2/3 = 브라우저 창 B(서비스 주소명 오류 장면 R3~R5-2와 LLM 배포명 변경 장면 R8~R9의 "지금 점검"·점검 상세·점검 이력 결과를 여기서 본다), 오른쪽 1/3 = 위 3/4 작업자 로그 터미널 / 아래 1/4 서비스 로그 터미널 |

순서(모든 전환이 이웃 한 칸. 이동은 `⌃→`/`⌃←`):

**L1** 화면 둘러보기(설정 → 점검 이력 → 이슈 → 이력 채팅) → `⌃→` **L2** 서비스 주소명 오류 주입 → `⌃→` **L3** (서비스 로그 터미널 다시 켜기) 창 B에서 지금 점검 → S04 적발 → 결과 화면 → 근거 서랍(주소 끝 점) → 작업자 로그(알림 발송·근거 요약만, 조사 줄 없음) · 서비스 로그(주소 호출 실패 줄) → 배너 `⌃←` **L2** Slack 1차 알림 → 명령 터미널 원복 → `⌃←` **L1** 지금 점검 → 정상·열린 이슈 없음 확인 → `⌃→` **L2** Slack 복구 알림 → ⏸ 녹화 밖 준비 → LLM 배포명 변경 주입 → Pod 정상·채팅 실패 확인 → `⌃→` **L3** 창 B에서 지금 점검 → 채팅 기능 점검 실패 → 조사 중(도구 호출 횟수) → 배너 `⌃←` **L2** Slack '조사 중' 안내 → `⌃→` **L3** 서비스 로그 403 줄 → AI 조사 로그 → 점검 이력 결과 훑기 → 배너 `⌃←` **L2** Slack 갱신·스레드 답글 → 보고서 링크(링크가 창 A에서 열려 macOS가 데스크톱 1로 이동) **L1** 보고서(결론 → 호출 체인 → 가설 → 근거 박스 403 줄) → 이력 채팅 → 녹화 끝. ⏸ 녹화 밖: LLM 배포명 변경 원복·정상 확인

Slack은 데스크톱 2에 있다. 창은 촬영 중에 옮기지 않는다.

시작 전: `make kg-web`으로 `http://localhost:8080`을 열어 둔다. **창 A(데스크톱 1)와 창 B(데스크톱 3)는 서로 다른 브라우저 앱으로 띄운다**(예: 창 A = 기본 브라우저, 창 B = 다른 브라우저). 기본 브라우저의 창은 창 A 하나뿐이어야 한다. Slack 보고서 링크(R10)가 기본 브라우저의 가장 최근 창, 곧 창 A에서 열려야 하고 macOS가 창 A가 있는 데스크톱 1로 이동해 주기 때문이다. 링크가 창 A에서 열리고 L2 → L1로 이동하는지 리허설에서 확인한다 [촬영 시 확인]. 창 B에는 묶음 1을 시작하기 전에 점검 이력 화면(`http://localhost:8080`)을 열어 둔다(R3에서 바로 "지금 점검"을 누른다). 데스크톱 2의 Pod 감시 터미널에서 `kubectl get pods -n dev -w`가 돌고 있고 명령 터미널은 `clear`로 비운 빈 프롬프트인지 확인한다. 데스크톱 3의 작업자 로그 터미널에서 `kubectl -n kubeguardian logs -f deploy/diagnostic-agent --all-containers --since=1s`가 돌고 있는지, 서비스 로그 터미널에는 서비스 주소명 오류 장면용 gateway 명령(R5-2의 코드 블록)이 켜져 있는지(R2 롤아웃 뒤 L3에 도착해 새 Pod 기준으로 다시 켜고, 묶음 2 시작 전에 llm-gateway 명령으로 바꾼다) 확인한다.

## 묶음 1 · 화면 둘러보기 · 서비스 주소명 오류 장애 · 원복

시작 전: 열린 이슈 없음 확인, 점검 이력 기간 필터를 걸어 `해결 #N` 줄을 피한다. 창 B(데스크톱 3)가 점검 이력 화면인지 확인한다. 정각을 피해(정각 직후 5~10분 사이) 시작한다.

### R1 화면 둘러보기 (데스크톱 1 · L1) — 설정 → 점검 이력 → 이슈 → 이력 채팅

왼쪽 메뉴에는 글자 없이 아이콘만 있다. 위에서부터 **점검 이력**(맥박 모양), **이슈**(깃발 모양), **설정**(슬라이더 모양)이다. 이력 채팅은 상단 오른쪽 **"질문" 버튼**(말풍선 아이콘)이다. 편집에서 콜아웃(영역 이름 + 한 줄 설명)과 줌이 클릭 순간에 들어간다.

| 순서 | 화면에서 할 일 |
|---|---|
| 1 | 녹화 시작(3초 대기). 점검 이력 첫 화면(클릭 전)을 4초 그대로 둔다(말: 화면은 네 영역). 커서는 왼쪽 메뉴 가까이에 둔다 |
| 2 | 왼쪽 메뉴의 **설정 아이콘**(슬라이더 모양) 클릭 → 설정은 **"대상 서비스" 탭**으로 열린다. 상단 세 탭(`대상 서비스` · `점검 규칙 14` · `기능 점검 1`) 위로 커서를 차례로 옮긴다(탭마다 약 2초, 총 5.8초). 서비스를 눌러 열지는 않는다. 말: "설정 화면에서는 점검 대상 서비스의 구성과 점검 규칙, 기능 점검을 확인할 수 있습니다." |
| 3 | **"점검 규칙 14" 탭** 클릭(기본 보기 "단계별"). 단계 머리(0 환경, 1 빌드, 2 설정, 3 배포, 4 스케줄, 5 구동 …)를 위에서 아래로 천천히 훑는다(커서 약 9.8초). 말은 설정부터 구동까지 단계별 정의이고 각 규칙이 Pod·Service 같은 구성 요소를 기준으로 수립됐다는 설명이다. 규칙 줄을 눌러 열지는 않는다 |
| 4 | 목록 위쪽 **"구성별" 토글** 클릭 → 구성 요소별 묶음(Node, Pod, Workload, Service, Config, 개선 권고. 실제 그룹 이름은 촬영 때 확인)이 보이면 커서로 훑는다(약 3.3초). **S04는 짚지 않는다.** "단계별"로 되돌리거나 S04 줄까지 스크롤하지 않는다 |
| 5 | 왼쪽 메뉴의 **점검 이력 아이콘**(맥박 모양, 맨 위) 클릭. 목록의 "주기 점검" 행들(정각 시각 09:00, 07:00 …)을 위에서 아래로 가리키며 훑는다(커서 8초. 말은 정각마다 점검이 돌고 동작은 직접 점검으로 보여 준다는 한 줄이다). 화면에는 '정각 점검'이라는 글자가 없고 정각 점검은 "주기 점검" 라벨이다(필터 때문에 정각 행이 빠지면 심각도를 전체로). **CronJob 명령은 치지 않는다.** 이어 목록 첫 줄의 판정 "정상"과 근거 열 위에 커서 1.5초 → 상단 "열린 이슈 없음" 띠 위에 커서 2초(총 11.5초) |
| 6 | 왼쪽 메뉴의 **이슈 아이콘**(깃발 모양) 클릭 → 이슈 목록 위에 커서 4.5초. 이슈는 열지 않는다 |
| 7 | 화면 오른쪽 위 **"질문" 버튼** 클릭 → "이력에 질문" 패널이 열린다. **질문은 입력하지 않고** 패널 위에 커서 약 4초, 닫기(X) 클릭(총 5.3초) |
| 8 | `⌃→`로 데스크톱 2로 넘긴다(R2) |

⚠ 설정의 체크박스와 "저장"은 누르지 않는다(규칙 이름을 눌러 오른쪽 설명을 바꾸는 것도 이 투어에서는 하지 않는다). 촬영 때는 열린 이슈가 0이어야 한다.

### R2 서비스 주소명 오류 주입 (데스크톱 2 · L2)

| 순서 | 화면에서 할 일 |
|---|---|
| 1 | 명령 터미널은 빈 프롬프트. 명령 터미널에 입력: `KG_TYPO=dot bash scenarios/A7/inject.sh` (롤아웃이 끝나면 echo 한 줄이 나온다). 입력하는 동안(약 5.3초) 말은 "먼저 규칙 점검을 보여 드리기 위해, 서비스 주소명 오류 장애를 주입하겠습니다"이고 **오타(점)는 말하지 않는다** |
| 2 | (대기 · 편집에서 삭제) 롤아웃이 끝날 때까지 Pod 감시 터미널을 본다 |
| 3 | Pod 감시 터미널에서 gateway 새 Pod가 ContainerCreating → Running이 되고 이전 Pod가 Terminating이 되는 줄에 커서 2초 |
| 4 | 새 Pod가 `1/1 Running`으로 보이면 그 줄 위에 커서를 5.4초 둔다. 말: "Pod는 Ready이고 Service도 그대로라서, Kubernetes는 이 오류를 알지 못합니다" |
| 5 | `⌃→`로 데스크톱 3으로 넘어간다. 서비스 로그 터미널(오른쪽 아래)에서 끊긴 `logs -f`를 `Ctrl+C`로 끝내고 `↑` `↩`로 새 Pod 기준으로 다시 켠다(gateway 명령은 R5-2의 코드 블록). 새 줄이 올라오지 않는 것이 정상이다. (대기 · 편집에서 삭제. 이동과 다시 켜기는 모두 자른다) |
| 6 | 창 B가 점검 이력 화면인지 확인하고 그대로 R3을 이어 찍는다(L3 그대로, 넘김 없음) |

⚠ Slack은 누르지 않는다. ⚠ 주소 화면 노출 주의: 주입 명령의 출력 한 줄에 바뀐 주소(`http://agent.:8006`)가 그대로 찍히고, 명령 줄에도 `KG_TYPO=dot`이 보인다. 말은 하지 않지만 화면에 읽히므로 편집에서 그 부분(`→` 뒤)과 `KG_TYPO=dot`을 흐리게 가린다. 커서도 그 출력 줄 위에 두지 않는다(영상에서 오타는 R4의 근거 서랍에서 처음 나온다).

### R3 점검 실행 (데스크톱 3 · L3 · 창 B)

로그가 필요 없는 장면이다. 직접 점검은 web 컨테이너에서 돌아 Job 로그가 없다. 창 B는 묶음 시작 전에 점검 이력 화면을 열어 둔다(이 점검 화면을 R4까지 창 B에서 이어 간다). 창 B는 화면 왼쪽 2/3(1280×1080)라 L1보다 글자가 작으므로, 편집에서 창 B 안을 확대한다(1.3~1.5배. 오른쪽 1/3 터미널은 확대에서 잘려도 된다).

| 순서 | 화면에서 할 일 |
|---|---|
| 1 | R2에서 `⌃→`로 넘어와 서비스 로그 터미널을 다시 켠 뒤(편집에서 삭제) 창 B 우상단 "지금 점검" 버튼에 커서를 올렸다가 클릭(약 2.5초. 말: "지금 점검을 눌러 점검을 실행합니다") |
| 2 | (대기 · 편집에서 삭제) 점검 완료까지. 완료 시간은 리허설에서 확인. 점검 이력 맨 위 새 점검 줄을 눌러 점검 상세를 연다(주소를 복사하거나 붙이는 단계는 필요 없다) |
| 3 | 열어 둔 점검 상세에서 **S04 적발 줄**(점검 규칙 · 서비스 주소 설정 오류)에 커서를 5.2초 둔다(규칙 ID와 이름을 말하는 동안 줄 위에서 움직이지 않는다). 말: "여기, 점검 규칙 중 서비스 주소 설정 오류 규칙, S04 위반으로 적발되었습니다"(S04는 `docs/05-rules.md` 104행 표, 249행 절) |
| 4 | 넘김 없음. 같은 데스크톱 3의 창 B에서 R4를 이어 찍는다 |

| 순서 | 화면에서 할 일 |
|---|---|
| 1 | 창 B 왼쪽 메뉴 "점검 이력" 아이콘 클릭 |
| 2 | 목록에서 방금 점검 줄 클릭 → 점검 상세. 판정의 기능 점검 chat 실패 줄 위에 커서 2.6초(말: "기능 점검은 채팅이 실제로 되는지 직접 호출해 봅니다"), 이어 "조사 안 함 — 규칙 기반 진단 결과" 위에 1.9초(말 끝과 겹친다. 총 4.5초) |

### R5-2 작업자 로그와 서비스 로그 (데스크톱 3 · L3, R4에서 이어서)

서비스 주소명 오류 장면의 서비스 로그 터미널 명령(오른쪽 아래 1/4 칸. 묶음 1 시작 전에 켜 두고, R2 롤아웃이 끝나 L3에 도착하면 새 Pod 기준으로 다시 켠다. 네임스페이스 `dev`, 디플로이먼트 `gateway`, 컨테이너 `gateway`는 `kubectl -n dev get deploy`로 확인했다):

```bash
kubectl -n dev logs -f deploy/gateway -c gateway --since=1s
```

필터 없이 gateway 로그 전체를 띄운다. 기능 점검이 채팅을 부르면 아래 두 줄과 함께 같은 호출의 `업스트림 요청 실패 (시도 1/2)`, `ServiceException: CONNECTION_ERROR` 줄과 가끔 `GET /health` 줄도 찍힌다. 촬영에서는 아래 두 줄에 커서를 두고, 편집에서 박스와 확대로 강조한다(근거: 2026-11-19 같은 장애의 gateway Pod 로그를 읽기 전용으로 확인한 실측 줄이다. gateway 시각은 UTC라 작업자 로그의 한국 시각과 9시간 어긋난다. `scenarios/A7/README.md` "기대 증상"의 `Name or service not known`과 같다):

```text
2026-11-19 11:10:28 [INFO] gateway - 프록시 요청: POST /api/v1/agent/invoke -> http://agent.:8006/api/v1/invoke
2026-11-19 11:10:28 [ERROR] gateway - 업스트림 요청 최종 실패: http://agent.:8006/api/v1/invoke - [Errno -2] Name or service not known
```

작업자 로그 터미널(오른쪽 위 3/4 칸)에는 "지금 점검" 직후 아래 줄이 찍힌다(근거: 같은 날 같은 장애의 직접 점검 때 `kubectl -n kubeguardian logs deploy/diagnostic-agent --all-containers`로 읽기 전용 확인한 실측 줄이다. 이슈·근거 번호와 시각은 촬영 때 달라진다). 규칙 경로는 조사 대기열에 요청을 넣지 않으므로 `[조사 #N] …`·`[작업] 조사 대기 집음` 줄이 없다(`app/service/pipeline/investigate.py`의 `queue_investigations`. `[작업] … AI 조사 생략` 줄은 배포 전에 쌓인 요청이 있을 때만 나온다):

```text
2026-11-19 20:10:24 INFO [web] 127.0.0.1:58314 - "POST /llm-gateway/checks HTTP/1.1" 303
2026-11-19 20:10:29 INFO [web] [알림] M1 발송 이슈 #30 (Slack)
2026-11-19 20:10:29 INFO [worker] 근거 요약: ev-0833 done 2.1초 입력 397 출력 79
2026-11-19 20:10:33 INFO [worker] 근거 요약: ev-0834 done 3.0초 입력 339 출력 168
```

| 순서 | 화면에서 할 일 |
|---|---|
| 1 | R4 끝(L3)에서 이어서 찍는다. 창 B는 R4의 이슈 상세 그대로 둔다(이 구간에서 창 B는 짚지 않는다). 오른쪽 위 작업자 로그 터미널의 `[알림] M1 발송 …` 줄 → `근거 요약: ev-… done` 줄에 커서를 1.2초씩, 그 아래 빈 자리(`[조사 #N]` 줄이 없는 곳)에 0.8초(총 3.2초). 말: "작업자 로그에는 알림 발송과 근거 요약만 있고, AI 조사 줄은 없습니다." 확대와 박스는 편집 |
| 2 | 오른쪽 아래 서비스 로그 터미널의 `프록시 요청: POST /api/v1/agent/invoke -> http://agent.:8006/…` 줄 → `업스트림 요청 최종 실패 … Name or service not known` 줄에 커서를 1.1초씩(총 2.2초, 말 끝과 겹친다. 자막이 이 줄을 설명한다) |
| 3 | 마지막 줄 위에 커서를 둔다. **녹화는 끄지 않고**, 오른쪽 위에 Slack 배너가 떠 있으면 그대로 두고 `⌃←`로 데스크톱 2로 넘어간다(컷 없이 전환 애니메이션까지 한 테이크. R5-1). 배너가 없으면 그냥 `⌃←` |

⚠ 640×270 서비스 로그 칸은 줄이 접혀 약 9줄이다(16pt). 필터가 없으므로 R5-2에 도착했을 때 두 줄이 다른 줄에 밀려 칸 위로 사라졌으면 터미널을 위로 조금 스크롤해 두 줄을 칸 안에 둔다. 두 줄은 편집에서 박스로 강조하고 오른쪽 1/3 칸을 1.3배 확대한다 [촬영 시 확인].
⚠ R4에서 화면을 여는 접속 줄(`[web] … "GET …" 200`)이 알림 줄을 위로 밀어낼 수 있다. 밀려나면 작업자 로그 명령 끝에 `| grep --line-buffered -v '"GET '`를 붙여 묶음 1 시작 전에 켠다(묶음 2에도 그대로 써도 된다) [촬영 시 확인].
⚠ 오른쪽 위에 남아 있는 Slack 배너가 작업자 로그 터미널의 윗줄(알림·근거 요약 줄)을 가릴 수 있다. 가리면 이 장면을 찍기 전에 배너를 닫아 로그가 읽히게 한다(Slack 알림은 그대로 남는다). 그러면 `⌃←` 전환은 배너 없이 찍고 R5-1은 Slack 알림 확인으로 시작한다(배너 연출 생략) [촬영 시 확인].

### R6 서비스 주소명 오류 원복 · 정상 확인 · Slack 복구 알림 (데스크톱 2 → 1 → 2 · L2 → L1 → L2, 이어서 녹화)

| 순서 | 화면에서 할 일 |

| 1 | R5-1 끝(L2)에서 이어 명령 터미널에 입력: `bash scenarios/A7/reset.sh` (롤아웃이 끝나면 `A7 원복: …` echo 한 줄. 롤아웃 대기는 편집에서 삭제). Pod 감시 터미널에서 gateway 새 Pod가 올라오고 이전 Pod가 Terminating이 되는 줄은 편집에서 잠깐 스치게 두고 커서를 올리지 않아도 된다 |
| 2 | `⌃←`로 데스크톱 1(L1)로 넘어간다(편집에서 전환을 자른다). 창 A는 R1을 마친 이슈 목록 화면이므로 왼쪽 메뉴 **점검 이력 아이콘**(맥박 모양)을 클릭해 점검 이력 화면으로 간다 |
| 3 | 우상단 "지금 점검" 버튼에 커서를 올렸다가 클릭 |
| 4 | (대기 · 편집에서 삭제) 점검이 끝날 때까지 |
| 5 | 목록 맨 위에 새 점검 줄이 올라오면 그 줄의 판정 "정상" 위에 커서 1.5초(편집에서 박스). 이어 상단 "열린 이슈 없음" 띠(또는 이슈 해결 표시) 위로 커서를 옮겨 그대로 둔다. 실제 화면 문구는 R1-2의 "열린 이슈 없음" 띠를 따르고, 이슈 해결이 점검 줄에 어떻게 표시되는지(`해결 #N` 같은 문구)는 [촬영 시 확인] |

Slack에서 **복구 알림**을 확인한다. 코드(`app/service/notify/messages.py`의 `recovery`) 기준 문구는 `✅ 복구 · {네임스페이스} — {대상 기능}이 정상으로 돌아왔습니다`, `확인: {HH:MM} 점검`, `장애 지속: 약 {N}분`, `이슈` 링크이고, 스레드 답글이면서 채널에도 보이게 발송된다. 제목 줄 → `장애 지속` 줄 위에 커서(총 약 2.8초) [촬영 시 확인] 실제 대상 기능 이름과 줄 순서, 알림이 스레드·채널 어느 쪽에 보이는지 |
