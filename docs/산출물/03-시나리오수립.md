# 3. 시나리오 수립 (상세본)

> 제출본은 [양식/03](양식/03-시나리오수립.md)이다. 이 문서에는 제출본에 다 담지 못한 전체 보고서 예시와 평가 시나리오 연결만 둔다. 예시는 설계한 흐름을 보여주는 것이고, 근거 번호와 Pod 이름은 예시 값이다.

## 1. 표기와 사용 방식

| 표기 | 뜻 |
|---|---|
| 근거 번호 | 도구가 수집한 데이터 한 건의 번호(예: ev-0012). 마스킹한 원문, 수집 시각, 출처는 화면의 근거 서랍에서 본다 |
| 판단 수준 | 결론을 무엇으로 확인했는지를 코드가 정하는 확정, 후보, 추정 |
| 가설 판정 | 지지(근거가 뒷받침), 반증(근거가 반박), 판단 불가(근거 부족) |
| 심각도 | 긴급(핵심 경로 장애), 주의(일부 사용자나 기능 실패), 잠재 위험과 개선 권고(알림 없이 화면에만 표시) |

| 시나리오 | 시작 방식 | 결과를 받는 곳 |
|---|---|---|
| SC-001 주기 점검과 이상 알림 | 자동, 매시 정각 | Slack 알림, 이슈 상세의 보고서 |
| SC-002 배포 직후 점검 | 직접, 화면의 지금 점검 또는 CLI kg check | 점검 상세와 이슈 상세, 이상이면 Slack 알림 |
| SC-003 증상 입력 조사 | 직접, CLI kg investigate | 터미널 요약 |

Slack은 알림 전용이다. 직접 점검은 보고서 화면의 지금 점검 버튼과 CLI kg check, 증상을 입력한 조사는 CLI kg investigate로 한다.

## 2. SC-001의 전체 보고서 예시

이슈 상세 화면은 결론, 문제, 사전 확인, 가설 판정, 확인한 범위, 권장 조치, 재검증의 일곱 절로 구성된다. 아래는 같은 내용을 글로 옮긴 것이다.

```text
[조사 보고서] 채팅 실패, llm-gateway의 LLM 호출 실패         판단 수준: 후보

결론
  agent가 llm-gateway의 LLM 호출에서 429(insufficient_quota)를 받아 채팅이 실패하고 있습니다.

문제
  1순위 채팅 실패 (긴급, 핵심 경로 장애)

사전 확인 (가설 없이 확인한 사실)
  채팅 호출을 다시 돌리니 로그인은 성공하고 채팅 단계가 실패합니다 [ev-0003]
  dev의 Pod는 모두 Ready이고 재시작이 없으며 Service 연결은 정상입니다 [ev-0002]
  실패 경로 서비스의 최근 30분 오류 로그에 429가 있습니다 [ev-0005]

가설 판정
  1. gateway나 agent Pod 자체의 문제   반증: Pod가 모두 Ready이고 오류는 하위 호출의 429뿐입니다 [ev-0002, ev-0005]
  2. llm-gateway의 LLM 호출 실패       지지: agent 로그에 429가 반복됩니다 [ev-0005, ev-0008]
  3. DB나 Redis 연결 문제              반증: 로그인이 성공합니다 [ev-0003]

확인한 범위
  구동, 연결, 로그 영역을 확인했습니다.
  설정 영역은 llm-gateway의 한도 설정을 직접 조회하지 못해 확인하지 못했습니다.

권장 조치 (자동 실행하지 않음)
  llm-gateway의 LLM 할당량을 확인하고 한도를 올리거나 초기화합니다.

재검증
  보고서 화면의 지금 점검 또는 kg check를 실행하거나 다음 정각 점검을 기다려 채팅 단계가 성공하는지 봅니다.
```

## 3. SC-003의 전체 보고서 예시

```text
[조사 보고서] 채팅 간헐 실패, agent Pod 1개만 오류             판단 수준: 후보

결론
  agent Pod 3개 중 agent-6d9f7c5b8-p9m2k만 채팅 요청에 500을 반환합니다. Service가 요청을 3개 Pod에
  나눠 보내므로 요청의 일부만 실패합니다.

사전 확인 (가설 없이 확인한 사실)
  입력한 증상으로 기능 점검을 다시 돌렸습니다 [ev-0004]
  agent Pod 3개가 모두 Ready이고 Endpoint 3개가 정상입니다 [ev-0003]

가설 판정
  1. 특정 Pod만 오류                   지지: Pod를 직접 부르면 2개는 200, p9m2k는 500입니다 [ev-0007]
  2. 하위 서비스의 간헐적 지연          판단 불가: 성공한 요청에서는 지연이 없지만 실패 요청의 하위 호출은 보지 못했습니다
  3. 외부 LLM 호출의 간헐 실패          반증: 정상 Pod 2개는 매번 성공합니다 [ev-0007]

확인한 범위
  구동, 연결, 로그 영역을 확인했습니다. p9m2k가 오류를 내기 시작한 시각은 확인하지 못했습니다.

권장 조치 (자동 실행하지 않음)
  p9m2k Pod를 삭제해 Deployment가 새 Pod를 띄우게 합니다.

재검증
  kg investigate로 같은 증상을 다시 조사하거나 kg check로 기능 점검이 성공하는지 봅니다.
```

## 4. 평가 시나리오 연결

사용자 시나리오는 원인을 아는 장애를 일부러 만들어 넣는 평가 시나리오로 검증한다. 시나리오 폴더는 10개다. 층별 채점 대상은 장애 6개(A1, A3, A5, B1, C1, C2)와 정상 기준선 2개(H0, H1)이고, C8과 A7은 시연 겸 사전 시험이라 채점 대상에 넣지 않았다. 기획 때 계획한 C5(스키마 불일치), E1(미끼 신호가 섞인 C2), A6은 만들지 않았다.

| ID | 사용자가 겪는 증상 | 실제 원인 | K8s 상태로 원인이 보이나 | 진단 시작 계기 | 연결 |
|---|---|---|---|---|---|
| A1 | agent를 거치는 기능 전부 실패 | agent Service selector 값 오타 | 보임 | 규칙 적발 (경로 A) | SC-002 |
| A3 | 새 버전이 뜨지 않음 | agent 이미지를 해석되지 않는 레지스트리로 변경 | 보임 | 규칙 적발 (장애 신호). 지속 시간 규칙이라 평가 러너(5분 간격 반복 점검)로는 약 25분, 운영에서는 조건이 충족된 뒤 다음 정시 점검 | SC-002 |
| A5 | 모든 API 실패 | gateway의 하위 서비스 주소 env 4개가 localhost | 보임 | 규칙 적발 (경로 A) | SC-002 |
| B1 | 요청의 일부만 실패 | agent Pod 3개 중 1개가 모든 HTTP 응답을 500으로 반환 (Chaos Mesh) | 보임 (Pod별 확인이 필요) | 사용자 증상 입력 (경로 B) | SC-003 |
| C1 | 채팅 실패 | llm-gateway의 채팅 완성 응답이 429(insufficient_quota) (Chaos Mesh) | 안 보임 | 기능 점검 실패 (경로 B) | SC-001 |
| C2 | 로그인 504, Pod 전부 정상 | admin과 Redis 사이 패킷 차단 (Chaos Mesh) | 안 보임 | 기능 점검 실패 (경로 B) | SC-001 |
| H0 | 없음 | 없음 (개선 권고만 존재) | 해당 없음 | 조사하지 않음 (경로 C) | SC-001의 정상 흐름 |
| H1 | 없음 | 설정이 없어도 정상인 서비스 | 해당 없음 | 조사하지 않음 (경로 C) | 오탐 기준선 |
| A7 | 채팅 호출 500 | gateway의 agent 주소 끝에 점 또는 대시 한 글자 | 보임 | 규칙 적발 (경로 A) | L1 시연 |
| C8 | 채팅 실패 | llm-gateway DB의 활성 배포명을 허용되지 않은 값으로 변경 | 안 보임 | 기능 점검 실패 (경로 B) | L3 시연 |

- 경로 A는 규칙이 장애 신호를 적발해 AI 조사 없이 규칙 기반 진단 결과로 끝나는 경우, 경로 B는 규칙 신호 없이 기능 점검 실패나 사용자 증상으로 시작하는 경우, 경로 C는 조사하지 않는 경우다.
- K8s 상태로 원인이 보이지 않는 시나리오(C1, C2)가 KPI 원인 규명 커버리지의 측정 대상이다.
- 평가 중에는 Slack 전송 없이 알림 이력에 기록한다.
