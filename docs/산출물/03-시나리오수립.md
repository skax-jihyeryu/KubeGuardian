# 3. 시나리오 수립

> 작성일: 2026-10-04 · 상세: [기획서](../01-project-proposal.md), [문제 정의 및 서비스 기획](02-문제정의및서비스기획.md)
>
> 이 문서는 **사용자가 KubeGuardian을 쓰는 흐름**을 정리한다. 각 시나리오의 예시 상황은 평가용 장애 시나리오(문서 끝 "평가 시나리오 연결")에서 가져왔다.

**읽기 전에: 출력 예시의 표기**

| 표기 | 뜻 |
|---|---|
| `[근거 12]` | 도구가 수집한 데이터 한 건의 번호. 화면에서 누르면 원문(마스킹 후), 수집 시각, 출처가 열린다 |
| 확신도 | 에이전트가 판정에 붙이는 높음 / 중간 / 낮음 |
| 가설 판정 | 지지(근거가 뒷받침) / 배제(근거가 반박) / 판단 보류(근거 부족) |

## 핵심 사용자 시나리오

### 시나리오 1 : 증상 입력으로 원인 조사 받기

- **ID** : SC-001
- **상황** : PR 담당자에게서 "보도자료 초안 생성을 누르면 오류가 나요"라는 문의를 받았다. `kubectl get pods`로 보면 **모든 Pod가 Running·Ready**로 정상이라 어디부터 봐야 할지 모른다.
  - 실제 원인: llm-gateway의 LLM 사용 할당량 소진. Kubernetes 상태로는 보이지 않는 장애다.
- **목표** : 증상만 입력해서 원인 서비스, 원인, 근거, 조치 방법을 빠르게 얻는다.
- **사전 조건** :
  - KubeGuardian이 진단 대상 네임스페이스(`dev`)에 조회 전용 권한으로 설치되어 있음
  - 설정 파일에 대상 네임스페이스, 증상 감지용 API 호출 순서(로그인 → 채팅), 조회를 허용할 앱 API(llm-gateway 상태·할당량)가 등록되어 있음
  - Azure OpenAI 연결 정상
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 입력창에 "초안 생성하면 502가 나요" 입력 | 사용자가 증상을 입력했으므로 규칙 결과와 관계없이 **AI 조사를 바로 시작** | |
| 2 | 진행 화면 확인 | 규칙 점검과 증상 감지 실행. 규칙은 모두 통과, 로그인 → 채팅 API 호출에서 채팅 단계 실패 확인 | 진행 단계가 실시간으로 표시됨 |
| 3 | 조사 계획 확인 | 증상을 해석해 **조사 계획과 원인 가설(최대 3개)을 먼저 보여줌**: ① agent 자체 오류 ② llm-gateway 이상 ③ DB·Redis 연결 문제 | |
| 4 | 도구 호출 단계 확인 (선택) | 서비스 호출 관계를 따라 거슬러 올라가며 확인: gateway의 하위 서비스 조회 → 채팅 API 재호출 → agent 로그 조회 → llm-gateway 할당량 조회. 결과는 모두 근거로 저장 | 조사 1건당 도구 호출 20회·150초 이내 |
| 5 | — | 가설 판정: ② 지지, ①·③ 배제. 보고서를 쓰고 **검증 코드가 모든 사실 문장의 근거 인용을 확인** | 인용 없는 문장은 "추정"으로 표시 |
| 6 | 보고서 확인, `[근거 15]` 클릭 | 근거 원문(마스킹 후), 수집 시각, 출처 API 표시 | |

- **입력 예시**

```text
보도자료 초안 생성하면 502가 나요. Pod는 전부 Running 상태입니다.
```

- **기대 출력**

```text
[조사 보고서] 채팅 실패 — llm-gateway 할당량 소진          확신도: 높음

■ 결론
  front-chat → gateway → agent → llm-gateway 경로에서 llm-gateway가 429(요청 한도 초과)를
  반환해 gateway가 502로 응답하고 있습니다.

■ 근거
  - 채팅 API 호출: 로그인 성공, 채팅 요청 502 [근거 12]
  - agent 로그: "llm-gateway returned 429 Too Many Requests" [근거 14]
  - llm-gateway 할당량 API: 오늘 사용량이 한도의 100% [근거 15]
  - dev 네임스페이스 Pod 전체 Running·Ready, 재시작 없음 [근거 3]

■ 가설 판정
  ① agent 자체 오류      — 배제 (agent 상태 확인 200, 오류는 하위 호출의 429뿐) [근거 13]
  ② llm-gateway 할당량   — 지지 [근거 14, 15]
  ③ DB·Redis 연결 문제   — 배제 (로그인 성공) [근거 12]

■ 권장 조치 (자동 실행하지 않음)
  llm-gateway 관리 화면에서 할당량 상향 또는 초기화

■ 재검증 방법
  kg check 실행 → 로그인 → 채팅 API 호출 성공 확인
```

- **성공 기준**
  - 기준 1: 보고서 1순위 원인이 정답(llm-gateway 할당량 소진)과 일치 — KPI "원인 규명 커버리지"에 포함되는 시나리오
  - 기준 2: 모든 사실 문장이 근거를 인용 (근거 인용률 100%)
  - 기준 3: 증상 입력부터 보고서 완성까지 120초 이내 (중앙값)

### 시나리오 2 : 배포 후 점검과 "지금 중요한 것" 요약 받기

- **ID** : SC-002
- **상황** : agent의 Kubernetes 배포 설정을 수정해 배포한 직후, 정상인지 확인하려고 점검을 실행한다. 채팅이 전부 실패하는데, 화면에는 경고·이벤트·과거 재시작 기록이 수십 개 섞여 있다.
  - 실제 원인: agent Service(내부 주소)의 대상 Pod 라벨 조건에 오타가 생겨, 요청을 받을 Pod가 0개가 됨.
- **목표** : 수십 개 신호 중 **지금 장애의 원인이 되는 것만** 골라 영향 순으로 보고, 나머지는 개선 권고로 분리해서 본다.
- **사전 조건** :
  - KubeGuardian 설치, 대상 서비스 배포 완료
  - KubeGuardian 전용 계정에 조회 권한(get/list/watch)
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 화면에서 [점검] 클릭 또는 CLI `kg check` | 리소스 수집 → 서비스 호출 관계 구성 (각 앱 설정의 서비스 주소를 실제 Service와 대조) | |
| 2 | — | 규칙 점검: **"agent Service에 연결된 Pod 0개"** 를 장애로 확정. 그 밖에 "준비 상태 확인이 포트 연결만 봄" 같은 항목은 개선 권고로 분류 | 코드로 판정 |
| 3 | — | 증상 감지: 로그인 → 채팅 API 호출에서 채팅 실패 | |
| 4 | — | 규칙이 장애를 찾았으므로 **AI 조사 시작**. 원시 신호 47개를 서비스별로 묶어 에이전트에 전달 | 장애도 증상도 없으면 AI를 호출하지 않음 |
| 5 | 요약 확인 | AI가 사용자 영향 순으로 **중요 문제 최대 3건**을 고르고, 무관한 신호는 개선 권고로 분리. 상위 문제는 도구로 추가 확인 후 원인·영향·근거 작성 | 문제 1건당 도구 호출 8회 이내 |
| 6 | 1순위 항목의 [자세히 조사] 클릭 | 해당 문제의 조사 보고서(시나리오 1과 같은 형식)로 이동 | |

- **입력 예시**

```bash
$ kg check --namespace dev
```

- **기대 출력**

```text
규칙 점검: 장애 1건, 개선 권고 3건 / 증상 감지: 채팅 API 실패
→ 규칙이 장애를 찾아 AI 조사를 시작합니다.

지금 중요한 것 1건 (수집된 신호 47개 중)
 1. 🔴 채팅이 전부 실패합니다 (확신도 높음)
    agent Service의 대상 Pod 조건이 app=agnet으로 되어 있어 연결된 Pod가 0개입니다 [근거 4].
    agent Pod 3개의 라벨은 app=agent입니다 [근거 5].
    방금 배포에서 이 값이 바뀌었습니다 [근거 6].
    조치: Service의 대상 Pod 조건을 app=agent로 수정

참고 — 개선 권고 (지금 장애와 무관)
 - 준비 상태 확인이 포트 연결만 봄 (6개 서비스)
 - CPU·메모리 요청·제한값 미설정 (2개 서비스)
 - agent Pod 1개의 어제 재시작 기록 1건: 이후 정상 동작 중
```

- **대안 흐름 — 정상일 때**: 규칙 장애도 증상도 없으면 AI를 호출하지 않고 "규칙 점검 통과, 증상 없음 + 개선 권고 3건"만 표시한다.
- **성공 기준**
  - 기준 1: 요약 1순위가 실제 원인(Service 대상 Pod 조건 오타)과 일치 (KPI "원인 정확도")
  - 기준 2: 신호 압축률 90% 이상 (47개 → 1건)
  - 기준 3: 정상 환경에서는 개선 권고만 표시되고 AI를 호출하지 않음 (KPI "정상 시 AI 미호출")

### 시나리오 3 : 조사 결과에 대해 후속 질문하기

- **ID** : SC-003
- **상황** : 시나리오 1·2의 보고서를 받은 뒤, AI의 판단을 그대로 믿기 전에 근거를 더 확인하거나 조치 방법을 묻고 싶다.
- **목표** : 근거를 인용한 답변으로 AI의 판단을 검증하고 다음 행동을 정한다.
- **사전 조건** : 조사 보고서가 생성되어 근거가 저장되어 있음
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 보고서 화면에서 "agent가 원인일 가능성은 정말 없어?" 입력 | 이미 저장된 근거로 답할 수 있는지 판단 | |
| 2 | — | 필요하면 도구를 추가로 호출 (예: agent Pod 3개를 각각 직접 호출해 상태 확인) | 조회만 함 |
| 3 | 답변 확인 | 근거를 인용한 답변 작성 → 검증 코드 통과 | |

- **입력 예시**

```text
agent가 원인일 가능성은 정말 없어? agent Pod 3개 모두 확인한 거야?
```

- **기대 출력**

```text
agent Pod 3개를 각각 직접 호출해 확인했습니다.
- agent-x2k, agent-p9m, agent-q4t 모두 상태 확인 200 응답 [근거 41, 42, 43]
- 3개 Pod의 오류 로그는 모두 llm-gateway의 429 응답뿐입니다 [근거 14, 44]
따라서 agent 자체보다 llm-gateway 할당량이 원인이라는 판단을 유지합니다.
```

- **성공 기준**
  - 기준 1: 답변의 사실 문장이 모두 근거를 인용
  - 기준 2: "재시작해 줘" 같은 클러스터 변경 요청은 실행하지 않고 명령어와 방법만 안내

## 평가 시나리오 연결

사용자 시나리오는 원인을 미리 아는 장애를 일부러 만들어 넣는 **평가용 장애 시나리오 8개 + 정상 환경 1개**로 검증한다.

| # | 난이도 | 사용자가 겪는 증상 | 실제 원인 | Kubernetes 상태로 원인이 보이나 | AI 조사 시작 계기 | 연결 |
|---|---|---|---|---|---|---|
| 1 | 신호 하나로 확정 | agent 관련 기능 전부 실패 | Service 대상 Pod 조건 오타 | 보임 | 규칙이 장애 적발 | SC-002 |
| 2 | 신호 하나로 확정 | 새 버전이 뜨지 않음 | 존재하지 않는 이미지 버전 지정 | 보임 | 규칙이 장애 적발 | SC-002 |
| 3 | 신호 하나로 확정 | 모든 API 502 | 서비스 주소 설정 누락 (원본 템플릿 상태, 데모용) | 보임 (설정 대조 시) | 규칙이 장애 적발 | SC-002 |
| 4 | 여러 신호 연결 | 요청의 약 1/3만 실패 | agent Pod 3개 중 1개만 오류 | 일부 | 증상 감지 | SC-001 |
| 5 | **원인이 다른 서비스** | 채팅 실패 (502) | llm-gateway LLM 할당량 소진 | **안 보임** | 증상 감지 | SC-001 |
| 6 | **원인이 다른 서비스** | 로그인 불가, Pod 전부 정상 | admin ↔ Redis 네트워크 차단 | **안 보임** | 증상 감지 | SC-001 |
| 7 | **원인이 다른 서비스** | 특정 API만 500 | 새 버전이 DB 컬럼을 추가했는데 DB에 반영 안 됨 | **안 보임** | 증상 감지 | SC-001 |
| 8 | 헷갈리는 신호 | 로그인 불가 | 6번 + 과거의 무해한 재시작 기록이 미끼로 섞임 | 안 보임 | 규칙 + 증상 | SC-001, SC-002 |
| — | 정상 | 없음 | 없음 (개선 권고만 존재) | — | AI 호출 안 함 | SC-002 대안 흐름 |

- **"안 보임" 시나리오(5~8번)**가 KPI "원인 규명 커버리지"의 측정 대상이다.
- 모든 사용자 시나리오는 후속 질문(SC-003)으로 이어질 수 있다.
