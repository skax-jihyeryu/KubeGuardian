# 3. 시나리오 수립

> 작성일: 2026-09-29 · 상세: [기획서 §5·§9](../01-project-proposal.md), [UI 화면 정의서](../04-ui-spec.md)

> 이 문서의 시나리오는 **사용자가 KubeGuardian을 쓰는 흐름**이다. 평가용 장애 주입 시나리오(A1~E1)는 각 사용자 시나리오의 예시 상황으로 연결해 두었다.

## 핵심 사용자 시나리오

### 시나리오 1 : 증상 입력 기반 AI 원인 조사 (규칙 사각지대)

- **ID** : SC-001
- **상황** : 사용자가 "채팅이 안 된다"는 문의를 받았다. `kubectl get pods`로 보면 **모든 Pod가 Running·Ready**라 어디부터 봐야 할지 모른다. (평가 시나리오 C1: llm-gateway 할당량 소진)
- **목표** : 증상만 입력해서 원인 서비스와 원인, 근거, 조치 방법을 빠르게 얻는다.
- **사전 조건** :
  - KubeGuardian이 진단 대상 네임스페이스(`dev`)에 읽기 전용 권한으로 설치되어 있음
  - `kubeguardian.yaml`에 대상 네임스페이스, 핵심 API 시나리오(로그인 → 채팅), 앱 조회 허용 목록(llm-gateway health·quota)이 설정됨
  - Azure OpenAI 연결 정상
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 워크스페이스 입력창에 "채팅하면 502가 나요" 입력 | 사용자 증상 입력 → **게이트 경로 B**로 즉시 AI 조사 시작 | 규칙 결과와 무관하게 조사 |
| 2 | 진행 화면 확인 | 규칙 점검·증상 센서 실행 결과를 신호판으로 구성. 규칙은 모두 통과, 채팅 API 시나리오 실패 확인 | SSE로 실시간 표시 |
| 3 | 조사 계획 확인 | 증상을 해석하고 **조사 계획과 가설(최대 3개)을 먼저 출력**: ① agent 오류 ② llm-gateway 이상 ③ DB·Redis 연결 문제 | 계획이 UI 타임라인에 표시 |
| 4 | 도구 호출 단계 확인 (선택) | 토폴로지를 따라 역추적: `get_topology(gateway)` → `run_api_scenario(chat)` → `get_pod_logs(agent)` → `query_app_api(llm-gateway, /quota)` 호출, 결과를 evidence로 저장 | 도구 호출 ≤ 20회, ≤ 150초 |
| 5 | — | 가설 판정: ② 지지, ①·③ 배제. 보고서 작성 → **근거 검증기**가 모든 사실 문장의 evidence id 인용 확인 | 인용 없는 문장은 "추정"으로 강등 |
| 6 | 보고서 확인, 근거 칩 `[ev-15]` 클릭 | 근거 드로어에 원문(마스킹 후), 수집 시각, 출처 API 표시 | |

- **입력 예시**

```text
채팅하면 502가 나요. Pod는 전부 Running 상태입니다.
```

- **기대 출력**

```text
[조사 보고서] 채팅 실패 — llm-gateway 할당량 소진          확신도: 높음

■ 결론
  front-chat → gateway → agent → llm-gateway 경로에서 llm-gateway가 429를 반환해
  gateway가 502로 응답하고 있습니다.

■ 근거
  - 채팅 API 시나리오: 로그인 성공, /agent/invoke 502 [ev-12]
  - agent 로그: "llm-gateway returned 429 Too Many Requests" [ev-14]
  - llm-gateway quota API: 오늘 사용량 100% / 한도 [ev-15]
  - dev 네임스페이스 Pod 전체 Running·Ready, 재시작 없음 [ev-3]

■ 가설 판정
  ① agent 자체 오류      — 배제 (agent /health 200, 오류는 하위 호출 429뿐) [ev-13]
  ② llm-gateway 할당량   — 지지 [ev-14, ev-15]
  ③ DB·Redis 연결 문제   — 배제 (로그인 성공) [ev-12]

■ 권장 조치 (자동 실행하지 않음)
  llm-gateway 관리 화면에서 할당량 상향 또는 초기화

■ 재검증 방법
  kg check 실행 → 채팅 API 시나리오 성공 확인
```

- **성공 기준**
  - 기준 1: 보고서 1순위 원인이 정답(llm-gateway 할당량 소진)과 일치 (L3 원인 Top-1 ≥ 70%)
  - 기준 2: 모든 사실 문장이 유효한 evidence id를 인용 (근거 인용률 100%)
  - 기준 3: 증상 입력부터 보고서 완성까지 120초 이내 (p50)

### 시나리오 2 : 정기·배포 후 점검과 "지금 중요한 것" 브리핑

- **ID** : SC-002
- **상황** : 새 서비스를 템플릿으로 시작해 클러스터에 처음 배포한 직후, 또는 주기 점검 시점. 모든 API가 502를 반환하지만 이벤트·경고가 여러 개 섞여 있다. (평가 시나리오 A5: 서비스 주소 설정 누락 → gateway가 `localhost` 호출)
- **목표** : 수십 개 신호 중 **지금 장애의 원인이 되는 것만** 골라 영향 순으로 보고, 나머지는 개선 권고로 분리한다.
- **사전 조건** :
  - KubeGuardian 설치, 대상 서비스 배포 완료
  - 진단용 ServiceAccount에 `get/list/watch` 권한
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 워크스페이스에서 [점검] 클릭 또는 CLI `kg check` | 리소스 수집 → 토폴로지 구성 (env의 `*_SERVICE_URL`을 Service와 매칭) | 주기·배포 후 자동 실행도 가능 |
| 2 | — | 감지기 26종 실행: **S04**(gateway env URL이 `localhost`를 가리킴) 장애 신호, H01(tcpSocket probe) 등 개선 권고 | 결정적 코드 |
| 3 | — | 증상 센서: 채팅 API 시나리오 실패 | |
| 4 | — | **게이트 경로 A** 판정 → AI 선별 시작. 신호판(원시 신호 47개)을 서비스별로 묶어 전달 | 정상이면 경로 C로 AI 미호출 |
| 5 | 브리핑 확인 | AI가 사용자 영향 순으로 **중요 이슈 최대 3건** 선별, 무관 신호는 개선 권고로 분리. 상위 이슈는 도구로 추가 확인 후 원인·영향·근거 작성 | 이슈당 도구 ≤ 8회 |
| 6 | 1순위 항목 [자세히 조사] 클릭 | 해당 이슈의 조사 보고서(SC-001과 같은 형식)로 이동 | |

- **입력 예시**

```bash
$ kg check --namespace dev
```

- **기대 출력**

```text
규칙 26개 중 1개 장애 신호, 개선 권고 3건 / 증상 센서: 채팅 API 실패
→ AI 게이트: 경로 A (규칙 적발) — AI 선별을 시작합니다.

지금 중요한 것 1건 (신호 47개 중)
 1. 🔴 모든 API가 실패합니다 (확신도 높음)
    gateway의 AGENT_SERVICE_URL 등 하위 서비스 주소가 http://localhost:* 입니다 [ev-4].
    클러스터 안에서 gateway는 agent·admin·llm-gateway를 찾지 못합니다 [ev-7, ev-9].
    조치: 매니페스트에 서비스 주소 env 추가 (예: http://agent:8006)

참고 — 개선 권고 (지금 장애와 무관)
 - readinessProbe가 포트 연결만 확인 (6개 서비스) [H01]
 - requests·limits 미설정 (2개 서비스) [H02]
```

- **성공 기준**
  - 기준 1: 브리핑 1순위 = 주입한 장애 (L1–L2 선별 정확도 ≥ 90%)
  - 기준 2: 신호 압축률 ≥ 90% (원시 신호 수 대비 브리핑 이슈 수)
  - 기준 3: 정상 환경(H0)에서는 개선 권고만 표시되고 AI를 호출하지 않음 (게이트 정확도 100%)

### 시나리오 3 : 배포 변경 검증

- **ID** : SC-003
- **상황** : 개발자가 agent 새 버전을 롤아웃한 직후 "방금 배포 괜찮아?"를 확인하고 싶다. 롤아웃이 멈추고 일부 요청이 실패한다. (평가 시나리오 B2: 신규 ReplicaSet에만 잘못된 env)
- **목표** : 무엇이 바뀌었는지, 그 변경이 어떤 서비스에 영향을 주는지, 안전한지 판정받는다.
- **사전 조건** :
  - 배포 전 스냅샷이 저장되어 있음 (주기 점검 또는 수동 스냅샷)
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | `kg verify --after-change` 또는 화면에서 [변경 검증] | before·after 스냅샷 diff 계산 (Deployment·RS·Service·ConfigMap 등) | |
| 2 | — | 토폴로지로 **영향 범위** 산출 (agent 변경 → gateway → front-chat) 후 해당 범위 재검증 | 결정적 |
| 3 | — | 규칙 W02(롤아웃 정체)·P06(CrashLoop) 적발 → diff와 실패 결과를 AI 조사로 전달 | 모두 통과면 "안전" 판정으로 종료, AI 미호출 |
| 4 | 판정 확인 | AI가 변경의 의미를 해석하고 **안전 / 주의 / 위험** 판정 + 근거 | |
| 5 | diff 드로어 확인 | 변경 타임라인과 리소스별 diff 원문 표시 | |

- **입력 예시**

```bash
$ kg verify --after-change --before snap-20261020-1002
```

- **기대 출력**

```text
변경 판정: 🔴 위험

변경 내용
  - Deployment/agent: image 0.0.1 → 0.0.2, env DATABASE_URL 변경 [ev-31]
영향 범위
  agent → gateway → front-chat
원인
  신규 ReplicaSet(agent-5d8f)의 Pod만 DB 연결 실패로 CrashLoopBackOff입니다 [ev-33, ev-34].
  구 ReplicaSet Pod 2개가 트래픽을 받고 있어 요청 일부만 실패합니다 [ev-35].
  롤아웃은 ProgressDeadlineExceeded로 멈췄습니다 [ev-32].
권장 조치
  DATABASE_URL 값 확인 후 재배포, 또는 kubectl rollout undo deployment/agent
```

- **성공 기준**
  - 기준 1: "신규 ReplicaSet의 env 변경"이 원인으로 판정됨
  - 기준 2: 변경이 없는 경우·문제없는 변경은 AI 호출 없이 "안전" 판정

### 시나리오 4 : 조사 결과에 대한 후속 대화

- **ID** : SC-004
- **상황** : SC-001·SC-002의 보고서를 받은 뒤, 판단 근거를 더 확인하거나 조치 방법을 묻고 싶다.
- **목표** : 근거를 인용한 답변으로 AI 판단을 검증하고, 다음 행동을 결정한다.
- **사전 조건** : 조사 보고서가 생성되어 evidence가 저장되어 있음
- **상세 흐름**

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|
| 1 | 보고서 화면에서 "agent가 원인일 가능성은 정말 없어?" 입력 | 기존 evidence 재사용으로 답변 가능한지 판단 | |
| 2 | — | 필요 시 도구 추가 호출 (예: `compare_pods`, `probe(agent, via=pod)`) | 읽기 전용 |
| 3 | 답변 확인 | 근거 인용 답변 작성 → 근거 검증기 통과 | |

- **입력 예시**

```text
agent가 원인일 가능성은 정말 없어? agent Pod 3개 모두 확인한 거야?
```

- **기대 출력**

```text
agent Pod 3개를 각각 직접 호출해 확인했습니다.
- agent-x2k, agent-p9m, agent-q4t 모두 /health 200 응답 [ev-41, ev-42, ev-43]
- 3개 Pod의 오류 로그는 모두 llm-gateway 429 응답뿐입니다 [ev-14, ev-44]
따라서 agent 자체보다 llm-gateway 할당량이 원인이라는 판단을 유지합니다.
```

- **성공 기준**
  - 기준 1: 답변의 사실 문장이 모두 evidence를 인용
  - 기준 2: 클러스터 변경 요청(예: "재시작해 줘")에는 실행하지 않고 명령어·방법만 안내

### 평가 시나리오 연결

사용자 시나리오는 난이도별 장애 주입 시나리오(16개)로 검증한다.

| 사용자 시나리오 | 게이트 경로 | 대표 평가 시나리오 |
|---|---|---|
| SC-001 | B (규칙 통과 + 증상) | C1 할당량 소진, C2 Redis 연결 차단, C5 스키마 드리프트, D1 CPU 제한 연쇄 타임아웃 |
| SC-002 | A (규칙 적발) / C (정상) | A1 selector 오타, A5 서비스 주소 누락, E1 미끼 신호, H0 정상 |
| SC-003 | A (변경 후 규칙 적발) | B2 신규 ReplicaSet env 오류 |
| SC-004 | — | SC-001·SC-002 결과 위에서 수행 |
