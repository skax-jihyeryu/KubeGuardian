# 3. 시나리오 수립

> 작성일: 2026-10-04 · 개정: 2026-10-12 (피드백 반영) · 상세: [기획서](../01-project-proposal.md), [문제 정의 및 서비스 기획](02-문제정의및서비스기획.md)
>
> 이 문서는 **사용자가 KubeGuardian을 쓰는 흐름**을 정리한다. 모든 시나리오는 로그인 → 채팅 **핵심 경로**를 기준으로 한다. 각 시나리오의 예시 상황은 평가용 장애 시나리오(문서 끝 "평가 시나리오 연결")에서 가져왔다.

**읽기 전에: 출력 예시의 표기**

| 표기 | 뜻 |
|---|---|
| `[근거 12]` | 도구가 수집한 데이터 한 건의 번호. 원문(마스킹 후), 수집 시각, 출처는 보고서 화면의 근거 보기에서 볼 수 있다 |
| 확신도 | 에이전트가 판정에 붙이는 높음 / 중간 / 낮음 |
| 가설 판정 | 지지(근거가 뒷받침) / 배제(근거가 반박) / 판단 보류(근거 부족) |
| 심각도 | 🔴 긴급(핵심 경로 장애) / 🟠 주의(일부 사용자·기능 실패) / 참고(🟡 잠재 위험, ⚪ 개선 권고. 알림 없이 화면에만 표시) |

**사용 방식 한눈에 보기**

| 시나리오 | 시작 방식 | 결과를 받는 곳 |
|---|---|---|
| SC-001 주기 점검과 이상 알림 (주 시나리오) | 자동 — 5분마다 | Slack 알림(요약 + 링크) → 보고서 화면 |
| SC-002 배포 직후 점검 | 수동 — Slack 명령 `/kg check` | Slack (명령을 입력한 곳의 스레드에 요약 + 링크) → 보고서 화면 |
| SC-003 증상 입력으로 원인 조사 | 수동 — Slack 명령 `/kg investigate 증상` | Slack (명령을 입력한 곳의 스레드에 요약 + 링크) → 보고서 화면 |

알림과 명령은 Slack에서, 전체 보고서와 근거 원문, 점검 이력은 **보고서 화면**(읽기 전용)에서 확인한다. 같은 기능을 CLI(`kg check`, `kg investigate`)로도 실행할 수 있지만 개발·디버깅용이다.

## 핵심 사용자 시나리오

### 시나리오 1 : 주기 점검으로 이상을 감지하고 Slack으로 알림 받기

- **ID** : SC-001
- **상황** : 평일 오후, 운영자는 다른 업무 중이다. 그 사이 llm-gateway의 LLM 사용 할당량이 소진되어 보도자료 초안 생성이 실패하기 시작했다. Pod는 모두 Running·Ready로 정상이라 Kubernetes 대시보드에는 아무 표시가 없고, PR 담당자는 아직 문의하지 않았다. 지금 방식이라면 사용자 문의로 장애를 알고 원인 파악까지 약 3~5일(추정)이 걸린다.
- **목표** : 사용자가 문의하기 전에, 원인과 조치 방법이 담긴 알림을 운영자가 먼저 받는다.
- **사전 조건** :
  - KubeGuardian이 진단 대상 네임스페이스(`dev`)에 조회 전용 권한으로 설치되어 있음
  - 주기 점검이 5분 간격으로 등록되어 있음 (Kubernetes CronJob)
  - 설정 파일에 증상 감지용 API 호출 순서(로그인 → 채팅), 조회를 허용할 앱 API(llm-gateway 상태·할당량)가 등록되어 있음
  - KubeGuardian Slack 앱(봇 토큰, Socket Mode용 앱 토큰)이 Secret으로 등록되어 있고, 알림 대상(기존 운영 채널 또는 DM)에 연결되어 있음
  - 보고서 화면에 접근할 수 있음
  - Azure OpenAI 연결 정상
- **상세 흐름**

| 단계 | 구분 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|---|
| 1 | 감지 | — | 5분 주기 점검 실행: 규칙 점검은 모두 통과, 로그인 → 채팅 API 호출에서 **채팅 단계 실패** | 정상이면 기록만 남기고 끝 |
| 2 | 판정 | — | 규칙은 통과했지만 증상이 있고, 로그인·채팅이 실패하므로 **심각도 🔴 긴급**. 이미 알린 문제가 아니므로 **AI 조사 시작** | 같은 문제면 AI 생략 |
| 3 | 조사 | — | **가설 없이 확인할 것을 먼저 확인**: Pod 상태(3개 모두 Ready), Service의 Endpoint 연결(정상), 채팅 API 재호출(502 재현) | 확정 사실로 저장 |
| 4 | 조사 | — | 확인된 사실을 바탕으로 원인 가설 3개를 세움: ① agent 자체 오류 ② llm-gateway 이상 ③ DB·Redis 연결 문제 | |
| 5 | 조사 | — | 서비스 호출 관계를 따라 거슬러 올라가며 도구로 확인: agent 로그 → agent Pod 3개 직접 호출 → llm-gateway 할당량. 결과는 모두 근거로 저장 | 조사 1건당 도구 호출 20회·150초 이내 |
| 6 | 조사 | — | 가설 판정(② 지지, ①·③ 배제) 후 보고서 작성. **검증 코드가 모든 사실 문장의 근거를 확인**하고 보고서를 화면에 저장 | 근거 없는 문장은 "추정"으로 표시 |
| 7 | 알림 | Slack 알림 수신 | **심각도, 한 줄 요약, 보고서 화면 링크**를 Slack으로 발송 | 장애 발생 후 7분 이내 |
| 8 | 인지·확인 | 알림을 보고 보고서 화면을 열어 원인·근거 확인 | 화면에서 보고서와 근거 원문 열람 | |
| 9 | 조치 | 보고서대로 할당량 상향 | 조치는 사람이 실행 (자동 실행 없음) | |
| 10 | 재알림 | (미해결 시) 리마인더 수신 | 같은 문제는 AI를 다시 호출하지 않고, 긴급은 30분 후 첫 리마인더, 이후 2시간마다 총 3회까지 | 알림 피로 방지 |
| 11 | 복구 | 복구 알림 수신 | 다음 주기 점검에서 채팅 API 호출 성공 → **복구 알림 1회 발송**, 리마인더 중단 | |

- **입력 예시** (자동 실행이라 사용자 입력은 없음. 등록하는 설정 예시)

```yaml
# kubeguardian.yaml (일부)
schedule: "*/5 * * * *"          # 5분마다
target:
  namespace: dev
api_scenarios:
  - name: chat
    steps: [login, chat]
notify:
  slack:
    target: "#pr-service-ops"    # 기존 운영 채널 또는 DM. 알림량이 늘면 전용 채널로 분리
    bot_token_secret: kg-slack-bot
  reminders:                     # 심각도별 재알림
    critical: {first_after: 30m, then_every: 2h, max: 3}   # max는 리마인더 총 횟수
    warning:  {first_after: 2h, max: 1}
```

- **기대 출력**

Slack 알림 본문:

```text
🔴 긴급 [KubeGuardian] dev — 채팅이 실패하고 있습니다 (확신도 높음)
원인: llm-gateway LLM 할당량 소진 (오늘 사용량 100%)

조치: llm-gateway 관리 화면에서 할당량 상향 또는 초기화
감지: 14:05 점검 · 수집된 신호 47개 중 중요 문제 1건
보고서: <보고서 화면 링크>
```

보고서 화면에 올라오는 전체 보고서:

```text

■ 결론
  front-chat → gateway → agent → llm-gateway 경로에서 llm-gateway가 429(요청 한도 초과)를
  반환해 gateway가 502로 응답하고 있습니다.

■ 근거
  사전 확인 (가설 없이 확인한 사실)
  - 채팅 API 호출: 로그인 성공, 채팅 요청 502 [근거 12]
  - dev 네임스페이스 Pod 전체 Running·Ready, 재시작 없음, Service Endpoint 정상 [근거 3]
  가설 검증
  - agent 로그: "llm-gateway returned 429 Too Many Requests" [근거 14]

■ 가설 판정
  ① agent 자체 오류      — 배제: agent Pod 3개 모두 상태 확인 200, 오류는 하위 호출의 429뿐 [근거 13]
  ② llm-gateway 할당량   — 지지 [근거 14, 15]
  ③ DB·Redis 연결 문제   — 배제: 로그인(DB·Redis 사용) 성공 [근거 12]

■ 확인한 범위
  - 확인함: 채팅 호출 경로의 서비스 4개(front-chat, gateway, agent, llm-gateway) 상태·로그,
    agent Pod 3개 각각 직접 호출, llm-gateway 할당량
  - 확인하지 못함: Azure OpenAI 쪽 할당량 (외부 서비스라 조회 권한 없음)

■ 권장 조치 (자동 실행하지 않음)
  1. llm-gateway 관리 화면 → 할당량 설정에서 한도 상향 또는 일일 사용량 초기화
  2. 반복된다면 사용량이 급증한 사용자·기능을 llm-gateway 감사 로그에서 확인

■ 재검증 방법
  다음 주기 점검(5분 이내)에서 자동 확인. 바로 확인하려면 Slack에서 /kg check 입력
```

재알림 (30분 경과, 미해결):

```

```

- **대안 흐름**
  - **일부 수집 실패**: Kubernetes API나 앱 API 호출이 일부 실패하면 해당 항목을 보고서의 "확인하지 못함"에 적고 나머지로 조사를 진행한다.
  - **AI 조사 실패·상한 초과**: 규칙·증상 결과만으로 알림하고 보고서에 "조사 미완"을 표시한다.
  - **점검기 자체가 멈춤**: "점검 중단" 알림을 별도로 보낸다.
- **성공 기준**
  - 기준 1: 장애 발생부터 알림 발송까지 7분 이내 (KPI "장애 감지 시간", 현재 방식 약 3~5일 대비 전/후)
  - 기준 2: 보고서 1순위 원인이 정답(llm-gateway 할당량 소진)과 일치 (KPI "원인 규명 커버리지" 대상 시나리오, 사람 기준 판정)
  - 기준 3: 보고서에 붙은 근거가 실제로 각 문장의 내용을 뒷받침함 (KPI "근거 일치율", 본인 검토 후 AI 기준과 일치도 확인)
  - 기준 4: 보고서만 보고 추가 확인 없이 조치할 수 있음 (배제한 가설의 이유, 확인한 범위, 구체적인 조치 포함)
  - 기준 5: 같은 내용의 알림이 반복되지 않고, 정해진 간격의 리마인더(30분 후, 이후 2시간마다 총 3회)만 발송되며, 해결 후 복구 알림이 1회 발송됨

### 시나리오 2 : 배포 직후 점검으로 "지금 중요한 것" 요약 받기

- **ID** : SC-002
- **상황** : agent의 Kubernetes 배포 설정을 수정해 배포한 직후, 다음 주기 점검(최대 5분)을 기다리지 않고 바로 확인하려고 점검을 실행한다. 채팅이 전부 실패하는데, 화면에는 경고·이벤트·과거 재시작 기록이 수십 개 섞여 있다.
  - 실제 원인: agent Service(내부 주소)의 대상 Pod 라벨 조건에 오타가 생겨, Service의 Endpoint가 비고 요청을 받을 Pod가 0개가 됨.
- **목표** : 수십 개 신호 중 **지금 장애의 원인이 되는 것만** 골라 영향 순으로 보고, 나머지는 개선 권고로 분리해서 본다.
- **사전 조건** :
  - KubeGuardian 설치, 대상 서비스 배포 완료
  - KubeGuardian 전용 계정에 조회 권한(get/list/watch)
  - KubeGuardian Slack 앱이 명령을 입력할 채널에 연결되어 있음
- **상세 흐름**

| 단계 | 구분 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|---|
| 1 | 감지 | Slack에서 `/kg check` 입력 | "점검을 시작합니다" 메시지를 올리고, 리소스 수집 → 서비스 호출 관계 구성 (각 앱 설정의 서비스 주소를 실제 Service와 대조) | 주기 점검과 같은 점검을 즉시 실행 |
| 2 | 판정 | — | 규칙 점검: **"agent Service의 Endpoint가 비어 있음(연결된 Pod 0개)"** 을 장애로 확정. 그 밖에 "준비 상태 확인이 포트 연결만 봄" 같은 항목은 개선 권고(참고)로 분류 | 코드로 판정 |
| 3 | 감지 | — | 증상 감지: 로그인 → 채팅 API 호출에서 채팅 실패 | |
| 4 | 조사 | — | 규칙이 장애를 찾았으므로 **AI 조사 시작**. 원시 신호 47개를 서비스별로 묶어 에이전트에 전달하고, 가설 없이 확인할 사실(Service selector ↔ Pod 라벨, Endpoint 개수)을 먼저 확인 | 장애도 증상도 없으면 AI를 호출하지 않음 |
| 5 | 조사 | — | AI가 사용자 영향 순으로 **중요 문제 최대 3건**을 고르고, 무관한 신호는 개선 권고로 분리. 상위 문제는 도구로 추가 확인 후 원인·영향·근거 작성 | 문제 1건당 도구 호출 8회 이내 |
| 6 | 알림 | 요약 확인 | 요약과 **보고서 화면 링크**를 "점검을 시작합니다" 메시지의 스레드에 답글로 올림 | 수동 실행 결과는 심각도와 관계없이 요청자에게 항상 표시 |
| 7 | 인지·확인 | 보고서 화면 열람 | 시나리오 1과 같은 형식의 전체 보고서와 근거 원문을 화면에서 확인 | |

- **입력 예시**

```text
/kg check
```

- **기대 출력**

```text
규칙 점검: 장애 1건, 개선 권고 3건 / 증상 감지: 채팅 API 실패
→ 규칙이 장애를 찾아 AI 조사를 시작합니다.

지금 중요한 것 1건 (수집된 신호 47개 중)
 1. 🔴 긴급 — 채팅이 전부 실패합니다 (확신도 높음)
    agent Service의 대상 Pod 조건이 app=agnet으로 되어 있어 Endpoint가 비어 있습니다(연결된 Pod 0개) [근거 4].
    agent Pod 3개의 라벨은 app=agent입니다 [근거 5].
    방금 배포에서 이 값이 바뀌었습니다 [근거 6].
    조치: Service의 대상 Pod 조건을 app=agent로 수정

참고 — 개선 권고 (지금 장애와 무관)
 - 준비 상태 확인이 포트 연결만 봄 (6개 서비스)
 - CPU·메모리 요청·제한값 미설정 (2개 서비스)
 - agent Pod 1개의 어제 재시작 기록 1건: 이후 정상 동작 중

전체 보고서: <보고서 화면 링크>
```

(위 내용은 `/kg check`가 올린 "점검을 시작합니다" 메시지의 스레드 답글로 올라온다.)

- **대안 흐름 — 정상일 때**: 규칙 장애도 증상도 없으면 AI를 호출하지 않고 "규칙 점검 통과, 증상 없음 + 개선 권고 3건"만 표시한다. 점검 결과는 화면의 점검 이력에서도 볼 수 있다.
- **대안 흐름 — 수집 실패**: 일부 수집이 실패하면 해당 항목을 "확인하지 못함"으로 표시하고 나머지 결과를 보여준다.
- **성공 기준**
  - 기준 1: 요약 1순위가 실제 원인(Service 대상 Pod 조건 오타)과 일치 (KPI "원인 정확도", 사람 기준 판정)
  - 기준 2: 확인 항목 감소율 90% 이상 (확인할 항목 47개 → 중요 문제 1건)
  - 기준 3: 정상일 때는 개선 권고만 표시되고 AI를 호출하지 않음

### 시나리오 3 : 자동 점검이 못 잡는 증상을 직접 입력해 조사 받기

- **ID** : SC-003
- **상황** : PR 담당자에게서 Slack으로 "초안 생성이 세 번에 한 번꼴로 실패해요"라는 문의를 받았다. 주기 점검은 5분마다 채팅 API를 한 번만 호출하는데, 그 호출이 마침 정상 Pod로 가면 통과해 버려서 알림이 오지 않았다.
  - 실제 원인: agent Pod 3개 중 1개만 오류를 냄. Service는 요청을 3개 Pod에 나눠 보내므로 요청의 약 1/3만 실패한다.
- **목표** : 문의를 받은 Slack에서 바로 증상을 맡기고, 원인 조사 보고서를 받는다.
- **사전 조건** : 시나리오 1과 같음
- **상세 흐름**

| 단계 | 구분 | 사용자 행동 | 시스템 동작 | 비고 |
|---|---|---|---|---|
| 1 | 감지 | Slack에서 `/kg investigate <증상>` 입력 | 사용자가 증상을 입력했으므로 규칙 결과와 관계없이 **AI 조사를 바로 시작**. 입력한 증상을 담은 "조사를 시작합니다" 메시지를 올림 | 허용된 채널·사용자만 실행 가능 |
| 2 | 조사 | 진행 상황 확인 | **조사 계획을 먼저 스레드에 올림**: 먼저 확인할 사실(채팅 API 반복 호출 결과, agent Pod 상태·Endpoint)을 확인하고, 그 결과로 가설을 세운다 | |
| 3 | 조사 | — | **사전 확인(가설 없이)**: 채팅 API 10회 반복 호출(3회 실패), agent Pod 3개 모두 Ready, Endpoint 3개 정상 | 확정 사실로 저장 |
| 4 | 조사 | — | 확인된 사실(Pod는 모두 정상인데 일부 요청만 실패)로 가설을 세움: ① 특정 Pod만 오류 ② 간헐적인 하위 서비스 응답 지연 ③ LLM 응답 간헐 실패 | |
| 5 | 조사 | — | 도구로 확인: agent Pod 3개 각각 직접 호출 → 실패한 Pod의 로그 조회. 가설 판정(① 지지, ②·③ 배제) 후 보고서 작성, 근거 검증 | |
| 6 | 알림·확인 | 요약 확인, 보고서 화면 열람 | 요약과 **보고서 화면 링크**를 같은 스레드에 올림 | |

- **입력 예시**

```text
/kg investigate 초안 생성이 세 번에 한 번꼴로 실패한다는 문의가 들어왔어요
```

- **기대 출력**

채널 메시지와 첫 스레드 답글:

```text
🔍 [KubeGuardian] 조사를 시작합니다 — 요청: @운영자
증상: "초안 생성이 세 번에 한 번꼴로 실패한다는 문의가 들어왔어요"

  └ (스레드) 조사 계획: ① 먼저 확인할 사실 — 채팅 API 반복 호출 결과, agent Pod 상태·Endpoint 연결.
            ② 확인된 사실을 바탕으로 원인 가설을 세워 Pod별 직접 호출과 로그로 검증합니다.
```

이어서 스레드에 올라오는 요약:

```text
🟠 주의 — 채팅 간헐 실패: agent Pod 1개(agent-p9m)만 오류 (확신도 높음)
전체 보고서: <보고서 화면 링크>
```

보고서 화면의 전체 보고서:

```text
[조사 보고서] 채팅 간헐 실패 — agent Pod 1개(agent-p9m)만 오류          확신도: 높음

■ 결론
  agent Pod 3개 중 agent-p9m만 채팅 요청에 500을 반환합니다. Service가 요청을 3개 Pod에
  나눠 보내므로 전체 요청의 약 1/3이 실패합니다.

■ 근거
  사전 확인 (가설 없이 확인한 사실)
  - 채팅 API 10회 호출 중 3회 실패 [근거 21]
  - agent Pod 3개 모두 Ready, Endpoint 3개 정상 [근거 20]
  가설 검증
  - Pod 직접 호출: agent-x2k 200, agent-q4t 200, agent-p9m 500 [근거 22, 23, 24]
  - agent-p9m 로그: 요청 처리 중 오류 반복 [근거 25]

■ 가설 판정
  ① 특정 Pod만 오류          — 지지 [근거 22~25]
  ② 하위 서비스 응답 지연     — 배제: 성공한 요청의 응답 시간 정상 [근거 21]
  ③ LLM 응답 간헐 실패        — 배제: 정상 Pod 2개는 매번 성공 [근거 22, 23]

■ 확인한 범위
  - 확인함: 채팅 API 반복 호출, agent Pod 3개 직접 호출, agent-p9m 로그
  - 확인하지 못함: agent-p9m이 오류를 내기 시작한 정확한 시각 (로그 보관 범위 밖)

■ 권장 조치 (자동 실행하지 않음)
  1. agent-p9m 재시작: kubectl delete pod agent-p9m -n dev (Deployment가 새 Pod를 띄움)
  2. 재발하면 agent-p9m이 떠 있던 노드와 다른 Pod의 차이를 비교

■ 재검증 방법
  /kg investigate로 같은 증상 재조사, 또는 /kg check로 채팅 API 호출 성공 확인
```

- **대안 흐름**: 조사가 도구 호출·시간 상한에 도달하면 확인한 사실까지만 담아 "조사 미완"으로 표시하고, 확인하지 못한 가설을 "확인하지 못함"에 적는다.
- **성공 기준**
  - 기준 1: 보고서 1순위 원인이 정답(agent Pod 1개만 오류)과 일치 (KPI "원인 정확도", 사람 기준 판정)
  - 기준 2: 보고서에 붙은 근거가 실제로 각 문장의 내용을 뒷받침함 (KPI "근거 일치율")
  - 기준 3: 증상 입력부터 보고서 완성까지 120초 이내 (중앙값)
  - 기준 4: 조사 계획이 보고서보다 먼저 스레드에 올라와, 조사가 진행 중임을 알 수 있음
