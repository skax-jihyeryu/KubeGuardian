# 5. 핵심 구현 및 동작 검증

**한 줄 정의:** KubeGuardian은 Kubernetes 위에서 동작하는 AI 서비스를 5분마다 점검하고, 문제가 있으면 AI 에이전트가 조회 전용 도구로 원인을 조사해 근거가 붙은 보고서와 Slack 알림으로 알려주는 진단 에이전트다.

* **입력(In):** 5분 주기 점검, `/kg check`, `/kg investigate 증상`
* **출력(Out):** Slack 알림(1차 감지, 원인 갱신), 조사 보고서(화면, Markdown 파일), 처리 이력

2026-10-19(W2 시작) 기준이다. 점검과 판정, 도구, 에이전트 기반, 평가 러너는 코드로 구현해 확인했다. LangGraph 조사 흐름과 지식 기반(RAG)은 W2에 구현하며, 아래에 "W2 구현 중"으로 표시했다.

### 핵심 구현 내용

이번 PoC 단계에서 실제 코드로 구현된 핵심 기능들을 **동작 원리**와 **사용 기술** 중심으로 상세히 기술합니다.

**1.1 에이전트 워크플로우 (Agent Workflow)**

* **구현 기능:** 점검과 AI 호출 여부 판정 (게이트). 문제 상황일 때만 AI 조사를 시작한다

* **동작 원리:** Kubernetes 상태를 수집해 규칙 13종(장애 신호 11종, 개선 권고 2종)으로 점검한다. 장애 신호가 하나라도 적발되면 경로 A(AI 조사 시작), 개선 권고만 있거나 모두 통과면 경로 C(AI 호출 없음)로 판정한다. 점검 결과와 판정에 쓴 값은 근거로 저장한다. 규칙 통과 후 실제 호출 실패로 여는 경로 B와, 경로 A나 B에서 이어지는 LangGraph 조사 흐름(사전 확인, 선별, 계획, 도구 반복, 판정, 보고서, 근거 검증)은 W2 구현 중이다

* **주요 기술:** Python 결정적 함수(규칙마다 `@detector` 등록), Kubernetes Python 클라이언트(조회 전용), SQLAlchemy와 SQLite, 에이전트 공통 기반(`BaseAgent`, `AgentSpec`, 레지스트리), LangGraph(W2)

**1.2 도구(Tool) 및 함수 연동**

* **구현 기능:** 조회 전용 진단 도구 7종 (`get_topology`, `get_resource`, `get_pod_logs`, `get_events`, `probe`, `run_api_scenario`, `query_app_api`)과 LLM 연결 함수

* **동작 원리:** 모든 도구가 같은 순서를 거친다: 입력 검증(모르는 인자 거부), 호출 상한 확인, 수집, 대상 네임스페이스 확인, 마스킹, 근거 저장, 요약 반환. 네임스페이스는 입력으로 받지 않고 코드가 고정한다. HTTP 도구는 대상 네임스페이스의 Service와 Pod만, 허용한 경로만 부른다. 호출이 실패해도 실패를 근거로 저장한다. LLM은 `build_chat_model(모델 이름)` 한 곳에서 만들고, 연결 정보(제공사, 주소, 키)는 설정으로만 받아 코드 수정 없이 바꿀 수 있다

* **주요 기술:** Pydantic(도구 입력 스키마), httpx(네임스페이스에 묶인 HTTP 클라이언트), Kubernetes Python 클라이언트, LangChain `AzureChatOpenAI`, Azure OpenAI `gpt-6.1-sol`(Responses API)

**1.3 데이터 및 메모리 (RAG & Context)**

* **구현 기능:** 근거 저장소와 점검 이력, 환경 설명과 조사 지침 템플릿. 공통 지식 기반(RAG)은 W2 구현 중

* **동작 원리:** 점검마다 수집 결과(스냅샷), 규칙 판정, 근거를 SQLite에 저장하고 근거마다 번호(ev-0001)를 붙인다. 보고서의 사실 문장은 이 번호로만 인용한다. 직전 점검 스냅샷과 관측 기록으로 "15분 이상 지속" 같은 시간 조건을 판정한다. 지식 기반은 운영 매뉴얼(증상별 조사 지침 6개)과 처리 이력(복구가 확인된 문제)을 임베딩해 Chroma에 넣고, 조사 중 `search_knowledge` 도구로 상위 3개를 찾는 구조로 구현한다

* **주요 기술:** SQLite(WAL 모드), SQLAlchemy, Markdown 지식 문서, Chroma와 Azure OpenAI `text-embedding-3-small`(W2)

### 주요 문제 해결 및 기술 리서치

구현 과정에서 마주친 기술적 문제와 이를 해결하기 위해 **찾아본 자료(리서치)** 및 **적용한 방법**을 기록합니다.

|           |                                      |                                                                                           |
| --------- | ------------------------------------ | ----------------------------------------------------------------------------------------- |
| **이슈 구분** | **문제 상황 및 원인**                       | **리서치 및 해결 과정 (Reference & Solution)**                                                    |
| **LLM 연동** | 진단 모델 `gpt-6.1-sol`이 temperature 0을 거부하고, 도구 호출이 기존 Chat Completions API에서 동작하지 않음 | **리서치:** Azure OpenAI 모델별 API 지원 범위 확인 (도구 호출은 Responses API, API 버전 `2025-03-01-preview` 이상) **적용:** 모델별 제약을 `MODEL_OPTIONS` 표 한 곳에 모으고, 해당 모델이면 temperature를 보내지 않고 Responses API를 쓰게 함. 결정성은 평가에서 3회 반복과 다수결로 확인 |
| **환경** | 사내 프록시가 TLS를 가로채 Pod 안에서 Azure OpenAI 호출과 이미지 받기가 인증서 오류로 실패 | **리서치:** minikube 사내 인증서 등록 방법, `SSL_CERT_FILE`이 기본 인증서 저장소를 대체한다는 점 확인 **적용:** 노드는 `--embed-certs`로 사내 CA 등록. Pod는 공개 CA와 사내 CA를 합친 번들을 만들어 `SSL_CERT_FILE`로 지정해 호출 성공 |
| **진단 정확도** | 템플릿의 readinessProbe가 포트만 보는 방식이라, 하위 서비스 주소가 틀려 모든 요청이 실패해도 Pod는 Ready로 보임 | **리서치:** Kubernetes probe 종류(tcpSocket, httpGet) 동작 확인, gateway 코드의 서비스 주소 기본값(`localhost`) 확인 **적용:** 서비스 주소가 `localhost`나 없는 Service를 가리키는지 보는 선언 규칙(S04)과, 로그인 후 채팅을 실제로 부르는 API 시나리오(증상 감지)를 함께 둠 |
| **보안** | Kubernetes 목록 API가 Secret 값을 함께 돌려주고, 처음 만든 ClusterRole은 모든 네임스페이스의 Secret을 읽을 수 있었음 | **리서치:** Kubernetes Secret과 RBAC 문서 확인 **적용:** 수집 직후 정규화 단계에서 Secret 값을 버리고 키 이름만 남김(단위 테스트로 고정). 권한은 `dev` Role로 좁히고 클러스터 범위는 Node 조회만 남김. `kubectl auth can-i`로 쓰기 권한 없음 확인 |
| **도구 안전** | `probe`가 Pod의 아무 경로나 부를 수 있으면 업무 API를 반복 호출해 앱 상태를 바꿀 수 있음 | **리서치:** 템플릿 앱의 상태 확인 경로와 readinessProbe 설정 확인 **적용:** `/health` 계열과 대상 Pod의 readinessProbe 경로만 허용하고, 그 밖의 경로는 호출 없이 실패로 돌려줌 |
| **평가 신뢰성** | 수집이 실패하면 규칙이 "확인하지 못함"이 되어 게이트가 경로 C(정상)로 가고, 장애가 없는 것처럼 채점됨 | **리서치:** 평가 러너의 단계별 실패 경우 정리 **적용:** 주입 전 정상 기준선 확인, 증상이 실제로 나는지 확인, 수집 실패와 예외는 모두 "무효"로 처리해 통과나 실패로 세지 않음 |

### 핵심 동작 검증

위에서 구현한 기능이 의도대로 동작하는지 보여주는 **대표적인 실행 결과**를 첨부합니다.

**[검증 시나리오: `A5. gateway의 서비스 주소가 localhost를 가리켜 모든 API가 실패`]**

* **입력:** `make eval S=A5` (평가 러너가 장애를 주입하고 점검을 한 번 실행)

* **에이전트 동작:**

  1. 정상 기준선 확인: 로그인 후 채팅 성공 (H0 스모크)

  2. 장애 주입: gateway의 하위 서비스 주소 환경변수 4개를 `localhost`로 바꿈

  3. 증상 확인: front-chat을 거친 로그인이 500으로 실패. gateway Pod는 Ready로 남음

  4. 점검: Kubernetes 상태 수집, 규칙 S04(서비스 주소 설정 오류)가 gateway를 긴급으로 적발, 판정에 쓴 값을 근거로 저장

  5. 판정: 장애 신호 적발이므로 경로 A (AI 조사 대상)

  6. 채점과 원복: 기대 신호(S04)와 기대 경로(A)가 모두 맞아 통과. 원복 후 로그인 후 채팅이 다시 성공

* **최종 결과:**

[2026-10-19 실행 결과: 통과. Pod는 모두 Ready였지만 S04가 gateway의 서비스 주소 오류를 긴급으로 적발했고, 게이트가 경로 A로 열렸다. 같은 날 H0(정상)은 개선 권고만 나오고 경로 C로 AI를 부르지 않아 통과했다. AI 조사 보고서(원인 1순위, 근거, 조치)까지 이어지는 검증은 W2 LangGraph 구현 후 이 시나리오로 추가한다.]
