| **이슈 구분**   | **문제 상황 및 원인**                         | **리서치 및 해결 과정 (Reference & Solution)**                                                                                 |
| ----------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **품질/탐색 실패** | 기준선(w4-final, 11/02)에서 B1(agent Pod 3개 중 1개만 500)이 3회 모두 실패했다. Pod 3개가 모두 Ready이고 재시작과 이벤트가 없으며, Service를 거친 호출은 건강한 Pod에 닿으면 성공한다. 에이전트가 Pod마다 직접 호출해 보지 않아 어느 Pod가 500을 내는지 찾지 못했다. | 리서치: B1을 주입한 상태에서 Pod별 호출을 직접 실행해, 장애 Pod만 500을 내고 이 근거를 도구로 얻을 수 있음을 확인했다. 적용: 간헐 실패 조사 지침에 "성공 로그만으로 외부 실패를 배제하지 않는다"를 추가하고, 지침이 간헐 실패인데 Pod별 호출 성공이 없으면 빈틈으로 보고 재조사하는 코드 검사를 더했다. 결과: 0/3에서 3/3으로 올랐다(w4-hardening-m3와 w4-hardening-m4, 11/02~11/03). w4-hardening-m4에서는 3회 모두 Pod별 호출을 했고 3회 모두 주입된 Pod를 특정했으며 조사 시간이 w4-hardening-m3의 163초에서 104초로 줄었다. 이후 w4-retest(11/03)에서는 2/3로 한 회가 보고 문장 불일치로 떨어졌다. 표본이 작아 일반 성능 향상으로 단정하지 않는다. |
| **품질/오확정** | 판단 수준이 무엇을 조회했는지만 봐서, 지지된 가설이 없고 결론에 "확정 보류"라고 쓴 보고서도 확정으로 나갔다. 운영자가 틀린 답을 확정으로 받을 위험이다. | 리서치: 모델이 매기는 확신도는 기준이 없고 정답률을 잰 적이 없으며 temperature가 고정이라, 10월 31일에 화면과 알림에서 빼고 코드가 저장된 근거로 확정, 후보, 추정을 정하게 했다. 적용: 확정 조건에 "지지된 가설 하나가 인용한 근거 출처가 2종 이상"을 추가했다. 결과: 보조 확인으로 저장된 보고서 8건을 에이전트 재실행 없이 다시 판정하자 오확정이 5건에서 1건으로 줄었다. 시나리오와 시점이 섞인 표본이다. 확정으로 나간 보고서 중 틀린 비율(오확정률)은 규칙 변경 전인 w4-final(11/02)이 27%(확정 15건 중 4건), 같은 구성으로 다시 잰 w4-retest(11/03)가 21%(14건 중 3건, 모두 C2)다. 0은 아니다. 8건 재판정은 에이전트를 다시 돌리지 않은 보조 확인이다. 무관한 가설이 지지로 판정되어도 통과하는 한계가 남았고 이슈 #181로 열려 있다. |
| **품질/추론 실패** | C1(LLM 호출이 429로 거부)에서 호출 대상인 llm-gateway 대신 호출자 agent를 원인으로 지목하는 오류가 반복되었다. 기준선 2/3이던 C1이 보강 측정에서 0/3이 되었다. 장애 주입 도구(Chaos Mesh의 HTTPChaos)가 앱 밖에서 응답을 바꾸기 때문에 429는 agent 로그에만 있고 llm-gateway 로그에는 성공 기록만 있다. 에이전트가 이 모순을 구분하지 못했다. | 리서치: 같은 장애 상태에서 두 버전을 3회씩 돌려 분리 비교했다(w4-c1-tools-vs-recheck, 11/03). 도구 보강만 1/3, 재조사 포함 0/3이었다. 결론 채점은 6회 중 5회가 일치였지만 원인 위치 일치는 1회뿐이었다. 적용: 보고서에 호출 체인을 추가했다. 증상이 보인 호출자에서 오류 출처 쪽으로 거슬러 올라가며 지점마다 리소스와 근거를 적게 하고, 체인의 끝이 원인 리소스와 다르거나 근거가 없거나 하위 오류를 전달하면 코드가 재조사시키고 판단을 후보로 제한한다. 결과: 적용 직후(w4-cause-chain-146, 11/03) C1은 1/3이었고 세 보고서 모두 후보였다. 이후 w4-retest(11/03) 0/3, w5-c1-recheck(11/09) 2/3로 흔들렸다. 호출 체인은 미해결을 후보로 정직하게 남기는 장치이고 원인 위치 정확도를 높였다고는 입증하지 못했다. |
| **보안/가드레일** | 비밀값 마스킹에 남은 구멍이 있었다. 인증 헤더와 쿠키 값이 가려지지 않았고, 로그가 잘려 BEGIN, END 줄 없이 개인 키 본문만 남으면 가려지지 않았다. Slack 알림, 알림 이력, CLI 출력에 보고서 문자열이 마스킹 없이 들어갈 수 있다는 지적도 있었다. | 리서치: 헤더 이름과 base64 줄의 형태를 기준으로 가릴 수 있는 범위와 오탐 위험을 따졌다. 적용(11/09): 인증 헤더와 쿠키는 헤더 이름이 전체 일치할 때 값을 가리고 cookie_name 같은 이름은 유지했다. 64자 base64 줄이 2줄 이상 이어지면 개인 키 본문으로 보고 가렸고, 한 줄뿐인 경우와 해시 줄은 구분할 수 없어 가리지 않았다. 알림 경로를 점검해 마스킹이 없던 CLI 출력만 고쳤고, 비밀값이 든 보고서가 알림, 알림 이력, CLI 출력에 남지 않는지 테스트로 고정했다. 결과: 단위 테스트가 1,833개에서 1,857개로 늘었고 긴 줄에서도 선형 시간으로 동작한다. 줄 앞에 타임스탬프가 붙은 개인 키 등은 가리지 못하는 한계를 코드 설명에 적었다. |
| **평가 신뢰성/정답 유출** | C2 보고서에 "PodNetworkChaos 갱신 이벤트도 확인했습니다"가 나왔다. 장애 주입 도구인 Chaos Mesh가 대상 네임스페이스에 남기는 이벤트를 에이전트가 읽어, 주입 사실이 정답 힌트가 되었다. | 리서치: 주입 도구가 남기는 부수 객체와 이벤트를 확인했다. 적용: 설정에서 chaos-mesh.org 그룹의 이벤트를 수집 단계에서 제외하게 했다. 점검 기록과 도구가 같은 클라이언트를 쓰므로 한 곳에서 걸러진다. 운영 클러스터에는 주입 도구가 없어 기본값은 비워 두었다. 결과: 11/01 C2, C1, B1 조사 기록과 점검 DB 전체에서 chaos 검색 결과가 0건이었다. 이후 모든 AI 평가의 유효성이 이 필터에 기대고 있다. |

## 1. LLM 답변 품질 평가 및 개선

| 항목       | 내용                                                                  |

| 평가 대상 기능 | 조사 에이전트가 보고서 1순위 원인을 정답 원인과 일치시키는지, 인용한 근거가 문장을 뒷받침하는지 |
| 평가 방식    | 장애 시나리오 6개와 정상 기준선 2개를 실제 minikube 클러스터에 주입하고 정답 파일과 비교했다. A1은 Service selector 오타, A3은 받을 수 없는 이미지, A5는 gateway의 하위 서비스 주소를 localhost로 바꾼 것, B1은 agent Pod 3개 중 1개만 500, C1은 LLM 호출이 429로 거부, C2는 admin과 Redis 사이 차단, H0는 정상, H1은 설정이 없어도 정상인 서비스다. 장애를 한 번 주입하고 조사를 3회 돌렸다. 채점은 네 가지다. 보고서 1순위 원인 리소스를 정답과 코드로 대조하고, 결론 문장을 조사와 다른 모델(gpt-4.1)이 채점하고, 핵심 근거를 직접 얻었는지 확인하고, 인용 근거가 문장을 뒷받침하는지 주장별로 채점한다. 사람 라벨로 채점 모델을 보정하지는 못했다 |

| 개선 후 결과  | 좋아진 것: B1이 0/3에서 3/3이 되었다(w4-hardening-m3와 w4-hardening-m4, 11/02~11/03). 근거 일치율은 모델 채점 기준으로 모든 배치가 0.93에서 1.00이었고 구성이 달라 추세로 보지 않는다. A1, A3, A5는 실행한 모든 배치에서 통과했다 |
| 나빠지거나 그대로인 것 | 전체 원인 정확도는 w4-hardening-m4 60%, w4-cause-chain-146 75%(8회 중 6회, 축소 회귀), w4-retest 61%로 기준선 61%와 거의 같다. B1이 올랐지만 C1이 내려가 상쇄되었다. C1은 2/3에서 0/3(w4-hardening-m3와 w4-hardening-m4), 1/3(w4-cause-chain-146), 0/3(w4-retest), 2/3(w5-c1-recheck, 11/09)로 배치마다 흔들렸고 위치 식별을 해결했다고 말할 수 없다. C2는 모든 배치에서 0/3이다. 원인 리소스 admin은 맞히지만 Redis 연결 차단은 현재 도구로 확인할 수 없어 도구 한계로 분류된다. 오확정률은 w4-final 27%, w4-retest 21%이고 w4-retest의 오확정 3건은 모두 C2였다 |
| 한계       | 시나리오마다 장애 주입은 1회, 조사는 3회라 표본이 작다. 독립된 장애 주입 반복이 아니고 배치마다 구성이 달라 정확도를 직접 비교하기 어렵다. 모든 시나리오를 같은 날 같은 코드로 다시 잰 배치는 w4-retest(11/03) 이후 없다. 보강 전후 차이를 일반 성능의 개선이나 악화로 단정하지 않는다 |

## 2. 성능 및 비용 최적화

| 항목    | 내용                                       |
| ----- | ---------------------------------------- |
| 기존 병목 | 점검이 정상일 때도 LLM을 부르면 매시간 비용이 든다. 조사 안에서는 도구를 부를 때마다 대화를 압축 없이 쌓아서 입력 토큰이 계속 커진다 |
| 개선 전략 | 정상일 때는 LLM을 부르지 않는다. 규칙 14개와 기능 점검을 결정적 코드로 먼저 판정하고, 규칙 신호도 기능 실패도 증상 입력도 없으면 조사를 시작하지 않는다. 조사가 시작되면 호출 수와 시간 상한을 코드로 강제한다 |
| 적용 기술 | 조사 시작 판단 단계, 문제당 도구 8회와 조사 전체 20회와 150초 상한(재조사 시 60초 한 번 연장), 같은 문제는 지문으로 알아보고 다시 조사하지 않는 이슈 추적 |
| 개선 결과 | 정상 시 조사 호출은 0이다. H0와 H1의 조사 생략 24회 중 24회(w4-final, w4-hardening-m4, w4-cause-chain-146, w4-retest, 11/02~11/03)와, 운영 CronJob의 정각 점검 27회(11/03~11/09)에서 조사가 한 번도 돌지 않았다. 조사 시간과 토큰 중앙값은 기준선 w4-final(11/02)에서 89초, 115,734로 목표(120초, 20만 토큰)를 만족했다 |
| 비용이 늘어난 부분 | 재조사와 도구 보강 뒤 비용이 늘었다. C1은 기준선 95초, 124,089토큰에서 w4-hardening-m3(11/02~11/03) 180초, 입력과 출력 합 약 31만 토큰이 되었고, w5-c1-recheck(11/09)에서도 166초, 277,296토큰이다. A1은 기준선 77초에서 w4-hardening-m4(11/03) 135초로 늘었다. 전체 중앙값은 w4-hardening-m4 135초, 177,167토큰, w4-cause-chain-146 167초, 297,944토큰으로 시간 목표를 넘고 마지막 배치는 토큰 목표도 넘었다. B1은 w4-hardening-m3에서 w4-hardening-m4로 가며 시간이 36% 줄었다. 요금으로 환산하지는 않았다 |
| 남은 과제 | 대화를 압축하지 않고 쌓는 구조가 원인이다. 입력 누적 줄이기는 이슈 #75에 남았다. 모델 조합을 바꿔 비교하는 실험은 하지 않았고 조사 모델은 하나로 고정했다. 근거 AI 요약과 이력 질의는 조사와 별개로 LLM을 쓰며 이 수치에 포함하지 않았다 |

| 항목     | 내용                              |
| ------ | ------------------------------- |
| 차단 대상  | 비밀번호, 토큰, 개인 키, 인증 헤더, 쿠키 같은 비밀값의 노출. 진단 대상 네임스페이스 밖 조회. 로그, 이벤트, API 응답 안에 든 지시문(프롬프트 인젝션). 클러스터 변경 |
| 탐지 방식  | 비밀값은 값의 형식과 이름 패턴으로 찾는다. 네임스페이스는 도구 입력에 필드를 두지 못하게 하고, 대상 네임스페이스에 묶인 클라이언트만 쓰고, 결과의 대상을 다시 확인하는 세 겹이다. 지시문은 도구 결과를 태그로 감싸 데이터로만 전달하고 결과 안의 꺾쇠 기호를 이스케이프해 감싸기를 닫지 못하게 한다 |
| 대응 로직  | 비밀값은 `***`로 바꾼 뒤에 근거 저장, LLM 전달, Slack 알림, 알림 이력, 화면, CLI 출력에 쓴다. 범위를 벗어난 입력과 결과는 거부한다. 시스템 프롬프트가 태그 안의 지시처럼 보이는 문장을 따르지 않게 정한다. 보고서의 근거 번호는 검증기가 걸러 지어낸 인용이 남지 않는다. 도구가 모두 조회 전용이고 Kubernetes 권한도 조회뿐이라 조치는 제안만 하고 실행하지 않는다 |
| 테스트 결과 | 단위 테스트로 확인했다. 마스킹 테스트 함수 41개(긴 줄 2만 줄이 선형 시간에 처리됨을 포함), 닫는 태그가 든 지시문이 도구 결과, 이력 질의, 사전 확인, 재조사 메시지에서 감싸기를 닫지 못함을 각각 검증하는 테스트, 예산과 근거 검증을 확인하는 테스트가 있고, 전체 1,892개가 통과한다(11/09 로컬 실행). 정답 유출 방지 필터는 조사 기록 전체에서 chaos 검색 0건으로 확인했다(11/01) |
| 한계     | 악성 지시문을 로그나 이벤트에 실제로 넣어 에이전트가 읽게 하는 공격 평가는 하지 않았다. 따라서 "몇 건 중 몇 건 방어" 같은 수치는 없다. 마스킹은 패턴 기반이라 줄 앞에 타임스탬프가 붙은 개인 키 등은 가리지 못한다. Kubernetes 권한은 리소스 단위라 진단 대상 네임스페이스의 Secret 값을 읽을 수 있고, 앱이 값을 즉시 버리는 것으로 막는다 |

## 4. 기타 문제 해결 사례

| **이슈 구분** | **문제 상황 및 원인** | **해결 과정과 결과** |
| --- | --- | --- |
| **알림 정확성** | 이슈 지문(같은 문제를 알아보는 값)이 같은 채 1차 심각도가 주의에서 긴급으로 올라가면 "이어지는 이슈"로 처리되어, 알림 갱신과 새 담당자 호출이 나가지 않았다. 담당자 멘션 기능을 만들다 발견했다 | 지문이 같아도 심각도가 오르면 "변경"으로 처리해 알림을 갱신하고 재조사하며 새 담당자를 스레드 답글로 부르게 했다. 심각도가 내려가면 이미 알린 값을 유지하고 다시 알리지 않는다. 단위 테스트로 확인했고 평가는 돌리지 않았다(11/09) |
| **동시 실행** | 주기 점검, 화면의 지금 점검, CLI가 같은 점검을 겹쳐 돌려 같은 이슈를 동시에 열 수 있었다 | SQLite에 점검 잠금을 두어 점검을 동시에 1건만 돌게 했다. 주기 점검은 잠겨 있으면 건너뜀을 기록하고 정상 종료한다 |
| **보고서 가설 수** | 계획은 문제당 가설 최대 3개인데 저장된 보고서 6건의 가설이 5개에서 7개였다 | 저장된 보고서와 단계 기록을 대조해, 상한 위반이 아니라 보고서가 별도 목록으로 세부 원인과 배제한 대안을 다시 만들기 때문임을 확인했다. 3개로 자르면 나중에 확인한 실제 원인과 배제 근거를 버려 판단 수준에 영향을 줄 수 있어, 상한을 코드로 강제하지 않기로 했다. 상한 강제에 따른 정확도 변화는 실험하지 않았다 |
