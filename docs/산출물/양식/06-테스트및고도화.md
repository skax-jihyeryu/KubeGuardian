## 2. 성능 및 비용 최적화

점검 분기는 정상과 규칙 진단 경로에서 조사 LLM을 호출하지 않고, 필요한 경우에만 AI 조사를 시작한다. 경로 B에서는 도구 조회와 재조사에 토큰을 쓰며, 최종 C1은 토큰 목표를 넘었다. 이 비교는 조사 호출과 토큰 사용량을 기준으로 하며 실제 청구액은 집계하지 않았다.

| 기존 병목 | 점검이 정상일 때도 LLM을 부르면 매시간 비용이 든다. 조사 안에서는 도구를 부를 때마다 대화를 압축 없이 쌓아서 입력 토큰이 계속 커진다 |
| 개선 전략 | **점검 단계.** 규칙 14개와 기능 점검으로 조사 필요 여부를 판단한다. 규칙이 장애를 적발하면 규칙 진단으로 종료한다. 규칙 신호·기능 실패·증상 입력이 모두 없을 때도 조사를 생략한다.<br>**조사 단계.** 코드가 도구 호출 수와 조사 시간 상한을 적용한다. |
| 적용 기술 | **호출 예산.** 도구 호출은 문제당 8회, 조사 전체 20회까지다. 조사 시간 상한은 150초이며 재조사 시 한 번 60초 연장한다.<br>**중복 조사 방지.** 이슈 지문으로 같은 문제를 알아보고 조사를 반복하지 않는다. |
| 개선 결과 | **조사 생략.** H0·H1 누적 24회(11/02~11/03)와 운영 정각 점검 27회(11/03~11/09)에서 조사 호출이 0회였다.<br>**최종 조사 9회.** 중앙값은 **183.8초·208,385토큰**이다. 200초 이내는 6회, 25만 토큰 이내는 7회였다. 초기 기준선 중앙값은 89초·115,734토큰이다.<br>**시나리오별 중앙값.** B1 113.7초·109,220토큰, C1 183.8초·287,950토큰(**토큰 초과**), C2 209.7초·208,385토큰(**시간 초과**). |
| 목표 산정 근거 | **200초.** 장애 감지 목표 5분에서 점검과 알림에 필요한 약 100초를 뺐다.<br>**25만 토큰.** 사전 확인과 재조사 1회를 포함해 도구 호출 상한 20회까지 쓸 수 있도록 정했다. |
| 운영자 직접 확인 항목 | **장애 6종 평균 74.2% 감소.** 규칙 진단 3종은 81.1%, AI 조사 3종은 67.2%다. 최종 평가 12회 합계는 **73개 → 21개**다.<br>**집계 방법.** 운영자가 확인할 상태값·설정값·오류·연결 결과를 세었다. 점검 결과나 보고서 근거에서 답을 얻은 항목의 비율을 시나리오별로 구한 뒤 같은 비중으로 평균했다. |
| 비용이 늘어난 부분 | 재조사와 도구 보강 뒤 일부 사례에서 조사 시간과 토큰이 늘었다. 여러 변경이 함께 적용된 결과다.<br>**C1.** 기준선 95초, 124,089토큰에서 도구·재조사 보강(11/02~11/03) 180초, 입력과 출력 합 약 31만 토큰이 되었고, C1 단독 재평가(11/09)에서도 166초, 277,296토큰이다.<br>**A1.** 기준선 77초에서 Pod별 확인 추가(11/03) 135초로 늘었다.<br>**배치별 중앙값.** Pod별 확인 추가 135초, 177,167토큰, 호출 체인 추가 후 축소 평가 167초, 297,944토큰으로 호출 체인 추가 후 축소 평가는 토큰 목표 25만을 넘었다.<br>**B1.** 도구·재조사 보강에서 Pod별 확인 추가로 가며 시간이 36% 줄었다. 요금으로 환산하지는 않았다 |
| 남은 과제 | **적용한 최적화.** 이전 도구 결과 발췌와 Service·Pod 확인 병렬화를 적용했다.<br>**C2.** 조사 시간 중앙값은 앞선 튜닝의 218.3초에서 최종 209.7초였고 병렬화의 단독 효과는 분리 측정하지 않았다.<br>**비용 집계 범위.** 조사 모델의 입력·출력 토큰을 합산했다. 근거 AI 요약과 이력 질의 채팅은 별도 호출이며 집계에서 제외했다.<br>**다음 검증.** C1의 로그 발췌 범위와 C2의 상태 조회 병렬화를 같은 재현 조건에서 한 번에 하나씩 바꿔 비교한다. 조사 시간·토큰과 함께 원인 정확도와 잘못된 확정 판정을 확인한다. |

## 3. 예외 처리 및 가드레일

| 항목     | 내용                              |
| ------ | ------------------------------- |
| 차단 대상  | 가드레일은 비밀값 노출, 진단 범위 밖 조회, 클러스터 변경을 막아야 한다. 로그·이벤트·API 응답에 포함된 지시문은 외부 데이터로 처리해야 한다. |
| 탐지 방식  | **비밀값.** 값의 형식과 이름 패턴으로 찾는다.<br>**조회 범위.** 도구 입력에서 네임스페이스를 받지 않고, 대상에 묶인 클라이언트를 사용한 뒤 결과의 범위를 다시 확인한다.<br>**외부 데이터의 지시문.** 지시문은 도구 결과를 태그로 감싸 데이터로만 전달하고 결과 안의 꺾쇠 기호를 이스케이프해 감싸기를 닫지 못하게 한다 |
| 대응 로직  | **마스킹.** 비밀값은 `***`로 바꾼 뒤에 근거 저장, LLM 전달, Slack 알림, 알림 이력, 화면, CLI 출력에 쓴다.<br>**조회 범위.** 범위를 벗어난 입력과 결과는 거부한다.<br>**지시문 격리.** 시스템 프롬프트가 태그 안의 지시처럼 보이는 문장을 따르지 않게 정한다.<br>**근거 인용.** 검증기가 저장 기록과 대조해 존재하지 않는 근거 번호를 걸러낸다.<br>**변경 제한.** 도구가 모두 조회 전용이고 Kubernetes 권한도 조회뿐이라 조치는 제안만 하고 실행하지 않는다 |
| 테스트 결과 | **마스킹.** 테스트 함수 41개로 검증했다. 긴 입력 2만 줄이 선형 시간에 처리되는지도 확인했다.<br>**지시문 격리.** 도구 결과, 이력 질의 채팅, 사전 확인, 재조사 메시지에서 닫는 태그가 데이터 경계를 벗어나지 못하는지 확인했다.<br>**기타 검증.** 도구 예산과 근거 검증을 포함해 로컬 전체 테스트 **1,962개**가 통과했다(11/10). 이벤트 필터 적용 후 조사 기록의 chaos 검색 결과는 **0건**이었다(11/01). |
| 한계     | **실환경 검증.** 로그·이벤트에 악성 지시를 넣어 방어율을 확인하는 과제가 남아 있다.<br>**마스킹 범위.** 마스킹은 패턴 기반이라 줄 앞에 타임스탬프가 붙은 개인 키 등은 가리지 못한다.<br>**Kubernetes 권한.** Kubernetes 권한은 리소스 단위라 진단 대상 네임스페이스의 Secret 값을 읽을 수 있고, 앱이 값을 즉시 버리는 것으로 막는다 |

## 4. 기타 문제 해결 사례

| **이슈 구분** | **문제 상황 및 원인** | **해결 과정과 결과** |
| --- | --- | --- |
| **운영 알림 / 첫 알림과 조사 결과 갱신** | 새 이슈를 먼저 알리고, AI 조사가 끝나면 같은 알림에 결과를 갱신해야 한다. | **운영 경로 확인.** 실제 Slack 첫 알림 6건과 조사 결과 갱신 3건을 확인했다. |
| **운영 알림 / 심각도 갱신** | 이슈 지문(같은 문제를 알아보는 값)이 같은 채 1차 심각도가 주의에서 긴급으로 올라가면 "이어지는 이슈"로 처리되어, 알림 갱신과 새 담당자 호출이 나가지 않았다. 담당자 멘션 기능을 만들다 발견했다 | **적용.** 지문이 같아도 심각도가 오르면 "변경"으로 처리해 알림을 갱신하고 새 담당자를 스레드 답글로 부르게 했다. 재조사는 AI 조사 경로에서 수행한다. 심각도가 내려가면 이미 알린 값을 유지하고 다시 알리지 않는다.<br>**검증.** 11/09 단위 테스트에서 확인했다. |
| **동시 실행** | 주기 점검, 화면의 지금 점검, CLI가 같은 점검을 겹쳐 돌려 같은 이슈를 동시에 열 수 있었다 | SQLite에 점검 잠금을 두어 점검을 동시에 1건만 돌게 했다. 주기 점검은 잠겨 있으면 건너뜀을 기록하고 정상 종료한다 |
| **보고서 가설 수** | 계획은 문제당 가설 최대 3개인데 저장된 보고서 6건의 가설이 5개에서 7개였다 | **확인.** 저장된 보고서와 단계 기록을 대조했다. 계획의 가설 목록과 별도로 보고서가 세부 원인과 배제한 대안을 정리한다.<br>**결정.** 3개로 자르면 나중에 확인한 실제 원인과 배제 근거를 버려 판단 수준에 영향을 줄 수 있어, 상한을 코드로 강제하지 않기로 했다. 상한 강제에 따른 정확도 변화는 실험하지 않았다 |

**후속 검증 우선순위**는 원인 리소스 특정과 판단 수준 보정이다. C2에서 Redis 연결 차단을 어디까지 근거로 확인할 수 있는지, 원인 가설이 입증되지 않았을 때 보고서가 후보 또는 추정으로 남는지 먼저 검증한다. 다음 과제는 운영과 유사한 로그·이벤트를 이용한 가드레일 평가와 경로별 실제 청구액 측정이다.
