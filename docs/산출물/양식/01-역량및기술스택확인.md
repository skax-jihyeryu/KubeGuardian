# 1. 역량 및 기술 스택 확인

> 프로젝트: KubeGuardian AI. AI 기반 Kubernetes 서비스 환경 진단 Agent (1인, 8주, 주 10~15시간)
>
> 역량과 경험, 학습 계획의 세부는 [상세본](../01-역량및기술스택확인.md)에 있다.

## 1. 현재 보유 역량

- Python 숙련도: 고급. FastAPI 계층형 백엔드(routes, service, repository), async SQLAlchemy, Pydantic 검증, 외부 API 연동(재시도와 타임아웃)을 실무에서 설계하고 구현했다.
- AI/ML 경험: 모델 학습보다 LLM 기반 AI 서비스의 설계, 구축, 운영이 중심이다. 수집, 정제, 유사도 중복 제거, LLM 관련성 판정으로 이어지는 데이터 파이프라인을 Prefect로 병렬 실행했고, 운영 데이터(Databricks, AWS)로 에이전트 응답 이슈의 원인을 분석했다.
- LLM 활용 경험: Azure OpenAI, AWS Bedrock, LangGraph, LangChain, DeepAgents, Structured Output, Arize Phoenix 트레이싱. 규칙으로 먼저 판정해 LLM 호출을 줄이는 규칙과 LLM 결합 구조를 설계했다.
- RAG/Agent 구현 경험: 있음
  - Agent: LangGraph 기반 PR 보도자료 작성 에이전트(Router 노드 분기, 자료 유형별 검색 Tool Calling, Checkpointer 세션 관리). 운영 중인 에이전트를 DeepAgent 구조로 전환했다.
  - RAG: 하이브리드 검색(BM25와 KNN을 RRF로 결합, 필드별 가중 KNN), AWS OpenSearch, Upstage 임베딩
  - 부족한 부분: 에이전트 결과의 정답 기반 정량 평가, Kubernetes 장애의 원인 분석
- 프로젝트 경험
  1. SK Inc. AI Agent 구축과 '26 안정화: LangGraph 에이전트와 하이브리드 RAG 구현, FastAPI와 PostgreSQL 백엔드 개발. 안정화 과제에서 DeepAgent 전환, AWS EKS 운영 인프라 정리, 장애 대응을 맡았다.
  2. BeingAX AI Agent, PR 뉴스 모니터링: 규칙과 LLM을 결합한 판정 구조로 비용과 일관성을 확보했고, Airflow 구조를 Prefect 워커와 FastAPI 분리 구조로 재설계했다.

## 2. 학습 필요 영역

- LangChain/LangGraph 기초: 실무 보유. 기초 학습 대신 가설을 세우고 도구로 검증해 판정하는 조사형 에이전트 설계로 심화했다. 조사 흐름 전체를 LangGraph로 구현했다.
- RAG 구현: 실무 보유. 이번에는 조사 지침 문서 6개와 환경 설명 1개를 시스템 프롬프트에 통째로 넣는 수준으로만 썼다. 필요한 지침만 불러오는 방식은 구현하지 않았다.
- Multi-Agent 시스템 설계: 실무 보유. 조사는 에이전트 하나로 충분해서 하위 조사 확장은 하지 않았다. 저장된 이력에만 답하는 이력 질의 에이전트를 별도로 하나 두었다.
- Vector DB 활용: 실무 보유. 지침 문서 규모가 작아 쓰지 않았다.
- 프롬프트 엔지니어링: 실무 보유. 사실 문장마다 근거 인용을 강제하고, 도구 결과 안의 문장을 지시로 따르지 않게 하는 규칙과 장애 유형별 조사 지침으로 심화했다.
- API 개발 (FastAPI): 실무 보유. 그대로 활용했다.
- UI 개발 (Streamlit): 미보유. 별도 UI 프레임워크 없이 FastAPI, Jinja2, HTMX 서버 렌더링으로 보고서 화면을 만들었다. 운영자 알림은 Slack이 맡는다.
- 추가, Kubernetes 장애 분석(중점): 리소스 모델, Service 라우팅, 설정 참조, RBAC, CronJob을 규칙 점검 코드와 장애 재현으로 학습했다.
- 추가, 에이전트 정량 평가(중점): 정답 데이터 설계, 지표 정의, 자동 채점 러너, 규칙만 쓰는 조건과의 비교를 직접 만들었다.
- 추가, 장애 주입(Chaos Mesh)과 Slack 앱 연동. MCP와 기술 비교 실험은 계획했으나 일정상 하지 않았다.

## 3. 기술 스택 선호도

| 영역 | 기술 |
|---|---|
| 언어와 API | Python 3.12, FastAPI, Pydantic |
| 패키지와 테스트 | uv, pytest, ruff |
| 에이전트 | LangGraph |
| LLM | Azure OpenAI (조사 gpt-6.1-sol, 평가 채점 gpt-4.1, 근거 요약 gpt-6-luna), Structured Output |
| K8s 접근과 실행 | kubernetes Python 클라이언트, CronJob(매시 정각 점검), minikube |
| 알림 | Slack 앱. 봇 토큰으로 알림만 보내고, 긴급 알림의 확인 버튼 클릭만 Socket Mode로 받는다 (slack_sdk) |
| 저장소 | SQLite |
| 추적 | Arize Phoenix (OpenTelemetry) |
| 화면 | Slack(알림 전용), 보고서 화면(FastAPI, Jinja2, HTMX), CLI(kg check, kg investigate, kg ask) |
| 장애 주입과 평가 | Chaos Mesh, kubectl 패치 스크립트, 자체 평가 러너 |

## 4. 프로젝트 관심 도메인

- 1순위 도메인: 미디어/홍보(PR)
- 2순위 도메인: 제조(반도체)
- 관심 사유: KubeGuardian 자체는 산업 중립적인 IT 운영 도구라서, 진단 대상 서비스의 도메인으로 연결한다.
  - 미디어/홍보: 진단 대상 템플릿의 대표 서비스가 직접 구축하고 운영한 SK Inc. PR 보도자료 자동화 서비스다. PR 업무는 보도 시점과 위기 대응처럼 시간에 민감해서 서비스 중단이 곧 업무 중단이며, 실제 운영 장애가 시나리오의 출처다.
  - 제조: SK하이닉스 보안 환경 재구축처럼 네트워크와 설정 값이 달라지는 환경의 배포 장애는 KubeGuardian의 설정 대조 점검이 가장 잘 맞는 영역이다.

## 5. 8주 목표 설정

- 기술 목표: 매시 정각 점검, AI 조사와 검증, 근거를 인용한 보고서, Slack 알림까지 동작하는 Kubernetes 진단 에이전트를 직접 설계하고 구현하며, Kubernetes 상태만으로는 원인이 보이지 않는 장애의 원인을 찾게 만든다.
- 비즈니스 목표: 템플릿 기반 AI 서비스 환경에서 동작하는 진단 에이전트 PoC를 완성한다. 장애 시나리오 6개와 정상 기준선 2개에서 원인 정확도 70% 이상을 목표로 하고, 규칙만 쓸 때 대비 효과를 숫자로 제시한다. 측정 결과는 07 산출물에서 다룬다.
- 성장 목표: 정량적으로 설계하고 숫자로 증명하는 Lv.3 Middle AI 개발자가 된다. 정답 파일과 지표를 개발 전에 정의하고, 평가 러너로 자동 측정하고, 기준 조건 대비 결과표와 실패 사례 분석으로 보고한다. 학습 노트와 설계 결정 기록(ADR 2건)으로 판단 근거를 남겼다.
