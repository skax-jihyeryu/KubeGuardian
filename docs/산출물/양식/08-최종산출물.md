# 프로젝트 개요

## 문제 정의

운영 중인 PR Agent 서비스에서 Pod는 모두 정상이었지만, **사용자 문의가 들어오고 나서야 장애를 알았다.** 증상은 채팅에 나타났지만 원인은 LLM API 할당량, Redis 연결 차단처럼 **다른 지점**에 있어, 앱 6개와 DB·캐시가 엮인 MSA에서 원인을 찾기까지 **약 3일**이 걸렸다.

## 프로젝트명

KubeGuardian — 규칙 점검과 AI 조사로 Kubernetes 서비스 장애 원인을 찾는 진단 에이전트

Kubernetes 리소스 상태로는 보이지 않는 서비스 장애를 정기 점검으로 먼저 감지하고, 규칙이 잡지 못하는 장애는 AI가 근거를 모아 원인 지점을 찾는다.

## 기술 스택

Python 3.12, FastAPI, LangGraph, Azure OpenAI, Kubernetes Python Client, SQLite, Slack SDK, Arize Phoenix, HTMX/Jinja2

minikube 기반 단일 클러스터 환경에서 조회 전용 진단과 평가 러너를 함께 구성했다.

## 주요 기능

* 주기 점검과 규칙 기반 이상 감지

* 기능 실패 시 AI 조사·가설 검증·근거 포함 보고서 생성

* Slack 알림, 보고서 화면, CLI 기반 수동 점검/조사

* 이력 기반 질의 에이전트: 과거 장애의 원인·조치·근거를 채팅으로 질의

## 기대 효과

AI 기능이 늘수록 서비스 구조가 복잡해져 증상과 원인의 거리가 더 멀어진다. 원인 파악을 일 단위에서 분 단위로 줄여 장애로 인한 업무 중단과 대응 비용을 줄인다. Key Message: 장애 원인 파악 3일 → 3분

Pod 상태만으로 드러나지 않는 장애를 조기에 감지하고, 운영자가 직접 확인해야 할 항목을 줄여 의사결정을 빠르게 돕는다.

정상 시 LLM 호출을 생략해 비용을 줄이고, 정답 기반 평가로 정확도를 검증한다.

# 서비스 아키텍처

![KubeGuardian 아키텍처](assets/kubeguardian-architecture.png)

## 기술 설계

* 01 점검 기준: 정상의 기준을 명확히 세워 장애를 놓치지 않고, AI 없이 판단할 수 있는 장애는 규칙으로 빠르게 점검함.

* 02 먼저 알림: 원인 파악을 기다리지 않고 문제가 있다는 사실을 운영자에게 먼저 알림.

* 03 조사 에이전트: 필요한 정보는 AI 조사 전에 먼저 제시하고, 부족하면 Runbook 기반 가설과 도구로 모은 근거로 원인을 파악함.

## 점검 계층

CronJob이 Kubernetes 리소스를 수집하고 규칙 14개와 기능 점검을 수행한다.

## 조사 계층

LangGraph 기반 조사 서버가 문제 선별, 가설 수립, 도구 호출, 보고서 생성을 담당한다.

이력 기반 질의 에이전트는 질문 파악, 이력 조회, 답변 작성, 근거 검증 순서로 과거 장애 질의에 답한다.

## 데이터/추적 계층

SQLite에 점검 결과·이슈·보고서·근거를 저장하고, Arize Phoenix로 조사 단계를 추적한다.

## 출력 계층

Slack 알림, FastAPI 기반 보고서 화면, CLI 명령(`kg check`, `kg investigate`, `kg ask`)으로 결과를 제공한다.

## 핵심 데이터 흐름

1. 정기 점검 또는 수동 명령으로 진단을 시작함.

2. 규칙이 적발한 장애는 진단 결과와 함께 바로 알림.

3. AI 조사가 필요하면(규칙은 통과했지만 기능 실패나 사용자 증상이 있으면) 문제 알림을 먼저 보낸 뒤 조사 결과를 추가로 알림.

4. 조사 결과를 보고서와 근거로 저장하고 Slack 알림을 갱신함.

5. 처리 이력은 이후 조사 시 지식 기반으로 재사용함.

# 핵심 기능 및 Agent 구현 내용

## 핵심 기능

### 규칙 기반 점검 게이트

규칙 장애는 코드로 판정하고, 기능 점검 실패나 사용자 증상 입력이 있을 때만 AI 조사를 시작하도록 구현했다.

### AI 조사 루프

LangGraph로 문제 선별 → 가설 수립 → 도구 선택 → 실행 → 가설 판정 → 보고서 작성 흐름을 구성했다.

* ReAct(Reasoning + Acting): 추론과 도구 실행을 번갈아 하며 근거를 모음.

* Self-Correction: 코드가 근거 번호를 대조해 빈틈이 있으면 다시 조사함(외부 피드백).

### 근거 기반 보고서 생성

결론, 영향 범위, 근거, 가설 판정, 확인 범위, 조치, 재검증 방법을 구조화해 저장하고 검증한다.

### 이력 기반 질의 에이전트

질문 파악 → 이력 조회 → 답변 작성 → 근거 검증 순서로 동작한다.

과거 장애의 원인·조치·근거를 채팅(`kg ask`)으로 질의할 수 있다.

### 운영 인터페이스

Slack 1차 알림과 갱신, 보고서 화면, CLI를 통해 자동 점검과 수동 조사를 지원한다.

## 사용 기술/라이브러리

* LangGraph — 조사 상태와 노드 기반 오케스트레이션

* Azure OpenAI — 문제 선별, 가설 생성, 보고서 작성

* Kubernetes Python Client — 리소스, 로그, 이벤트 조회

* Pydantic — 구조화 출력과 보고서 스키마 검증

* SQLite — 점검 결과, 이슈, 근거, 보고서 저장

* Slack SDK — 알림 발송과 운영 연동

* Arize Phoenix — 모델/도구 호출 추적

# KPI 달성도

평가 구성: 장애 10종 + 정상 2종, 총 28회

## 달성 항목

* 원인 정확도 — 70% 이상 → AI 조사 100%(18/18, 원인 지점 기준), 규칙 진단 4/4 (달성)

* 장애 감지 시간 — 5분 이내 → AI 조사 장애 평균 184초(최대 241초), 규칙 진단 0.2~3.5초 (달성)

* 확인 항목 감소율 — 70% 이상 → 평균 74.2%, 142개 → 37개 (달성)

* AI 조사 시간·비용 — 중앙값 200초·25만 토큰 이하 → 200.3초(목표 수준)·200,764토큰 (토큰 달성)

## 미달성 항목

* 시나리오별 세부 목표 안정화 — 모든 시나리오에서 시간/토큰 기준 충족 → C1·C4는 토큰 초과, C2·C4·C8은 시간이 200초를 조금 넘음 (부분 미달성)

원인 지점은 모두 찾았지만, 그 안의 원인 리소스까지 특정한 것은 8회(44%)이고, C1·C2·C8은 원인 지점까지만 찾고 원인 리소스는 특정하지 못했다.

복합 의존성 장애(C1, C2, C4, C8)에서 추가 재조사와 근거 검증이 늘어나 비용과 시간이 증가했다.

# 기술 문제 해결 과정

핵심 기술 난제: 증상이 보이는 지점과 원인 지점이 다른 MSA에서 진짜 원인을 찾는 문제이다. 초기에는 오류를 전달만 한 컴포넌트를 지목하거나, 일부 Pod만 실패하는 장애를 놓치거나, 충분히 확인하기 전에 원인을 확정했다.

## 대표 이슈

### 간헐 장애 탐지 실패

1. 문제 상황 — agent Pod 3개 중 1개만 실패하는 B1 시나리오를 초기 기준선에서 찾지 못함.

2. 원인 — Service 경유 호출만으로는 실패 Pod가 아닌 정상 Pod에 연결될 수 있음.

3. 해결 방법 — Pod별 직접 호출과 재조사 규칙을 추가함.

4. 결과 — B1 정확도가 0/3에서 3/3으로 개선됨.

### 오확정 보고서 문제

1. 문제 상황 — 근거가 부족한 보고서도 확정으로 표시되는 문제가 있음.

2. 원인 — 모델 확신도에 의존하고 코드 수준의 판정 조건이 약했음.

3. 해결 방법 — 지지된 가설과 근거 출처 수를 기준으로 확정/후보/추정을 코드로 재판정함.

4. 결과 — 오확정률이 27%에서 21%로 낮아짐.

### 원인 리소스 혼동

1. 문제 상황 — C1 시나리오에서 실제 원인 지점은 찾았지만 원인 리소스를 agent로 잘못 지목하는 경우가 있음.

2. 원인 — 호출자 로그와 하위 컴포넌트 오류 출처를 분리해 해석하지 못함.

3. 해결 방법 — 호출 체인 검증을 추가하고 근거가 약한 결론은 후보로 제한함.

4. 결과 — C1 재평가 3/3을 유지하면서 과도한 확정 판정을 줄임.

### 보안 마스킹 누락

1. 문제 상황 — 점검과 조사가 환경변수, 로그, 설정 등 많은 클러스터 정보를 수집해 Slack, CLI, 웹 화면, DB 이력으로 내보내는데, 인증 헤더, 쿠키, 앞뒤가 잘린 개인 키 본문이 일부 출력 경로에서 마스킹되지 않고 노출됨.

2. 원인 — 마스킹 패턴이 Authorization·Cookie 헤더 형식과 BEGIN·END가 잘린 PEM 본문을 다루지 못했고, 출력 경로(CLI 출력 등)마다 마스킹이 적용되는지 검증하지 않았음.

3. 해결 방법 — 수집 단계에서 Secret 값은 버리고 키 이름만 남기며, 공통 마스킹 함수(`core/guard/redact.py`)를 Slack 알림, CLI, 웹 화면, DB 이력 저장 경로에 적용함. 헤더 및 잘린 PEM 본문 패턴을 보강하고 CLI 출력의 누락 지점을 수정함.

4. 결과 — 마스킹 규칙과 출력 경로별(Slack 알림, CLI) 테스트를 추가했고 전체 2,199개 테스트를 통과함.

# 향후 개선 및 확장 방향

한계 → 다음: 원인 지점은 모두 찾았지만 그 안의 원인 리소스는 일부만 특정 → 연결 구간을 확인하는 Runbook·점검 규칙 확장

## 단기 개선 (1~3개월)

* 컴포넌트 사이 연결 구간을 확인하는 Runbook과 점검 규칙을 확장해 원인 지점 안의 원인 리소스(LLM 할당량, Redis 연결, 배포명 설정) 특정

* 확정/후보/추정 판단 조건 정교화

* 조사 시간·토큰이 큰 경로의 로그 전달량 축소와 병렬화

* PoC 범위 내 화면 인증과 운영 설정 보강

조사 신뢰도와 비용 효율을 함께 높여 운영 적용 가능성을 개선할 수 있다.

## 장기 확장 (6개월+)

* 의미 기반 이력 검색과 장애 사례 재사용 고도화

* 운영자 승인 기반 조치 자동화 에이전트 확장

* 변경 이력·정상 설정 비교 기반 사전 검증 기능 추가

* 실제 운영 클러스터와 다중 프로젝트 지원 구조로 확장

장애 탐지 도구를 넘어 조사·기록·후속 조치까지 연결되는 운영형 AI 에이전트로 확장할 수 있다.
