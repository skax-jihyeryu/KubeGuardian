# 프로젝트 개요

## 프로젝트명

KubeGuardian AI — AI 기반 Kubernetes 서비스 환경 진단 Agent

템플릿 기반 AI 서비스 환경에서 규칙 점검과 AI 조사를 결합해 장애 원인과 조치 가이드를 제공하는 PoC입니다.

## 기술 스택

Python 3.12, FastAPI, LangGraph, Azure OpenAI, Kubernetes Python Client, SQLite, Slack SDK, Arize Phoenix, HTMX/Jinja2

minikube 기반 단일 클러스터 환경에서 조회 전용 진단과 평가 러너를 함께 구성했습니다.

## 주요 기능

* 주기 점검과 규칙 기반 이상 감지

* 기능 실패 시 AI 조사·가설 검증·근거 포함 보고서 생성

* Slack 알림, 보고서 화면, CLI 기반 수동 점검/조사

## 기대 효과

Pod 상태만으로 드러나지 않는 장애를 조기에 감지하고, 운영자가 직접 확인해야 할 항목을 줄여 의사결정을 빠르게 돕습니다.

정상 시 LLM 호출을 생략해 비용을 줄이고, 정답 기반 평가로 정확도를 검증합니다.

# 서비스 아키텍처

## 점검 계층

CronJob이 Kubernetes 리소스를 수집하고 규칙 14개와 기능 점검을 수행합니다.

## 조사 계층

LangGraph 기반 조사 서버가 문제 선별, 가설 수립, 도구 호출, 보고서 생성을 담당합니다.

## 데이터/추적 계층

SQLite에 점검 결과·이슈·보고서·근거를 저장하고, Arize Phoenix로 조사 단계를 추적합니다.

## 출력 계층

Slack 알림, FastAPI 기반 보고서 화면, CLI 명령(`kg check`, `kg investigate`, `kg ask`)으로 결과를 제공합니다.

## 핵심 데이터 흐름

1. 정기 점검 또는 수동 명령으로 진단을 시작합니다.

2. 규칙 장애가 있으면 규칙 기반 진단 결과를 바로 알립니다.

3. 규칙은 통과했지만 기능 실패나 사용자 증상이 있으면 AI 조사를 시작합니다.

4. 조사 결과를 보고서와 근거로 저장하고 Slack 알림을 갱신합니다.

5. 처리 이력은 이후 조사 시 지식 기반으로 재사용합니다.

# 핵심 기능 및 Agent 구현 내용

## 핵심 기능

### 규칙 기반 점검 게이트

규칙 장애는 코드로 판정하고, 기능 점검 실패나 사용자 증상 입력이 있을 때만 AI 조사를 시작하도록 구현했습니다.

### AI 조사 루프

LangGraph로 문제 선별 → 가설 수립 → 도구 선택 → 실행 → 가설 판정 → 보고서 작성 흐름을 구성했습니다.

### 근거 기반 보고서 생성

결론, 영향 범위, 근거, 가설 판정, 확인 범위, 조치, 재검증 방법을 구조화해 저장하고 검증합니다.

### 운영 인터페이스

Slack 1차 알림과 갱신, 보고서 화면, CLI를 통해 자동 점검과 수동 조사를 지원합니다.

## 사용 기술/라이브러리

* LangGraph — 조사 상태와 노드 기반 오케스트레이션

* Azure OpenAI — 문제 선별, 가설 생성, 보고서 작성

* Kubernetes Python Client — 리소스, 로그, 이벤트 조회

* Pydantic — 구조화 출력과 보고서 스키마 검증

* SQLite — 점검 결과, 이슈, 근거, 보고서 저장

* Slack SDK — 알림 발송과 운영 연동

* Arize Phoenix — 모델/도구 호출 추적

# KPI 달성도

## 달성 항목

* 원인 정확도 — 70% 이상 → AI 조사 88.9%, 규칙 진단 3/3 (달성)

* 장애 감지 시간 — 5분 이내 → AI 조사 평균 170초, 규칙 진단 0.6~3.1초 (달성)

* 확인 항목 감소율 — 70% 이상으로 조정 목표 → 평균 74.2%, 73개 → 21개 (달성)

* AI 조사 시간·비용 — 중앙값 200초·25만 토큰 이하 → 183.8초·208,385토큰 (달성)

## 미달성 항목

* 시나리오별 세부 목표 안정화 — 모든 시나리오에서 시간/토큰 기준 충족 → C1은 토큰 초과, C2는 시간 초과 (부분 미달성)

복합 의존성 장애(C1, C2)에서 추가 재조사와 근거 검증이 늘어나 비용과 시간이 증가했습니다.

# 기술 문제 해결 과정

## 대표 이슈

### 간헐 장애 탐지 실패

1. 문제 상황 — agent Pod 3개 중 1개만 실패하는 B1 시나리오를 초기 기준선에서 찾지 못했습니다.

2. 원인 — Service 경유 호출만으로는 실패 Pod가 아닌 정상 Pod에 연결될 수 있었습니다.

3. 해결 방법 — Pod별 직접 호출과 재조사 규칙을 추가했습니다.

4. 결과 — B1 정확도가 0/3에서 3/3으로 개선되었습니다.

### 오확정 보고서 문제

1. 문제 상황 — 근거가 부족한 보고서도 확정으로 표시되는 문제가 있었습니다.

2. 원인 — 모델 확신도에 의존하고 코드 수준의 판정 조건이 약했습니다.

3. 해결 방법 — 지지된 가설과 근거 출처 수를 기준으로 확정/후보/추정을 코드로 재판정했습니다.

4. 결과 — 오확정률이 27%에서 21%로 낮아졌습니다.

### 원인 리소스 혼동

1. 문제 상황 — C1 시나리오에서 실제 원인 지점은 찾았지만 원인 리소스를 agent로 잘못 지목하는 경우가 있었습니다.

2. 원인 — 호출자 로그와 하위 서비스 오류 출처를 분리해 해석하지 못했습니다.

3. 해결 방법 — 호출 체인 검증을 추가하고 근거가 약한 결론은 후보로 제한했습니다.

4. 결과 — C1 재평가 3/3을 유지하면서 과도한 확정 판정을 줄였습니다.

### 보안 마스킹 누락

1. 문제 상황 — 인증 헤더, 쿠키, 잘린 개인 키 본문이 일부 출력 경로에서 마스킹되지 않았습니다.

2. 원인 — 패턴 조건과 출력 경로별 검증이 충분하지 않았습니다.

3. 해결 방법 — 마스킹 규칙을 보강하고 Slack, CLI, 이력 저장 경로 테스트를 추가했습니다.

4. 결과 — 관련 단위 테스트를 확장했고 전체 1,962개 테스트를 통과했습니다.
