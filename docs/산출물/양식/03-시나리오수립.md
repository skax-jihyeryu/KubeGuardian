**시나리오 1 : 주기 점검으로 이상을 감지하고 Slack으로 알림 받기**

* ID : SC-001

* 상황 : 평일 오후 운영자가 다른 업무 중일 때 llm-gateway의 LLM 사용 할당량이 소진되어 보도자료 초안 생성이 실패하기 시작했다. Pod는 모두 정상이라 대시보드에는 표시가 없고, PR 담당자는 아직 문의하지 않았다. 지금 방식이라면 장애 인지부터 원인 파악까지 약 3~5일(추정)이 걸린다.

* 목표 : 사용자가 문의하기 전에 원인과 조치 방법이 담긴 알림을 먼저 받는다.

* 사전 조건 : KubeGuardian이 조회 전용 권한으로 설치되어 매시 정각 점검(CronJob)과 조사 worker(diagnostic-agent)가 돌고 있고, 설정에 기능 점검(로그인 후 채팅)이 등록되어 있으며, Slack 앱이 알림 채널에 연결되어 있고, 보고서 화면에 접근할 수 있음

* 상세 흐름

| 단계 | 구분 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | ------ | -- |
| 1  | 감지 | 없음 | 14시 정각 점검에서 규칙은 모두 통과하고, 기능 점검의 채팅 단계가 실패한다 | 정상이면 기록만 남김 |
| 2  | 판정 | 없음 | 규칙 신호는 없고 기능 점검이 실패했으므로 조사 시작(기능 점검 실패), 1차 심각도 긴급, 새 이슈로 판정한다 | 같은 문제의 이슈가 열려 있으면 AI 생략 |
| 3  | 1차 알림 | Slack 알림 수신 | AI 조사를 기다리지 않고 1차 알림을 보낸다 (심각도, 실패한 기능, 원인 조사 중) | 점검 직후 |
| 4  | 조사 | 없음 | 조사 작업자(worker)가 조사 대기열에서 이슈를 집어, 가설 없이 확인할 사실을 먼저 모은다 (채팅 호출 재현, 로그의 오류 줄, Pod와 이벤트). 이어 가설을 세우고 도구로 검증한다 | 도구 호출 20회, 150초 상한 |
| 5  | 원인 갱신 | 갱신된 알림 수신 | 같은 메시지를 원인, 판단 수준, 영향, 조치로 갱신하고 스레드에 원인 확인 답글을 단다 | 조사 상한에 닿으면 조사 미완, LLM 오류면 조사 실패로 표시 |
| 6  | 인지와 확인 | 보고서 화면 열람, 원하면 확인 버튼 클릭 | 화면에서 결론, 근거, 가설 판정, 확인한 범위, 조치, 재검증 방법을 본다. 확인 버튼을 누르면 확인 답글이 달리고 리마인더가 멈춘다 | 긴급 알림에만 확인 버튼 |
| 7  | 조치 | 보고서대로 llm-gateway 할당량 조치 | 조치는 사람이 실행 | 자동 실행 없음 |
| 8  | 재알림과 복구 | 리마인더와 복구 알림 수신 | 긴급 알림은 확인할 때까지 30분마다 다시 알린다. 확인 기능을 쓸 수 없으면 리마인더는 최대 3회다. 다음 정각 점검에서 복구를 확인하면 복구 알림을 한 번 보낸다 | 같은 알림 반복 없음 |

```text
(자동 실행, 사용자 입력 없음)
```

* 성공 기준

  * 기준 2 : 보고서에서 조치와 재검증 방법을 확인할 수 있고, 같은 알림이 반복되지 않으며 정해진 간격의 리마인더와 복구 알림 1회만 발송됨

**시나리오 2 : 배포 직후 지금 점검으로 이상 확인하기**

* ID : SC-002

* 상황 : agent 배포 설정을 수정해 배포한 직후, 다음 정각 점검을 기다리지 않고 바로 확인하려 한다. 채팅이 전부 실패하는데 경고, 이벤트, 개선 권고가 함께 섞여 있다. 실제 원인은 agent Service의 selector 값 오타로, 연결된 Pod가 0개가 된 것이다.

* 목표 : 지금 장애가 어느 리소스에서 적발됐는지 바로 보고, 지금 장애와 무관한 개선 권고는 분리해서 본다.

* 사전 조건 : KubeGuardian 설치, 보고서 화면 또는 CLI(kg check)를 실행할 수 있음

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1  | 보고서 화면에서 지금 점검 클릭 (또는 CLI kg check) | 주기 점검과 같은 점검을 즉시 실행한다. 다른 점검이 진행 중이면 시작하지 않는다 | 웹의 지금 점검은 1분 간격 제한 |
| 2  | 점검 상세 확인 | 규칙이 selector에 맞는 Pod가 없는 Service를 긴급으로 적발하고(조사 안 함: 규칙 기반 진단 결과), 기능 점검의 채팅도 실패한다. 개선 권고는 점검 행에 건수로만 표시한다 | 권고만 나오면 이슈를 열지 않고 이상 없음 |
| 3  | Slack 알림 확인 | 새 이슈이므로 주기 점검과 같은 1차 알림을 보내되 원인 조사 안내 대신 규칙 요약과 "근본 원인은 확인하지 않았습니다" 줄을 담는다. 조사 대기열에 넣지 않고 AI 원인 조사를 시작하지 않는다 | 알림은 원인으로 갱신되지 않음 |
| 4  | 보고서 화면 열람 | 이슈 상세에서 규칙 기반 진단 결과를 본다. 적발마다 위치, 규칙, 심각도, 근거, 확인할 사항이 한 행이고 함께 확인된 기능 실패가 따로 보인다 | |

* 입력 예시

```text
보고서 화면의 지금 점검 버튼 클릭, 또는 CLI: kg check
```

* 기대 출력

아래는 실제 메시지 형식을 따른 예시이며 시각, 원인 문장, 근거 종류, Pod 이름은 예시 값이다(실측 아님).

```text
🔴 *긴급 · dev — chat 기능 장애*
• 감지: 14:05 점검
• 사유: 적발: S01
• S01 selector에 맞는 Pod 없음 — dev/Service/agent
📋 규칙 기반 진단 결과입니다. 근본 원인은 확인하지 않았습니다.
🔗 이슈: <이슈 상세 링크>
```

이슈 상세의 규칙 기반 진단 결과는 다음과 같이 보인다.

```text
위치: dev/Service/agent
규칙: S01 selector에 맞는 Pod 없음 (긴급)
근거: Service selector app=agentx, 같은 앱으로 보이는 Pod의 라벨 app=agent
함께 확인된 기능 실패: chat 2단계 실패
확인할 사항: Service selector와 대상 Pod의 라벨이 일치하는지 확인하세요.
규칙이 확인한 위치와 사실입니다. 근본 원인과 영향 범위는 확인하지 않았습니다.
```

* 성공 기준

  * 기준 1 : 적발 위치(Service/agent)와 규칙(S01)이 알림과 이슈 상세에 보이고 AI 조사는 하지 않음

  * 기준 2 : 개선 권고는 알림 없이 화면에만 표시되어, 사람이 볼 적발이 1건으로 좁혀짐

**시나리오 3 : 자동 점검이 못 잡는 증상을 직접 입력해 조사 받기**

* ID : SC-003

* 상황 : PR 담당자가 초안 생성이 세 번에 한 번꼴로 실패한다고 문의했다. 정각 점검의 기능 점검은 요청이 한 번뿐이라 마침 정상 Pod로 가서 통과했다. 실제 원인은 agent Pod 3개 중 1개만 오류를 내는 것이다.

* 목표 : 문의를 받은 자리에서 증상을 그대로 입력하고 원인 조사 결과를 받는다.

* 사전 조건 : 시나리오 1과 같음, CLI를 실행할 수 있음

* 상세 흐름

| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| -- | ------ | ------ | -- |
| 1  | CLI에서 kg investigate 와 증상 입력 | 점검을 한 번 돌린 뒤, 규칙 신호가 없으면 입력한 증상(최대 500자)을 근거로 조사를 시작한다. 규칙이 장애를 적발했으면 AI 원인 조사 대신 규칙 결과를 출력한다 | 증상 조사는 CLI에서만 가능 |
| 2  | 진행 확인 | 등록된 기능 점검이 있으면 사전 확인에서 실패한 흐름 또는 첫 흐름을 다시 실행하고, 입력 증상에 대해 가설(특정 Pod만 오류, 하위 서비스 지연, 외부 호출 간헐 실패)을 세운다 | |
| 3  | 결과 확인 | Pod마다 직접 호출해 한 Pod만 500을 내는지 가리고, 결론 요약을 터미널에 출력한다 | 증상 조사로 새 이슈나 1차 알림을 만들지 않고, 일치하는 열린 이슈가 있으면 연결한다 |

* 입력 예시

```text
kg investigate "초안 생성이 세 번에 한 번꼴로 실패한다는 문의가 들어왔어요"
```

* 기대 출력

아래는 실제 메시지 형식을 따른 예시이며 시각, 원인 문장, 근거 종류, Pod 이름은 예시 값이다(실측 아님).

```text
조사 상태: done
결론: agent Pod 3개 중 agent-example-pod-b만 채팅 요청에 500을 반환하며, 나머지 2개는 정상 응답합니다. (판단 후보, LLM 확신도 medium)
판단 근거: 원인 리소스 설정 미인용 · 근거 출처 3종(로그, 설정·상태, 연결 확인) · 지지 가설 근거 2종
1순위: 채팅 간헐 실패: agent Pod 1개만 오류 (warning)
근거 N건
```

* 성공 기준

  * 기준 1 : 보고서 1순위 원인이 정답(agent Pod 1개만 오류)과 일치

  * 기준 2 : 조사가 Pod별 직접 호출로 특정 Pod를 가려냄
