# 3. 시나리오 수립

### 핵심 사용자 시나리오

**시나리오 1 : 주기 점검으로 이상을 감지하고 Slack으로 알림 받기**

* ID : SC-001

* 상황 : 평일 오후 운영자가 다른 업무 중일 때 llm-gateway의 LLM 사용 할당량이 소진되어 보도자료 초안 생성이 실패하기 시작했다. Pod는 모두 정상이라 대시보드에는 표시가 없고, PR 담당자는 아직 문의하지 않았다.

* 목표 : 사용자가 문의하기 전에 원인과 조치 방법이 담긴 알림을 먼저 받는다.

* 사전 조건 : KubeGuardian이 조회 전용 권한으로 설치되어 5분 주기 점검(CronJob)이 등록되어 있고, Slack 앱이 알림 채널에 초대되어 있음

* 상세 흐름

|    |        |        |    |
| -- | ------ | ------ | -- |
| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| 1  | — | 5분 주기 점검: 규칙은 모두 통과, 로그인 → 채팅 API 호출에서 채팅 실패 | 정상이면 기록만 남김 |
| 2  | — | 규칙은 통과했지만 증상이 있어 AI 조사 시작. 가설 3개(agent 오류 / llm-gateway 이상 / DB·Redis 문제)를 도구로 확인 | 도구 호출 20회·150초 이내 |
| 3  | Slack 알림 확인 | 알림 채널에 요약, 스레드에 전체 보고서 발송 | 장애 발생 후 7분 이내 |
| 4  | 보고서대로 할당량 상향 | 해결될 때까지 같은 알림을 반복하지 않음 | |
| 5  | 복구 알림 확인 | 다음 점검에서 정상 확인 후 복구 알림 1회 | |

* 입력 예시

```text
(자동 실행 — 사용자 입력 없음)
```

* 기대 출력

```text
🔴 [KubeGuardian] dev — 채팅이 실패하고 있습니다 (확신도 높음)
원인: llm-gateway LLM 할당량 소진 (오늘 사용량 100%)
조치: llm-gateway 관리 화면에서 할당량 상향 또는 초기화
전체 보고서는 스레드를 확인하세요.

  └ (스레드) 결론 / 근거 [근거 12, 14, 15] / 가설 판정(② 지지, ①·③ 배제와 이유)
            / 확인한 범위 / 권장 조치 / 재검증 방법

✅ [KubeGuardian] dev — 채팅이 정상으로 돌아왔습니다 (장애 지속 약 20분)
```

* 성공 기준

  * 기준 1: 장애 발생부터 알림 도착까지 7분 이내, 보고서 1순위 원인이 정답(할당량 소진)과 일치

  * 기준 2: 보고서만 보고 추가 확인 없이 조치할 수 있고, 해결 전까지 같은 알림이 반복되지 않음

**시나리오 2 : 배포 직후 Slack 명령으로 점검 받기**

* ID : SC-002

* 상황 : agent 배포 설정을 수정해 배포한 직후 다음 주기 점검을 기다리지 않고 바로 확인하려 한다. 채팅이 전부 실패하는데 경고·이벤트·과거 재시작 기록이 수십 개 섞여 있다. (실제 원인: Service의 대상 Pod 조건 오타)

* 목표 : 수십 개 신호 중 지금 장애의 원인만 골라 보고, 나머지는 개선 권고로 분리해서 본다.

* 사전 조건 : KubeGuardian 설치, Slack 앱이 채널에 초대되어 있음

* 상세 흐름

|    |        |        |    |
| -- | ------ | ------ | -- |
| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| 1  | Slack에서 `/kg check` 입력 | "점검을 시작합니다" 메시지를 올리고 주기 점검과 같은 점검을 즉시 실행 | 3초 안에 접수 |
| 2  | — | 규칙이 "agent Service에 연결된 Pod 0개"를 장애로 확정 → AI가 신호 47개 중 중요 문제를 선별 | |
| 3  | 스레드 확인 | 요약과 전체 보고서를 스레드에 답글로 올림 | 정상이면 "이상 없음 + 개선 권고"만 |

* 입력 예시

```text
/kg check
```

* 기대 출력

```text
지금 중요한 것 1건 (수집된 신호 47개 중)
 1. 🔴 채팅이 전부 실패합니다 (확신도 높음)
    agent Service의 대상 Pod 조건이 app=agnet이라 연결된 Pod가 0개입니다 [근거 4].
    조치: 대상 Pod 조건을 app=agent로 수정
참고 — 개선 권고 3건 (지금 장애와 무관)
```

* 성공 기준

  * 기준 1: 요약 1순위가 실제 원인(대상 Pod 조건 오타)과 일치

  * 기준 2: 확인할 항목 47개 → 중요 문제 1건 (확인 항목 감소율 90% 이상)

**시나리오 3 : 자동 점검이 못 잡는 증상을 Slack으로 맡겨 조사 받기**

* ID : SC-003

* 상황 : PR 담당자가 "초안 생성이 세 번에 한 번꼴로 실패해요"라고 문의했다. 주기 점검의 API 호출은 마침 정상 Pod로 가서 통과했다. (실제 원인: agent Pod 3개 중 1개만 오류)

* 목표 : 문의를 받은 Slack에서 바로 증상을 맡기고 원인 조사 보고서를 받는다.

* 사전 조건 : 시나리오 1과 같음, 명령 허용 채널·사용자로 등록되어 있음

* 상세 흐름

|    |        |        |    |
| -- | ------ | ------ | -- |
| 단계 | 사용자 행동 | 시스템 동작 | 비고 |
| 1  | Slack에서 `/kg investigate <증상>` 입력 | "조사를 시작합니다" 메시지를 올리고 AI 조사를 바로 시작 | 규칙 결과와 관계없이 조사 |
| 2  | 조사 계획 확인 | 가설(특정 Pod만 오류 / 응답 지연 / LLM 간헐 실패)을 스레드에 먼저 올림 | |
| 3  | 보고서 확인 | API 10회 반복 호출, Pod별 직접 호출, 로그 확인 후 보고서를 스레드에 올림 | |

* 입력 예시

```text
/kg investigate 초안 생성이 세 번에 한 번꼴로 실패한다는 문의가 들어왔어요
```

* 기대 출력

```text
[조사 보고서] 채팅 간헐 실패 — agent Pod 1개(agent-p9m)만 오류      확신도: 높음
근거: API 10회 중 3회 실패 [근거 21] / Pod 직접 호출 x2k 200, q4t 200, p9m 500 [근거 22~24]
권장 조치: kubectl delete pod agent-p9m -n dev (Deployment가 새 Pod를 띄움)
```

* 성공 기준

  * 기준 1: 보고서 1순위 원인이 정답(Pod 1개만 오류)과 일치

  * 기준 2: 조사 계획이 보고서보다 먼저 올라오고, 보고서 완성까지 120초 이내
