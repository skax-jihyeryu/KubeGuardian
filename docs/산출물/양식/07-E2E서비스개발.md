## 1. 최종 아키텍처 요약

* **완성된 아키텍처 핵심:** Kubernetes CronJob이 매시 정각에 점검하고 새 이슈를 알린다. 정기 점검이나 화면의 직접 점검에서 규칙 신호 없이 기능이 실패하면 조사 서버(diagnostic-agent)의 작업자(worker)가 LangGraph 에이전트를 실행한다. CLI의 `kg investigate`는 규칙 신호가 없으면 입력한 증상으로 직접 조사한다. 규칙이 장애를 적발하면 규칙 기반 진단 결과(위치, 규칙, 심각도, 근거, 확인할 사항)를 제공한다. 근거 요약은 원인 조사와 별도로 실행될 수 있다. 진단 대상은 minikube의 dev 네임스페이스(앱 6개와 PostgreSQL, Redis)다. 점검은 규칙 14개(장애 신호 12개, 개선 권고 2개)를 LLM 없이 코드로 판정하고, 로그인 후 채팅을 실제로 호출하는 기능 점검을 더해 Pod는 정상인데 서비스가 안 되는 증상을 잡는다. 규칙 신호, 기능 실패, 사용자 증상이 모두 없으면 AI 원인 조사를 시작하지 않는다.

* **최종 산출물 형태:** Slack 알림 앱(알림 전용, 긴급 알림에는 확인 버튼), 보고서 화면(FastAPI, Jinja2, HTMX로 만든 점검 이력, 이슈, 점검 구성, 지금 점검, 근거 원문, 이력 질의 채팅 패널), CLI(kg check, kg investigate, kg ask). 화면은 인증 없이 port-forward로만 접근하는 PoC다.

* **Agent 구조:** 요청은 다음 순서로 흐른다.

  1. CronJob이 Kubernetes API를 조회 전용으로 수집해 규칙 14개를 판정하고 기능 점검을 실행한다. 수집에 실패한 항목은 통과가 아니라 "확인하지 못함"으로 남긴다.
  2. 게이트가 조사를 시작할지 정한다. 장애 신호가 있으면 "조사 안 함 — 규칙 기반 진단 결과", 새 기능 실패에 조사 요청을 만들면 "조사 시작 — 기능 점검 실패", 장애 신호가 없으면 "조사 안 함 — 장애 신호 없음"이다.
  3. 정기 점검이나 화면의 직접 점검에서 새 이슈가 열리면 Slack에 1차 알림을 먼저 보내고, 규칙 신호 없는 기능 실패(경로 B)만 조사 요청을 대기열에 넣는다. 규칙 감지(경로 A)는 규칙 결과를 담아 알림을 끝낸다. 같은 문제는 이슈 지문으로 알아보고 다시 조사하지 않는다.
  4. 조사 작업자가 대기열에서 조사를 집어 읽기 전용 도구 7종으로 사실을 모으고 가설을 검증한다. 끝나면 근거 검증기와 빈틈 검사를 거친 보고서를 저장하고, 코드가 판단 수준(확정, 후보, 추정)을 정한다.
  5. 1차 알림을 원인, 판단 수준, 조치로 갱신하고 스레드에 답글을 단다. 다음 점검에서 문제가 사라지면 이슈를 닫고 복구 알림을 한 번 보낸다.

  조사 모델은 Azure OpenAI를 호출하고, 운영자 알림은 Slack으로 보낸다. 조사 단계는 Arize Phoenix로 추적하며 점검 결과와 보고서, 근거는 SQLite에 저장한다.

## 3. 창출된 핵심 가치

### 3-1. 비즈니스 가치

* **운영자는 사용자 제보를 기다리기 전에 로그인·채팅 장애를 알아차릴 수 있다.** 정기 기능 점검이 실제 요청을 보내 실패를 감지하고 Slack에 알린다. 평가에서는 Kubernetes 규칙 점검을 통과했던 LLM 호출 거부(C1)와 로그인 시간 초과(C2)를 기능 점검에서 발견해 조사로 넘겼다.

* **담당자는 확인된 사실과 남은 작업을 한 보고서에서 파악하고 다음 담당자에게 넘길 수 있다.** 보고서에서 근거 원문, 배제한 가설, 확인하지 못한 범위, 조치와 재검증 방법을 함께 볼 수 있다. 최종 평가 12회에서 운영자가 직접 확인할 정보는 수작업 기준 73개에서 21개로 줄었다. 나머지 52개는 점검 결과나 보고서 근거로 확인할 수 있었다.

* **담당자는 보고서에서 확인된 내용과 추가로 확인할 내용을 구분할 수 있다.**

* **주기적으로 점검하면서도 조사 모델 사용량을 제한할 수 있다.** 정상 기준선 24회와 운영 정각 점검 27회에서 조사 모델을 호출하지 않았다. 규칙이 장애를 적발한 경우에도 규칙 진단 결과를 제공해 조사 모델 호출을 아낀다.

* **당번 운영자는 Slack에서 장애의 첫 확인 지점을 받아 후속 진단을 시작할 수 있다.** 최종 AI 조사 시나리오 3종에서 점검 시작부터 원인 요약 알림까지 평균 2분 50초가 걸렸다. 이 시간은 서비스가 대응에 필요한 정보를 전달하기까지의 평가 결과이며, 운영자의 수작업 진단 시간이나 실제 복구 시간은 실측하지 않았다.

### 3-2. 기술적 가치

* **점검과 AI 조사를 분리해 모델 응답을 기다리지 않고 장애를 알린다.** CronJob은 Kubernetes 규칙과 실제 기능 호출을 코드로 판정한다. 규칙에 걸린 장애는 진단 근거를 바로 제공하고, 규칙 신호 없이 기능이 실패하면 첫 알림을 보낸 뒤 조사 요청을 대기열에 넣는다. 조사 작업자가 대기열에서 요청을 처리한다.

* **조사 결과에서 결론이 나온 경로를 추적할 수 있다.** LangGraph는 호출 관계와 사전 확인 결과에서 출발해 가설을 세우고 도구로 검증한다. 보고서에는 호출 구간별 관찰과 근거 번호를 남긴다. 코드는 인용과 호출 체인을 검증하고, 확인이 빠진 경우 한 차례 더 조사한 뒤 판단 수준을 계산한다.

* **조사 권한과 실행 비용의 상한을 코드에서 통제한다.** 에이전트는 조회 전용 도구를 쓰며, 도구 실행 계층이 조회 대상 네임스페이스, 호출 수, 시간을 제한한다. 도구 응답의 비밀값을 마스킹한 뒤 근거로 저장한다.

* **한 번 수집한 운영 기록을 알림, 보고서, 이력 질의 채팅에서 재사용한다.** 점검·이슈·조사 보고서와 근거를 SQLite에 연결해 저장한다. Slack 알림은 해당 보고서로 연결되고, 이력 질의 채팅은 저장된 기록을 검색해 근거를 인용한다. 같은 대화 ID로 저장된 사용자 질문과 에이전트 답변 중 최근 메시지 최대 10개를 불러와 후속 답변에 사용한다. 조사 단계도 저장해 결과를 검토하거나 평가 실행과 대조할 수 있다.

## 4. 운영 및 보안 고려 사항

* **인증 방식**: 보고서 화면에는 인증이 없고 Ingress도 없다. 클러스터에 port-forward할 권한이 곧 화면 접근 권한이다. LLM 키와 Slack 토큰, 기능 점검용 테스트 계정은 Kubernetes Secret으로 주입한다.

* **권한 통제**: 조사용 ServiceAccount는 dev 네임스페이스의 get, list, watch만 허용하고, 클러스터 수준은 노드 조회 하나뿐이다. 생성, 수정, 삭제 권한이 없고 화면에서 클러스터를 바꿀 수도 없다. 컨테이너는 비root, 읽기 전용 파일시스템, 모든 capability 제거로 돌린다. 남은 위험은 Secret 값도 읽을 수 있는 권한 구조이고, 앱이 값을 즉시 버려 막는다.

* **Injection 대응**: 도구 결과를 태그로 감싸 데이터로만 전달하고 결과 안의 꺾쇠 기호를 이스케이프해 감싸기를 닫지 못하게 한다. 근거 번호는 검증기가 걸러 지어낸 인용을 남기지 않고, 비밀값은 모든 출력 경로에서 마스킹한다. 단위 테스트로 확인했고 실제 악성 지시문으로 공격 평가를 하지는 않았다.

* **장애 대응**: 수집에 실패하면 "확인하지 못함"으로 표시하고, 조사가 상한에 닿으면 "조사 미완", LLM 오류면 "조사 실패"를 알린다. 마지막 점검이 주기의 3배(3시간)보다 오래되면 점검 중단 알림을 한 번 보낸다. 점검은 동시에 1건만 돌고 조사 요청은 10분 안에 끝나지 않으면 다시 집는다.

* **운영 한계**: 데이터는 SQLite 파일 하나와 단일 노드용 PVC에 저장하고, 프로젝트 하나만 지원하며, 스키마가 바뀌면 DB를 지우고 다시 만든다. Slack 담당자 멘션은 구현되었으나 운영 설정에 담당자가 없어 실제 발송은 확인하지 못했다.

## 5. 회고 및 향후 확장

### 기술적 한계

* **하위 의존성이 끊긴 구간을 특정하기 어려웠다.** C2의 최종 TCP readiness 평가 3회에서 admin의 HTTP 무응답까지 확인했으나 admin에서 Redis로 연결이 차단됐다는 근거는 확보하지 못했다. admin 로그에는 Redis 오류가 나타나지 않았고, 현재 조사 도구는 admin Pod에서 출발하는 Redis 연결을 관측하지 못한다.

* **오류를 처음 발생시킨 리소스를 안정적으로 특정하지 못했다.** C1의 최종 평가 3회에서 agent가 llm-gateway 호출 중 받은 429는 확인했지만, 해당 요청에서 429가 처음 생성된 지점은 특정하지 못했다.

* **장애 위치를 확인한 근거만으로도 결론에 확정 라벨이 붙을 수 있다.** 확정으로 표시된 보고서 중 오확정 비율은 초기 기준선의 27%(4/15건)에서 전체 재평가의 21%(3/14건)로 줄었다. 최종 C2 보고서 세 건은 Redis 차단을 규명하지 못했지만, TCP 준비 상태 검사나 admin의 무응답에 관한 가설이 판정 조건을 충족해 모두 확정으로 표시됐다.

* **조사 부담은 시나리오에 따라 차이가 났다.** 경로 B 전체 중앙값은 183.8초·208,385토큰으로 목표 이내였지만, C1의 토큰 중앙값은 287,950개로 25만 개를 넘었고 C2의 시간 중앙값은 209.7초로 200초를 넘었다.

### Next Step

* **실패 구간과 원인 리소스를 구분할 근거를 보강한다.** C1은 요청 식별자로 agent와 llm-gateway의 로그를 대조해 429가 처음 발생한 구간을 좁힌다. C2는 애플리케이션의 의존성 상태와 호출 기록을 조회해 Redis 자체 상태와 admin에서 Redis로 가는 연결을 구분한다.

* **원인까지 증명할 때만 확정하도록 판단 조건을 고친다.** 보고서에서 확인된 장애 위치와 근본 원인 가설을 구분하고, 1순위 원인 가설에 직접 연결된 근거를 요구한다. 하위 호출이 미확인인 경우 후보로 표시하고 운영자가 이어서 확인할 대상을 제공한다.

* **조사 시간과 토큰이 많이 드는 경로부터 줄인다.** C1은 호출 구간과 관련된 로그만 다음 모델 호출에 전달하고, C2는 독립적인 상태 조회를 병렬화할 수 있는 범위를 확인한다. 같은 조건에서 원인 정확도·오확정률과 함께 시간·토큰을 다시 잰다.

* **정상 설정과 변경 이력을 연결해 조사 범위를 넓힌다.** 서비스별 정상 설정을 저장하고 배포·설정 변경 시각을 장애와 대조한다. 설정값 비교는 클러스터 안에서 수행하고 비교 결과를 조사 근거로 사용한다.

* **이력 질의 채팅과 대응 흐름을 확장한다.** 표현이 달라도 유사 장애와 당시 근거를 찾을 수 있게 의미 기반 검색을 더한다. 보고서의 조치는 운영자가 검토하고 승인한 뒤 실행할 수 있도록 조사와 조치의 권한을 분리한다.
