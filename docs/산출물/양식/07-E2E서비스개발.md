## 1. 최종 아키텍처 요약

* **완성된 아키텍처 핵심:** Kubernetes CronJob이 매시 정각에 점검하고 새 이슈를 알린다. 정기 점검이나 화면의 직접 점검에서 규칙 신호 없이 기능이 실패하면 조사 서버(diagnostic-agent)의 작업자(worker)가 LangGraph 에이전트를 실행한다. CLI의 `kg investigate`는 규칙 신호가 없으면 입력한 증상으로 직접 조사한다. 규칙이 장애를 적발한 경우는 LLM 없이 규칙 기반 진단 결과(위치, 규칙, 심각도, 근거, 확인할 사항)로 끝난다. 진단 대상은 minikube의 dev 네임스페이스(앱 6개와 PostgreSQL, Redis)다. 점검은 규칙 14개(장애 신호 12개, 개선 권고 2개)를 LLM 없이 코드로 판정하고, 로그인 후 채팅을 실제로 호출하는 기능 점검을 더해 Pod는 정상인데 서비스가 안 되는 증상을 잡는다. 규칙 신호도 기능 실패도 없으면 LLM을 호출하지 않는다.

* **최종 산출물 형태:** Slack 알림 앱(알림 전용, 긴급 알림에는 확인 버튼), 보고서 화면(FastAPI, Jinja2, HTMX로 만든 점검 이력, 이슈, 점검 구성, 지금 점검, 근거 원문, 이력 질의 패널), CLI(kg check, kg investigate, kg ask). 화면은 인증 없이 port-forward로만 접근하는 PoC다.

* **Agent 구조:** 요청은 다음 순서로 흐른다.

  1. CronJob이 Kubernetes API를 조회 전용으로 수집해 규칙 14개를 판정하고 기능 점검을 실행한다. 수집에 실패한 항목은 통과가 아니라 "확인하지 못함"으로 남긴다.
  2. 게이트가 조사를 시작할지 정한다. 장애 신호가 있으면 "조사 안 함 — 규칙 기반 진단 결과", 새 기능 실패에 조사 요청을 만들면 "조사 시작 — 기능 점검 실패", 장애 신호가 없으면 "조사 안 함 — 장애 신호 없음"이다.
  3. 정기 점검이나 화면의 직접 점검에서 새 이슈가 열리면 Slack에 1차 알림을 먼저 보내고, 규칙 신호 없는 기능 실패(경로 B)만 조사 요청을 대기열에 넣는다. 규칙 감지(경로 A)는 규칙 결과를 담아 알림을 끝낸다. 같은 문제는 이슈 지문으로 알아보고 다시 조사하지 않는다.
  4. 조사 작업자가 대기열에서 조사를 집어 읽기 전용 도구 7종으로 사실을 모으고 가설을 검증한다. 끝나면 근거 검증기와 빈틈 검사를 거친 보고서를 저장하고, 코드가 판단 수준(확정, 후보, 추정)을 정한다.
  5. 1차 알림을 원인, 판단 수준, 조치로 갱신하고 스레드에 답글을 단다. 다음 점검에서 문제가 사라지면 이슈를 닫고 복구 알림을 한 번 보낸다.

  외부 통신은 Azure OpenAI와 Slack API뿐이다. 조사 단계는 Arize Phoenix로 추적하고, 점검 결과와 보고서와 근거는 SQLite에 저장한다.

## 3. 창출된 핵심 가치

### 3-1. 비즈니스 가치

* 규칙만으로는 정상으로 보이던 장애를 기능 점검과 AI 조사로 다룬다. 규칙만 쓴 조건에서는 C1(LLM 호출 거부)과 C2(admin과 Redis 사이 차단)가 정상으로 판정되었다(10/21). 기능 점검을 더한 뒤에는 조사 대상이 되었다(10/23). Kubernetes에 흔적이 남는 장애(A1, A3, A5)는 w4-final, w4-hardening-m4, w4-cause-chain-146, w4-retest의 조사 26회에서 모두 원인을 맞혔고 모두 확정으로 판정되었다. C1은 일부만 맞혔고, C2는 원인 서비스 admin까지는 맞혔지만 Redis 연결 차단은 현재 도구로 확인하지 못했다.

* 모든 판단에 근거 원문이 붙은 보고서를 낸다. 보고서의 사실 문장은 저장된 근거 번호를 인용하고, 근거 일치율이 0.93에서 1.00이었다. 배제한 가설과 확인한 범위, 조치, 재검증 방법도 한 보고서에 담긴다.

* 틀린 답을 확정으로 내보내는 일을 줄이려 판단 규칙을 바꿨다. 규칙 변경 전 w4-final(11/02)의 오확정률은 27%(확정 15건 중 4건)였고, 같은 구성으로 다시 잰 w4-retest(11/03)는 21%(14건 중 3건, 모두 C2)다. 0은 아니다. 저장된 보고서 8건을 다시 판정한 보조 확인에서는 오확정이 5건에서 1건으로 줄었다.

* 정상일 때 조사 비용이 들지 않는다. 정상 기준선 24회와 정각 점검 27회에서 조사가 한 번도 돌지 않았다. 11월 9일부터는 규칙이 적발한 장애에도 조사 LLM을 부르지 않는다. 줄어든 비용은 측정하지 않았다.

* 사람이 직접 진단하는 시간은 일부러 측정하지 않았으므로 시간 단축 폭은 수치로 주장하지 않는다. AI 조사 자체의 시간은 배치별 중앙값으로 89초에서 167초였다.

### 3-2. 기술적 가치

* 읽기만 하는 조사 에이전트의 안전 구조를 만들었다. 도구가 모두 조회 전용이고, 네임스페이스 범위와 호출 수와 시간 상한을 프롬프트가 아니라 코드가 강제하며, 모든 결과를 마스킹해 저장한다.

* 확신도 대신 코드가 판단 수준을 정한다. 원인 리소스의 설정을 직접 인용했는지, 근거 출처가 몇 종인지를 보고 확정, 후보, 추정을 계산한다.

* 정답과 비교하는 자동 평가 체계를 구축했다. 정답 파일, 네 가지 채점, 실패 원인 분류, 장애 주입과 원복을 자동으로 도는 평가 러너를 만들었고, 전체 테스트 1,892개가 통과한다(11/09).

* 보강 전후를 같은 지표로 비교해 좋아진 것과 아닌 것을 가렸다. B1은 0/3에서 3/3이 되었고 C1과 C2는 개선하지 못했으며 비용은 늘었다.

## 4. 운영 및 보안 고려 사항

* 인증 방식: 보고서 화면에는 인증이 없고 Ingress도 없다. 클러스터에 port-forward할 권한이 곧 화면 접근 권한이다. LLM 키와 Slack 토큰, 기능 점검용 테스트 계정은 Kubernetes Secret으로 주입한다.

* 권한 통제: 조사용 ServiceAccount는 dev 네임스페이스의 get, list, watch만 허용하고, 클러스터 수준은 노드 조회 하나뿐이다. 생성, 수정, 삭제 권한이 없고 화면에서 클러스터를 바꿀 수도 없다. 컨테이너는 비root, 읽기 전용 파일시스템, 모든 capability 제거로 돌린다. 남은 위험은 Secret 값도 읽을 수 있는 권한 구조이고, 앱이 값을 즉시 버려 막는다.

* Injection 대응: 도구 결과를 태그로 감싸 데이터로만 전달하고 결과 안의 꺾쇠 기호를 이스케이프해 감싸기를 닫지 못하게 한다. 근거 번호는 검증기가 걸러 지어낸 인용을 남기지 않고, 비밀값은 모든 출력 경로에서 마스킹한다. 단위 테스트로 확인했고 실제 악성 지시문으로 공격 평가를 하지는 않았다.

* 장애 대응: 수집에 실패하면 "확인하지 못함"으로 표시하고, 조사가 상한에 닿으면 "조사 미완", LLM 오류면 "조사 실패"를 알린다. 마지막 점검이 주기의 3배(3시간)보다 오래되면 점검 중단 알림을 한 번 보낸다. 점검은 동시에 1건만 돌고 조사 요청은 10분 안에 끝나지 않으면 다시 집는다.

* 운영 한계: 데이터는 SQLite 파일 하나와 단일 노드용 PVC에 저장하고, 프로젝트 하나만 지원하며, 스키마가 바뀌면 DB를 지우고 다시 만든다. Slack 담당자 멘션은 구현되었으나 운영 설정에 담당자가 없어 실제 발송은 확인하지 못했다.

## 5. 회고 및 향후 확장

### 기술적 한계

* C2(admin과 Redis 사이 차단)는 도구 한계로 매번 실패한다. admin 로그에 오류가 남지 않고 현재 도구로는 Redis 연결 차단을 확인할 수 없다. 원인 리소스 admin은 맞히지만 일부 회차는 확정으로 나와 오확정이 되었다. 출발 Pod 안에서 명령을 실행해야 하는데 조회 전용 원칙과 충돌해 택하지 않았다.

* C1은 배치마다 0/3에서 2/3 사이로 흔들린다. 호출한 쪽과 호출 받은 쪽 중 어디가 원인인지 구분하는 문제를 해결했다고 말할 수 없다. 호출 체인 검증은 미해결을 후보로 남기는 장치이고 정확도 개선을 입증하지 못했다.

* 판단 수준이 아직 완전하지 않다. 무관한 가설이 지지로 판정되어도 확정을 허용할 수 있고, 확정이 근본 원인이 아니라 즉시 실패한 위치에 대한 판단일 수 있다.

* 규칙이 확정한 장애는 AI 없이 규칙 기반 진단 결과로 끝난다(이슈 #185, 11/09 구현). 이 결과는 위치와 사실만 보이며 근본 원인과 영향 범위는 확인하지 않는다. 이전 평가의 AI 수치와는 분모가 다르다.

* 조사 비용이 보강 뒤 커졌다. 대화를 압축하지 않고 쌓아서 도구를 부를 때마다 입력 토큰이 커진다.

* 계획한 비교 실험을 하지 않았다. 직접 구현한 루프나 deepagents와의 구조 비교, 지침 전체 주입과 선택 주입 비교, 함수 호출과 MCP 비교, 모델 조합 비교, 사람 채점과 모델 채점 비교를 하지 않았고, 효과 비교는 규칙만 쓴 조건 대비와 보강 전후에 그쳤다.

* 감지 시간과 원인 파악 시간을 주입 시각 기준으로 측정하지 못했고, 4시간 연속 오탐 확인과 확인 항목 감소율도 하지 못했다. 평가 표본도 작아서 시나리오당 장애 주입 1회에 조사 3회다.

* 실제 프롬프트 인젝션 공격 평가를 하지 않았다. 점검 주기가 1시간이라 지속 시간 규칙은 사실상 다음 정시 점검에서 적발된다.
