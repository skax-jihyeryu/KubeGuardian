# 2. 문제 정의 및 서비스 기획

### 프로젝트 명

**KubeGuardian AI** — AI 기반 Kubernetes 서비스 환경 진단 Agent

### 배경 및 문제 정의

* 현재 상황 (As-Is): 우리 팀은 앱 6개(front-chat, front-admin, gateway, agent, admin, llm-gateway)로 구성된 AI 서비스 템플릿을 만들어 쓰고 있고, SK Inc. PR 보도자료 서비스도 여기서 출발해 Kubernetes에서 운영 중이다. 장애가 나면 사용자 문의가 와야 알게 되고, 운영자가 kubectl로 앱마다 하나씩 수작업으로 원인을 찾는다. 장애 발생부터 원인 파악까지 약 3~5일(경험 기반 추정)이 걸린다.

* 일반화: MSA 구조에서는 서비스 하나가 여러 레포·Pod·공유 설정·DB로 나뉘어, 한 곳의 문제가 호출 경로를 타고 다른 곳의 증상으로 나타난다. Kubernetes 위에서 이 구조를 운영하는 팀이라면 같은 어려움을 겪는다.

* Pain Point:
  * 보이지 않음 — Pod는 모두 Running·Ready인데 서비스가 안 된다
  * 멀리 있음 — 증상(gateway 502)과 원인(llm-gateway 할당량 소진, Redis 연결 차단)이 다른 서비스에 있다
  * 너무 많음 — 경고·이벤트·재시작 기록 대부분이 지금 장애와 무관해, 무엇이 중요한지 고르는 일이 숙련자에게 의존한다
  * 시간 — 사용자가 문의해야 장애를 알게 되고 원인 파악에도 오래 걸린다(약 3~5일, 추정). PR 업무는 시간에 민감해 서비스 중단이 곧 업무 중단이다

* 기회 요인: 조건이 명확한 오류(Endpoint가 비어 있음, 포트 불일치, 이미지 받기 실패)는 규칙 코드로 확정하고, 여러 신호를 연결하고 증상에서 원인을 거슬러 올라가는 일은 LLM 에이전트의 추론 + 도구 호출로 자동화할 수 있다. 정상일 때 LLM을 부르지 않는 룰 + LLM 구조는 BeingAX 뉴스 판정에서 비용·일관성 효과를 이미 확인했다.

### 목표 사용자 (Target User)

* 주 사용자: **템플릿 기반 AI 서비스의 개발·운영 담당자** — 서비스 개발·배포와 운영을 함께 맡으며, Kubernetes 배포는 할 줄 알지만 장애 원인 분석 경험은 많지 않다. Slack으로 이상 알림을 받고 보고서 화면에서 원인을 확인하며, 배포 직후 점검과 증상 조사를 Slack 명령으로 맡긴다.
* 보조 사용자: **장애 1차 대응 담당자** — Slack 알림의 심각도와 "지금 중요한 것" 요약으로 무엇부터 볼지 판단한다.

### 프로젝트 목표

* 정성적 목표

  * 목표 1: 반복 진단 업무 자동화 — kubectl로 하던 확인(상태·이벤트·로그·호출 경로·API 호출)을 5분마다 자동으로 수행하고, 이상이 있을 때만 Slack으로 알린다

  * 목표 2: 의사결정 지원 — 수십 개 신호 중 "지금 중요한 것"을 골라, 원인·근거·조치·재검증 방법을 담은 보고서 하나로 판단이 끝나게 한다

  * 목표 3: AI 기술 내재화 — 원인을 아는 장애를 주입해 정답과 비교하는 정량 평가 체계를 구축하고, 에이전트 기술을 같은 지표로 비교한다

* 정량적 목표 (KPI) — 비교 기준은 현재 방식(사용자 문의 후 사람이 수작업 진단, 약 3~5일 추정)이며, 같은 장애 시나리오를 "규칙 점검만" 조건과 "규칙 점검 + AI 조사" 조건으로 실행해 보완한다. 현재 수준은 경험 기반 추정치이다.

* 현재 수준과 개선 폭은 경험 기반 추정치이며 W4 평가에서 측정값으로 교체한다. 사람의 정확도(약 69%)는 시나리오를 "K8s 상태로 원인이 보이나"로 나눈 판단 기반 추정이다.

* 정확도 평가 기준: 사람 기준(사람이 정한 정답 원인과 보고서 1순위 원인의 일치)을 주 지표로 쓰고, AI 기준(LLM 채점)은 비교 실험에서 사람 기준과의 일치도를 확인한 뒤 보조로 쓴다. 효과의 기준선은 항상 현재 방식이다. 사람은 시간만 있으면 원인을 대부분 찾으므로 시간 제한 없는 정확도는 사람과 비슷한 수준을 유지하고, 7분 이내 정확도에서 차이를 만든다(주장하는 가치는 정확도 우위가 아니라 시간 단축).

### 핵심 기능 정의

1. 주기 점검과 이상 감지: 5분마다(Kubernetes CronJob) Kubernetes API(Python 클라이언트)로 리소스를 조회 전용으로 수집해 명확한 오류를 규칙 약 10종으로 확정하고, 로그인 → 채팅 API를 실제로 호출해 "K8s는 정상인데 서비스가 안 되는" 증상을 잡는다. 둘 다 정상이면 LLM을 호출하지 않는다.

2. AI 조사·검증 에이전트: 이상이 있으면 가설 없이 확인할 사실(Pod 상태, Endpoint 연결, 이벤트, API 호출 결과)을 먼저 확인한 뒤, 중요한 문제를 사용자 영향 순으로 고르고 원인 가설(최대 3개)을 읽기 전용 도구 7종으로 검증해 지지 / 배제 / 판단 보류로 판정한다. 모든 사실 문장에 수집 데이터(근거)를 붙이고, 배제한 가설의 이유·확인한 범위·구체적인 조치·재검증 방법까지 담은 보고서를 쓴다.

3. 심각도별 Slack 알림과 보고서 화면: 점검 → 이상 판정 → 알림 → 인지·확인 → 조치 → 복구를 단계로 나눈다. 이상을 판정하면 AI 조사를 기다리지 않고 1차 감지 알림(심각도, 실패한 기능, 원인 조사 중)을 먼저 보내고, 조사가 끝나면 같은 알림을 원인·조치·보고서 링크로 갱신한다. 조사가 실패해도 1차 알림은 이미 나간 상태다. 같은 문제는 AI를 다시 호출하지 않고 심각도별 리마인더(긴급: 30분 후 첫 리마인더, 이후 2시간마다 총 3회)만 보내며, 해결되면 복구 알림을 한 번 보낸다. 전체 보고서·근거 원문·점검 이력은 읽기 전용 보고서 화면에서 본다. 운영자는 Slack에서 `/kg check`(즉시 점검), `/kg investigate 증상`(증상 조사)으로 직접 맡길 수도 있다.

### 설계 판단

* 주기 실행은 Kubernetes CronJob, Kubernetes 접근은 Python 클라이언트(API)로 하고 kubectl CLI 호출은 쓰지 않는다. Prometheus는 대상 장애가 상태·선언 기반이고 시간 의존 장애가 범위 밖이며 자원·시간 제약이 있어 도입하지 않는다.
* 알림 대상은 기존 운영 채널 또는 DM에서 시작하고, 알림량이 늘면 전용 채널을 만든다. 평가 중에는 Slack 전송 없이 알림 이력에 기록한다.
* 예상하지 못한 상황은 수집 실패 시 "확인하지 못함"으로 표시, AI 실패 시 규칙 결과만으로 "조사 미완" 알림, 점검기 중단 시 "점검 중단" 알림으로 처리한다.

### 기대 효과

* 업무 효율화: 사용자 문의 전, 장애 발생 6분 안에 감지 알림, 7분 안에 원인을 받고(현재 약 3~5일, 추정 → 약 99.8% 이상 단축), 사람이 직접 확인할 항목을 90% 이상 줄임 (예: 47개 → 중요 문제 2건)

* 품질 향상: K8s 상태로는 원인이 보이지 않는 장애에서 원인 규명 60% 이상, 모든 판단에 근거 원문이 연결된 검증 가능한 진단

* 비용 절감: 숙련자에게 집중되던 원인 분석을 서비스 담당자가 1차로 수행, 정상일 때 LLM 비용 0 · 조사 1회 10만 토큰 이하

### 범위 및 제약사항

* In Scope: 템플릿 앱 6개 + PostgreSQL·Redis(minikube, 단일 네임스페이스) 진단(로그인 → 채팅 핵심 경로 기준), 5분 주기 점검, 규칙 약 10종, API 호출 증상 감지, AI 조사·검증 에이전트와 보고서, 심각도별 Slack 알림·명령, 보고서 화면(홈=점검 이력, 점검 상세(보고서·조사 과정·근거), 이슈, 점검 구성, 이력 질의 채팅), 장애 시나리오 8개 + 정상 환경 평가, 에이전트 기술 비교 실험(일정 여유에 따라)

* Out of Scope: 조치 에이전트(보고서의 조치를 실행 — 다음 단계 과제), 클러스터를 조회하는 후속 질문(저장된 이력 질의 채팅은 범위 안), 배포 전후 변경 검증, 상태 대시보드(실시간 리소스·로그 조회), 보고서 메일 발송·알림 확인(ack) 기능, 부하·시간 의존 장애, Prometheus 등 별도 관측 스택, 실제 운영 클러스터 적용, 범용 애드온 배포

* 제약사항: 1인 · 8주 · 주 10~15시간, 로컬 minikube(CPU 4·메모리 10GB), Azure OpenAI만 사용(사내 SSL CA 주입 필요), 에이전트는 조회 권한만, Slack 앱 생성 승인과 사내망 통신 허용 필요(전용 채널 개설은 필수 아님), 과거 장애의 진단 시간 기록이 없어 현재 수준은 경험 기반 추정치로 표기하고 규칙만 쓴 조건 대비 측정값으로 보완
