# 2. 문제 정의 및 서비스 기획

> 문제 배경, 평가 기준, 알림 정책의 세부는 [상세본](../02-문제정의및서비스기획.md)에 있다.

### 프로젝트 명

KubeGuardian AI. AI 기반 Kubernetes 서비스 환경 진단 Agent

### 배경 및 문제 정의

* 현재 상황 (As-Is): 우리 팀은 앱 6개(front-chat, front-admin, gateway, agent, admin, llm-gateway)로 구성된 AI 서비스 템플릿을 만들어 쓰고 있고, SK Inc. PR 보도자료 서비스도 여기서 출발해 Kubernetes에서 운영 중이다. 장애가 나면 사용자 문의가 와야 알게 되고, 운영자가 kubectl로 앱마다 하나씩 수작업으로 원인을 찾는다. 장애 발생부터 원인 파악까지 약 3~5일(경험 기반 추정)이 걸린다.

* 일반화: MSA 구조에서는 서비스 하나가 여러 레포, Pod, 공유 설정, DB로 나뉘어 한 곳의 문제가 호출 경로를 타고 다른 곳의 증상으로 나타난다. Kubernetes 위에서 이 구조를 운영하는 팀이라면 같은 어려움을 겪는다.

* Pain Point:
  * 보이지 않음: Pod는 모두 Running과 Ready인데 서비스가 안 된다.
  * 멀리 있음: 증상은 gateway의 오류로 보이는데 원인은 llm-gateway의 LLM 호출 실패나 admin과 Redis 사이의 연결 차단처럼 다른 서비스에 있다.
  * 너무 많음: 경고, 이벤트, 재시작 기록 대부분이 지금 장애와 무관해서, 무엇이 중요한지 고르는 일이 숙련자에게 의존한다.
  * 시간: 사용자가 문의해야 장애를 알게 되고 원인 파악에도 오래 걸린다(약 3~5일, 추정). PR 업무는 시간에 민감해서 서비스 중단이 곧 업무 중단이다.

* 기회 요인: 조건이 명확한 오류(Endpoint가 비어 있음, 포트 불일치, 이미지 받기 실패)는 규칙 코드로 확정하고, 여러 신호를 연결하고 증상에서 원인을 거슬러 올라가는 일은 LLM 에이전트의 추론과 도구 호출로 자동화할 수 있다. 정상일 때 LLM을 부르지 않는 규칙과 LLM 결합 구조는 BeingAX 뉴스 판정에서 비용과 일관성 효과를 이미 확인했다.

### 목표 사용자 (Target User)

* 주 사용자: 템플릿 기반 AI 서비스의 개발과 운영 담당자. 서비스 개발, 배포, 운영을 함께 맡으며 Kubernetes 배포는 할 줄 알지만 장애 원인 분석 경험은 많지 않다. Slack으로 이상 알림을 받고 보고서 화면에서 원인을 확인한다. 배포 직후에는 화면의 지금 점검 버튼이나 CLI로 점검하고, 자동 점검이 못 잡는 증상은 CLI의 증상 조사로 맡긴다.
* 보조 사용자: 장애 1차 대응 담당자. Slack 알림의 심각도와 판단 수준, 원인 요약으로 무엇부터 볼지 판단한다.

### 프로젝트 목표

* 정성적 목표

  * 목표 1, 반복 진단 업무 자동화: kubectl로 하던 확인(상태, 이벤트, 로그, 호출 경로, API 호출)을 매시 정각에 자동으로 수행하고, 이상이 있을 때만 Slack으로 알린다.

  * 목표 2, 의사결정 지원: 수십 개 신호 중 지금 중요한 것을 골라, 원인, 근거, 조치, 재검증 방법을 담은 보고서 하나로 판단이 끝나게 한다.

  * 목표 3, AI 기술 내재화: 원인을 아는 장애를 주입해 정답과 비교하는 정량 평가 체계를 구축하고, 조사 에이전트의 보강 전후를 같은 지표로 비교한다.

* 정량적 목표 (KPI): 비교 기준은 현재 방식(사용자 문의 후 사람이 수작업으로 진단, 약 3~5일 추정)이며, 같은 장애 시나리오를 규칙 점검만 쓰는 조건과 규칙 점검에 AI 조사를 더한 조건으로 실행해 보완한다. 후 칸의 목표는 기획 시점의 값이다. 점검 주기 변경 등으로 그대로는 성립하지 않게 된 항목에만 변경 후 기준을 덧붙였고, 변경 후 기준은 11월 9일 산출물 정리 때 정한 참고 값이다. 실제 측정 결과는 07 산출물에서 다룬다.

### 목표와 측정 방법 변경 내역

* 장애 감지 시간: 6분 이내에서 점검 시작 기준 1분 이내로 보았다. 점검 주기가 5분에서 1시간으로 바뀌어(11월 2일) 장애 발생 기준 6분이 성립하지 않기 때문이다.
* 원인 파악 시간과 7분 이내 정확도: 7분에서 점검 시작 기준 5분으로 보았다. 같은 이유(11월 2일)이고, 5분은 점검 약 1분, 조사 상한 150초, 재조사 연장 60초를 합친 값이다.
* 조사 비용: 10만 토큰에서 20만 토큰으로 바꿨다. 도구를 부를 때마다 대화가 누적되는 점을 처음 값이 빠뜨렸고, 첫 실측이 약 13.5만 토큰이었다(10월 23일).
* 원인 규명 커버리지 대상: 4개에서 2개로 줄었다. C5와 E1을 만들지 않았다.
* 정확도와 근거 일치율의 평가 주체: 사람 판정에서 코드 대조와 모델 채점으로 바꿨다. 자동 채점을 구현했고 사람 라벨은 모으지 못해 보정은 하지 않았다.
* 잘못된 알림: 48회 연속 점검은 1시간 주기로는 약 2일이라 하지 못하고 H0, H1 회차 기록으로 대신했다.
* 확인 항목 감소율: 계산 기능을 구현하지 못했다.
* 감지 시간과 원인 파악 시간은 원래 기준이든 변경 기준이든 정식으로 측정하지 못했다(이슈 #30, 결과는 07 산출물).

* 현재 수준과 개선 폭은 경험 기반 추정치다. 사람의 정확도(약 69%)는 계획 시점 시나리오 8개를 K8s 상태로 원인이 보이는지로 나눈 판단 기반 추정이고 최종 시나리오 구성과 달라서 비교 값으로 쓰지 않는다. 효과의 기준선은 규칙 점검만 쓴 조건의 측정값이다.

* 정확도 평가 기준: 시나리오마다 정답 원인을 미리 정해 두고, 보고서 1순위 원인 리소스를 정답과 코드로 대조한 뒤 결론 문장 일치를 조사와 다른 모델(gpt-4.1)이 채점한다. 사람은 시간만 있으면 원인을 대부분 찾으므로 주장하는 가치는 정확도 우위가 아니라 시간 단축이다. 목표별 근거와 채점 방식은 [상세본](../02-문제정의및서비스기획.md)에 있다. 결과는 07 산출물에서 다룬다.

### 핵심 기능 정의

1. 주기 점검과 이상 감지: 매시 정각에 Kubernetes CronJob이 점검한다. Kubernetes API(Python 클라이언트)로 리소스를 조회 전용으로 수집해 명확한 오류를 규칙 14개(장애 신호 12개, 개선 권고 2개)로 판정하고, 로그인 후 채팅 API를 실제로 호출하는 기능 점검으로 K8s는 정상인데 서비스가 안 되는 증상을 잡는다. 규칙 신호도 기능 실패도 없으면 LLM을 호출하지 않는다. 직접 점검은 보고서 화면의 지금 점검 버튼과 CLI(kg check)로 하고, 증상을 적어 조사를 시키는 것은 CLI(kg investigate)로 한다.

2. AI 조사와 검증 에이전트: 이상이 있으면 항상 떠 있는 조사 서버(diagnostic-agent)의 조사 작업자(worker)가 조사한다. 가설 없이 확인할 사실을 먼저 모으고, 중요한 문제를 사용자 영향 순으로 최대 3건 고르고, 원인 가설(문제당 최대 3개)을 읽기 전용 도구 7종으로 검증한다. 모든 사실 문장에 수집 데이터를 근거로 붙이고, 배제한 가설의 이유, 확인한 범위, 조치, 재검증 방법까지 보고서에 담는다. 결론의 판단 수준(확정, 후보, 추정)은 LLM의 자기 평가가 아니라 저장된 근거를 보고 코드가 정한다.

3. Slack 알림, 보고서 화면, 이력 질의: Slack은 알림 전용이고 슬래시 명령은 없다. 이상을 판정하면 AI 조사를 기다리지 않고 1차 알림을 먼저 보내고, 조사가 끝나면 같은 메시지를 원인, 판단 수준, 조치로 갱신하고 스레드에 답글을 단다. 긴급 알림에는 확인 버튼이 있고 설정하면 담당자를 멘션한다. 같은 문제는 AI를 다시 부르지 않고 심각도별 리마인더만 보내며(정책은 상세본), 해결되면 복구 알림을 한 번 보낸다. 전체 보고서, 근거 원문, 점검 이력은 보고서 화면에서 보고, 화면의 이력 질의 패널에서는 저장된 점검, 이슈, 보고서, 알림 이력만 읽어 답한다.

### 설계 판단

* 주기 실행은 Kubernetes CronJob, 접근은 Python 클라이언트(API)로 하고 kubectl CLI 호출은 쓰지 않는다. CronJob은 점검만 하고, 조사는 항상 떠 있는 diagnostic-agent의 worker가 한다. 실행 시간 제한 안에 조사가 잘리지 않게 하기 위해서다. Prometheus는 대상 장애가 상태와 선언 기반이고 시간 의존 장애가 범위 밖이며 자원과 시간 제약이 있어 도입하지 않았다.
* 점검 주기는 운영자 인터뷰를 반영해 1시간으로 정했다. 지속 시간 규칙은 다음 정시 점검에서 적발된다.
* 알림은 Slack 전용으로 하고 명령 수신은 제외했다. 알림이 핵심 가치이고 명령은 화면과 CLI로 대신할 수 있기 때문이다. 평가 중에는 Slack 전송 없이 알림 이력에 기록한다.
* 예상하지 못한 상황은 수집 실패 시 확인하지 못함으로 표시하고, 조사가 상한에 닿으면 조사 미완, LLM 오류면 조사 실패로 알리고, 점검기가 멈추면 점검 중단 알림을 보낸다.

### 기대 효과

* 업무 효율화: 사용자 문의를 기다리지 않고 점검이 끝나는 대로 장애를 알림으로 받고 몇 분 안에 원인을 받는다(현재 약 3~5일, 추정). 다만 자동 점검은 매시 정각이라 장애가 점검 직후에 생기면 최대 약 1시간을 기다리므로, 바로 확인하려면 화면의 지금 점검이나 CLI로 직접 점검한다. 사람이 직접 확인할 항목을 크게 줄이는 것이 목표이나 감소율 계산은 구현하지 못했다.

* 품질 향상: K8s 상태로는 원인이 보이지 않는 장애에서 원인 규명을 목표로 하고, 모든 판단에 근거 원문이 연결된 검증 가능한 진단을 제공한다.

* 비용 절감: 숙련자에게 집중되던 원인 분석을 서비스 담당자가 1차로 수행한다. 정상일 때 조사용 LLM 비용은 0이고(근거 요약과 이력 질의는 별도로 LLM을 쓴다) 조사 1회는 20만 토큰 이하를 목표로 한다.

### 범위 및 제약사항

* In Scope: 템플릿 앱 6개와 PostgreSQL, Redis(minikube, 단일 네임스페이스) 진단, 매시 정각 점검, 규칙 14개, 기능 점검, AI 조사 에이전트와 보고서, 심각도별 Slack 알림, 읽기 중심 보고서 화면(점검 이력, 이슈, 점검 구성, 지금 점검, 근거 원문, 이력 질의 패널), 장애 시나리오와 정상 기준선 평가

* Out of Scope: 조치 에이전트(보고서의 조치를 실행하는 다음 단계 과제), 배포 전후 변경 검증, 상태 대시보드, 보고서 메일 발송, Slack 슬래시 명령, 의미 기반 이력 검색, 부하와 시간 의존 장애, Prometheus 등 별도 관측 스택, 실제 운영 클러스터 적용, 범용 애드온 배포, 에이전트 구조와 모델 비교 실험(계획했으나 하지 않음, 상세본 참고)

* 제약사항: 1인, 8주, 주 10~15시간, 로컬 minikube(CPU 4, 메모리 10GB), Azure OpenAI만 사용(사내 SSL CA 주입 필요), 에이전트는 조회 권한만, Slack 앱 생성 승인과 사내망 통신 허용 필요, 보고서 화면은 인증 없이 port-forward로만 접근하는 PoC, 과거 장애의 진단 시간 기록이 없어 현재 수준은 경험 기반 추정치로 표기하고 규칙만 쓴 조건 대비 측정값으로 보완
