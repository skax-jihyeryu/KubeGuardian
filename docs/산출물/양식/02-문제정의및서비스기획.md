# 2. 문제 정의 및 서비스 기획

### 프로젝트 명

KubeGuardian AI. AI 기반 Kubernetes 서비스 환경 진단 Agent

### 배경 및 문제 정의

* 현재 상황 (As-Is): 우리 팀은 앱 6개(front-chat, front-admin, gateway, agent, admin, llm-gateway)로 구성된 AI 서비스 템플릿을 만들어 쓰고 있고, SK Inc. PR 보도자료 서비스도 여기서 출발해 Kubernetes에서 운영 중이다. 장애가 나면 사용자 문의가 와야 알게 되고, 운영자가 kubectl로 앱마다 하나씩 수작업으로 원인을 찾는다. 장애 발생부터 원인 파악까지 약 3~5일(경험 기반 추정)이 걸린다. 이러한 MSA 구조에서는 서비스 하나가 여러 레포, Pod, 공유 설정, DB로 나뉘어 한 곳의 문제가 호출 경로를 타고 다른 곳의 증상으로 나타난다. Kubernetes 위에서 이 구조를 운영하는 팀이라면 같은 어려움을 겪는다.

* Pain Point:
  * 보이지 않음 — Pod는 모두 Running과 Ready인데 서비스가 안 된다.
  * 멀리 있음 — 증상(gateway 502)과 원인(llm-gateway 할당량 소진, Redis 연결 차단)이 다른 서비스에 있다
  * 너무 많음 — 경고, 이벤트, 재시작 기록 대부분이 지금 장애와 무관해서, 무엇이 중요한지 고르는 일이 숙련자에게 의존한다.
  * 시간 — 사용자가 문의해야 장애를 알게 되고 원인 파악에도 오래 걸린다(약 3~5일, 추정). PR 업무는 시간에 민감해서 서비스 중단이 곧 업무 중단이다.

* 기회 요인: 조건이 명확한 오류(Endpoint가 비어 있음, 포트 불일치, 이미지 받기 실패)는 규칙 코드로 확정하고, 여러 신호를 연결하고 증상에서 원인을 거슬러 올라가는 일은 LLM 에이전트의 추론과 도구 호출로 자동화할 수 있다. 규칙을 기반으로 먼저 작동해 LLM 토큰 사용을 절약하고, 문제가 있을 경우에는 LLM을 통해 빠른 원인 파악이 가능하다.

### 목표 사용자 (Target User)

* 주 사용자: 템플릿 기반 AI 서비스의 개발과 운영 담당자. 서비스 개발, 배포, 운영을 함께 맡으며 Kubernetes 배포는 할 줄 알지만 장애 원인 분석 경험은 많지 않다. Slack으로 이상 알림을 받고 보고서 화면에서 원인을 확인한다. 배포 직후에는 화면의 지금 점검 버튼이나 CLI로 점검하고, 자동 점검이 못 잡는 증상은 CLI의 증상 조사로 맡긴다.
* 보조 사용자: 장애 1차 대응 담당자. Slack 알림의 심각도와 판단 수준, 원인 요약으로 무엇부터 볼지 판단한다.

### 프로젝트 목표

* 정성적 목표

  * 목표 1, 반복 진단 업무 자동화: kubectl로 하던 확인(상태, 이벤트, 로그, 호출 경로, API 호출)을 매시 정각에 자동으로 수행하고, 이상이 있을 때만 Slack으로 알린다.

  * 목표 2, 의사결정 지원: 수십 개 신호 중 지금 중요한 것을 골라, 원인, 근거, 조치, 재검증 방법을 담은 보고서 하나로 판단이 끝나게 한다.

  * 목표 3, AI 기술 내재화: 원인을 아는 장애를 주입해 정답과 비교하는 정량 평가 체계를 구축하고, 조사 에이전트의 보강 전후를 같은 지표로 비교한다.

* 정량적 목표 (KPI): 비교 기준은 현재 방식(사용자 문의 후 사람이 수작업으로 진단, 약 3~5일 추정)이며, 같은 장애 시나리오를 규칙 점검만 쓰는 조건과 규칙 점검에 AI 조사를 더한 조건으로 실행해 보완한다.

| **성과 지표**           | **목표 수치**             | **측정 방법**                             | **현재 수준**                   |
| ------------------- | --------------------- | ------------------------------------- | --------------------------- |
| 원인 정확도              | 70% 이상                | 보고서가 원인 지점을 찾고 원인 서비스 또는 직접 연결된 서비스를 1순위로 지목한 비율 (시나리오당 3회 반복) | 사람 측정 기준 약 40%              |
| 장애 감지 시간 (원인 파악 포함) | 5분 이내 | 점검 시작 시각 → 조사 완료 알림(원인 요약이 담긴 Slack 알림) 발송 시각. 정각 점검까지의 대기는 제외 | 약 3~5일 (사용자 문의 대기 + 수작업 진단) |
| 확인 항목 감소율 | 시나리오별 감소율 평균 70% 이상 | 시나리오별로 `1 − (남은 직접 확인 항목 수 / 수작업 기준 항목 수)`를 계산한 뒤, 각 시나리오에 같은 비중을 두어 평균한다. | 0% (모든 항목을 사람이 확인) |
| AI 조사 시간·비용         | 중앙값 200초, 25만 토큰 이하 (입력+출력) | 평가 러너 자동 기록. 200초는 장애 감지 5분에서 점검·알림 여유 약 100초를 뺀 조사 예산이고, 25만 토큰은 도구 호출 상한(20회)까지 쓰는 조사를 허용하는 값이다 (11/11 확정) | 1시간~2시간                     |


최종 평가 후 목표를 조정했다. 운영자가 직접 확인해야 하는 정보의 비율을 시나리오 평균 30% 이하로 줄이는 기준이다.

장애 감지 시간은 점검이 시작된 시각부터 원인 요약이 담긴 조사 완료 알림이 Slack으로 발송된 시각까지 잰다. 현재 PoC는 매시 정각 점검을 실행하므로 정각까지의 대기와 운영 작업자 대기열은 측정 범위에서 제외했다.

### 핵심 기능 정의

1. **서비스 상태 점검** — 매시 정각 또는 운영자가 요청한 시점에 Kubernetes 리소스와 로그인·채팅 기능을 점검한다. 설정과 상태에서 확인한 이상은 규칙 기반 진단 결과로 보여 준다.
2. **근거 기반 AI 조사** — 규칙으로 확인할 이상이 없는데 기능이 실패하거나 운영자가 증상을 입력하면, 원인 후보를 검증해 근거와 조치 방법을 담은 보고서를 작성한다.
3. **알림과 이력 확인** — 점검에서 발견한 장애를 Slack으로 알리고, AI 조사가 끝나면 같은 알림에 결과를 덧붙인다. 운영자는 웹 화면에서 보고서와 근거를 열거나 저장된 점검·이슈 이력에 질문할 수 있다.

### 설계 판단

* 주기 실행은 Kubernetes CronJob, 접근은 Python 클라이언트(API)로 하고 kubectl CLI 호출은 쓰지 않는다. CronJob은 점검만 하고, 조사는 항상 떠 있는 diagnostic-agent의 worker가 한다. 실행 시간 제한 안에 조사가 잘리지 않게 하기 위해서다. Prometheus는 대상 장애가 상태와 선언 기반이고 시간 의존 장애가 범위 밖이며 자원과 시간 제약이 있어 도입하지 않았다.
* 점검 주기는 운영자 인터뷰를 반영해 1시간으로 정했다. 지속 시간 규칙은 다음 정시 점검에서 적발된다.
* 알림은 Slack 전용으로 하고 명령 수신은 제외했다. 알림이 핵심 가치이고 명령은 화면과 CLI로 대신할 수 있기 때문이다. 평가 중에는 Slack 전송 없이 알림 이력에 기록한다.
* 예상하지 못한 상황은 수집 실패 시 확인하지 못함으로 표시하고, 조사가 상한에 닿으면 조사 미완, LLM 오류면 조사 실패로 알리고, 점검기가 멈추면 점검 중단 알림을 보낸다.

### 기대 효과

* 업무 효율화: 사용자 문의를 기다리지 않고 점검이 끝나는 대로 장애를 알림으로 받고 몇 분 안에 원인을 받는다(현재 약 3~5일, 추정). 다만 자동 점검은 매시 정각이라 장애가 점검 직후에 생기면 최대 약 1시간을 기다리므로, 바로 확인하려면 화면의 지금 점검이나 CLI로 직접 점검한다. 사람이 직접 확인할 항목을 크게 줄이는 것이 목표이나 감소율 계산은 구현하지 못했다.

* 품질 향상: K8s 상태로는 원인이 보이지 않는 장애에서 원인 규명을 목표로 하고, 모든 판단에 근거 원문이 연결된 검증 가능한 진단을 제공한다.

* 비용 절감: 숙련자에게 집중되던 원인 분석을 서비스 담당자가 1차로 수행한다. 정상일 때와 규칙이 장애를 적발한 경우(11월 9일 이후)에는 조사용 LLM을 부르지 않는다. 규칙 신호 없이 기능 실패나 증상 입력으로 시작하는 조사는 중앙값 200초, 25만 토큰 이하를 목표로 한다. 근거 요약과 이력 질의 채팅는 별도로 LLM을 쓴다. 규칙 장애에서 줄어든 LLM 비용은 측정하지 않았다.

### 범위 및 제약사항

* In Scope: 템플릿 앱 6개와 PostgreSQL, Redis(minikube, 단일 네임스페이스) 진단, 매시 정각 점검, 규칙 14개, 기능 점검, AI 조사 에이전트와 보고서, 심각도별 Slack 알림, 읽기 중심 보고서 화면(점검 이력, 이슈, 점검 구성, 지금 점검, 근거 원문, 이력 질의 채팅 패널), 장애 시나리오와 정상 기준선 평가

* Out of Scope: 조치 에이전트(보고서의 조치를 실행하는 다음 단계 과제), 배포 전후 변경 검증, 상태 대시보드, 보고서 메일 발송, Slack 슬래시 명령, 의미 기반 이력 검색, 부하와 시간 의존 장애, Prometheus 등 별도 관측 스택, 실제 운영 클러스터 적용, 범용 애드온 배포, 에이전트 구조와 모델 비교 실험(계획했으나 수행하지 않음)

* 제약사항: 1인, 8주, 주 10~15시간, 로컬 minikube(CPU 4, 메모리 10GB), Azure OpenAI만 사용(사내 SSL CA 주입 필요), 에이전트는 조회 권한만, Slack 앱 생성 승인과 사내망 통신 허용 필요, 보고서 화면은 인증 없이 port-forward로만 접근하는 PoC, 과거 장애의 진단 시간 기록이 없어 현재 수준은 경험 기반 추정치로 표기하고 규칙만 쓴 조건 대비 측정값으로 보완
