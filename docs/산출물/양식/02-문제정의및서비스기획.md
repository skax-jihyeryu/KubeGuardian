# 2. 문제 정의 및 서비스 기획

### 프로젝트 명

**KubeGuardian AI** — AI 기반 Kubernetes 서비스 환경 진단 Agent

### 배경 및 문제 정의

* 현재 상황 (As-Is): MSA 구조에서는 서비스 하나가 여러 레포·Pod·공유 설정·DB로 나뉘어, 한 곳의 문제가 다른 곳의 증상으로 나타난다. 우리 팀은 앱 6개(front-chat, front-admin, gateway, agent, admin, llm-gateway)로 구성된 AI 서비스 템플릿을 만들어 쓰고 있고, SK Inc. PR 보도자료 서비스도 여기서 출발해 Kubernetes에서 운영 중이다. 장애가 나면 운영자가 사용자 문의를 받은 뒤 kubectl로 앱마다 하나씩 수작업으로 원인을 찾는다.

* Pain Point:
  * 보이지 않음 — Pod는 모두 Running·Ready인데 서비스가 안 된다
  * 멀리 있음 — 증상(gateway 502)과 원인(llm-gateway 할당량 소진, Redis 연결 차단)이 다른 서비스에 있다
  * 너무 많음 — 경고·이벤트·재시작 기록 대부분이 지금 장애와 무관해, 무엇이 중요한지 고르는 일이 숙련자에게 의존한다
  * 시간 — 사용자가 문의해야 장애를 알게 되고, 원인 파악에도 오래 걸린다. PR 업무는 시간에 민감해 서비스 중단이 곧 업무 중단이다

* 기회 요인: 조건이 명확한 오류는 규칙 코드로 확정하고, 여러 신호를 연결하고 증상에서 원인을 거슬러 올라가는 일은 LLM 에이전트의 추론 + 도구 호출로 자동화할 수 있다. 정상일 때 LLM을 부르지 않는 룰 + LLM 구조는 BeingAX 뉴스 판정에서 비용·일관성 효과를 이미 확인했다.

### 목표 사용자 (Target User)

* 주 사용자: **템플릿 기반 AI 서비스의 개발·운영 담당자** — 서비스 개발·배포와 운영을 함께 맡으며, Kubernetes 배포는 할 줄 알지만 장애 원인 분석 경험은 많지 않다. Slack으로 이상 알림을 받고, 배포 직후 점검과 증상 조사를 Slack 명령으로 맡긴다.
* 보조 사용자: **장애 1차 대응 담당자** — Slack 알림의 "지금 중요한 것" 요약으로 무엇부터 볼지 판단한다.

### 프로젝트 목표

* 정성적 목표

  * 목표 1: 반복 진단 업무 자동화 — kubectl로 하던 확인(상태·이벤트·로그·호출 경로·API 호출)을 5분마다 자동으로 수행하고, 이상이 있을 때만 Slack으로 알린다

  * 목표 2: 의사결정 지원 — 수십 개 신호 중 "지금 중요한 것"을 골라, 원인·근거·조치·재검증 방법을 담은 보고서 하나로 판단이 끝나게 한다

  * 목표 3: AI 기술 내재화 — 원인을 아는 장애를 주입해 정답과 비교하는 정량 평가 체계를 구축하고, 에이전트 기술을 같은 지표로 비교한다

* 정량적 목표 (KPI) — 같은 장애 시나리오를 "규칙 점검만" 조건과 "규칙 점검 + AI 조사" 조건으로 실행해 비교

| --------- | --------- | --------- | --------- |
| **성과 지표** | **목표 수치** | **측정 방법** | **현재 수준** |
| 원인 규명 커버리지 | 60% 이상 | K8s 상태 조회만으로는 원인이 드러나지 않는 시나리오 중 원인을 맞힌 비율 | 규칙만 쓴 조건 측정값 (0%에 가까울 것으로 예상) |

| AI 조사 시간·비용 | 120초, 10만 토큰 이하 (잠정) | 평가 러너 자동 기록. 3주차 실측 후 확정 | 수동 진단 수십 분 이상 |

### 핵심 기능 정의

1. 주기 점검과 이상 감지: 5분마다(Kubernetes CronJob) Kubernetes 리소스를 조회 전용으로 수집해 명확한 오류를 규칙 약 10종으로 확정하고, 로그인 → 채팅 API를 실제로 호출해 "K8s는 정상인데 서비스가 안 되는" 증상을 잡는다. 둘 다 정상이면 LLM을 호출하지 않는다.

2. AI 조사·검증 에이전트: 이상이 있으면 원시 신호에서 사용자 영향 순으로 중요한 문제를 고르고, 원인 가설(최대 3개)을 읽기 전용 도구 7종으로 검증해 지지 / 배제 / 판단 보류로 판정한다. 모든 사실 문장에 수집 데이터(근거)를 붙이고, 배제한 가설의 이유·확인한 범위·구체적인 조치·재검증 방법까지 담은 보고서를 쓴다.

3. Slack 알림과 명령: 요약은 알림 채널에, 전체 보고서는 그 스레드에 보내고, 같은 문제는 한 번만 알리고 해결되면 복구 알림을 보낸다. 운영자는 Slack에서 `/kg check`(즉시 점검), `/kg investigate 증상`(증상 조사), `/kg evidence 번호`(근거 원문)로 직접 맡길 수도 있다.

### 기대 효과

* 업무 효율화: 사용자 문의 전, 장애 발생 7분 안에 원인과 함께 알림을 받고, 사람이 직접 확인할 항목을 90% 이상 줄임 (예: 47개 → 중요 문제 2건)

* 품질 향상: K8s 상태로는 원인이 보이지 않는 장애에서 원인 규명 60% 이상, 모든 판단에 근거 원문이 연결된 검증 가능한 진단

* 비용 절감: 숙련자에게 집중되던 원인 분석을 서비스 담당자가 1차로 수행, 정상일 때 LLM 비용 0 · 조사 1회 10만 토큰 이하

### 범위 및 제약사항

* In Scope: 템플릿 앱 6개 + PostgreSQL·Redis(minikube, 단일 네임스페이스) 진단, 5분 주기 점검, 규칙 약 10종, API 호출 증상 감지, AI 조사·검증 에이전트와 보고서, Slack 알림·명령, 장애 시나리오 8개 + 정상 환경 평가, 에이전트 기술 비교 실험(일정 여유에 따라)

* Out of Scope: 조치 에이전트(보고서의 조치를 실행 — 다음 단계 과제), 보고서 후속 질문, 배포 전후 변경 검증, 제품용 웹 화면, 부하·시간 의존 장애, 실제 운영 클러스터 적용, 범용 애드온 배포

* 제약사항: 1인 · 8주 · 주 10~15시간, 로컬 minikube(CPU 4·메모리 10GB), Azure OpenAI만 사용(사내 SSL CA 주입 필요), 에이전트는 조회 권한만, Slack 앱 생성 승인과 사내망 통신 허용 필요, 과거 장애의 진단 시간 기록이 없어 규칙만 쓴 조건 대비로 효과 측정
