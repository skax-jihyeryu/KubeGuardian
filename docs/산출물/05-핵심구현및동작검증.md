## 0. 서비스 한 줄 정의와 구현 범위

**KubeGuardian은 Kubernetes 위에서 동작하는 AI 서비스를 5분마다 점검하고, 문제가 있으면 AI 에이전트가 조회 전용 도구로 원인을 조사해 근거가 붙은 보고서와 Slack 알림으로 알려주는 진단 에이전트다.**

| 구분 | 내용 |
|---|---|
| 입력 (In) | 5분 주기 점검, `/kg check`(즉시 점검), `/kg investigate 증상`(증상 조사) |
| 출력 (Out) | Slack 알림(1차 감지, 원인 갱신, 리마인더, 복구), 조사 보고서(화면, Markdown 파일), 처리 이력 |

**구현 상태 (2026-10-19)**

| 기능 | 상태 | 코드 위치 |
|---|---|---|
| 상태 수집, 규칙 13종, 게이트(경로 A, C) | 구현, 확인 | `service/sensors/`, `service/checks/`, `service/pipeline/check.py` |
| 진단 도구 7종 | 구현, 단위 테스트 | `service/tools/` |
| 에이전트 공통 기반 (BaseAgent, 레지스트리, 예산, 사용량) | 구현, 단위 테스트 | `service/agent/base.py`, `registry.py`, `core/guard/budget.py` |
| LLM 연결 (`build_chat_model`) | 구현, Pod 안 호출 확인 | `core/llm.py` |
| 근거 저장소, 점검 이력 | 구현 | `core/db/` |
| 마스킹 | 구현, 단위 테스트 | `core/guard/redact.py` |
| 평가 러너 (기준 조건: 규칙만) | 구현, H0와 A5 통과 | `eval/`, `scenarios/` |
| 경로 B (실제 호출 실패), LangGraph 조사 흐름, 근거 검증기 | W2 구현 중 | `service/checks/symptoms.py`, `service/agent/investigator/v1/` |
| 공통 지식 기반 (RAG), `search_knowledge` | W2 구현 중 | `service/knowledge/` |
| Slack 알림과 명령, 보고서 화면 | W2~W3 | `service/notify/`, `api/` |

## 1. 핵심 구현 내용

### 1.1 에이전트 워크플로우 (Agent Workflow)

| 항목 | 내용 |
|---|---|
| **구현 기능** | 점검과 AI 호출 여부 판정(게이트). 문제 상황일 때만 AI 조사를 시작한다 |
| **동작 원리** | Kubernetes 상태를 수집해 규칙 13종(장애 신호 11종, 개선 권고 2종)으로 점검한다. 장애 신호가 하나라도 적발되면 경로 A(AI 조사 시작), 개선 권고만 있거나 모두 통과면 경로 C(AI 호출 없음)다. 경로 A의 1차 심각도는 적발된 신호 중 가장 높은 것이다. 점검 결과와 판정에 쓴 값은 근거로 저장한다 |
| **주요 기술** | Python 결정적 함수(규칙마다 `@detector("S04")`로 등록), Kubernetes Python 클라이언트(조회 전용), SQLAlchemy와 SQLite |

**점검 흐름 (구현됨)**: 수집, 점검 이력과 스냅샷 저장, 규칙 점검, 근거 저장, 게이트, 신호판 생성 순서로 실행한다. 주기 점검, `/kg check`, 화면 실행, 평가 러너가 모두 같은 함수(`run_check`)를 부른다.

**규칙 점검의 설계 포인트**

- 규칙은 `ClusterSnapshot`(정규화된 수집 결과)과 관측 기록만 보는 결정적 함수다. 그래서 실제 클러스터 없이 저장한 스냅샷 파일로 테스트한다.
- 규칙 명세는 [규칙 점검 명세](../05-rules.md)가 정본이고, `catalog.py`가 코드 표현이다. 둘이 일치하는지 테스트로 확인한다.
- "15분 이상 지속"처럼 시간 조건이 있는 규칙은 첫 관측 시각을 저장해 두고, 조건을 채우기 전에는 "관찰 중"으로 둔다.
- 수집에 실패한 리소스와 관련된 규칙은 "확인하지 못함"으로 표시하고, 나머지 규칙은 계속 판정한다.

**AI 조사 흐름 (W2 구현 중)**: 경로 A 또는 B에서 시작해 사전 확인, 선별, 계획, 도구 반복(act, tools, judge), 보고서 작성, 근거 검증 순서로 진행한다. 흐름과 State는 [4장 그림](04-상세설계및개발환경구축.md#21-처리-로직)과 같다. 미리 만든 기반은 다음과 같다.

| 기반 | 하는 일 |
|---|---|
| `AgentSpec` | 에이전트 이름, 버전, 역할별 모델, 예산, 프롬프트 위치를 정한다 |
| `BaseAgent.run()` | 구현은 `_run()`만 쓴다. 시간과 사용량 집계, 예외를 `failed`로 바꾸는 처리(오류 메시지 마스킹 포함)는 공통으로 한다 |
| 레지스트리 | `"investigator:v1"` 같은 키로 구현을 고른다. 평가와 비교 실험이 같은 키를 쓴다 |
| `BudgetTracker` | 문제당 8회, 전체 20회, 150초 상한. 도구가 호출 수를 세고, 상한을 넘으면 호출하지 않고 실패로 돌려준다 |
| 구조화 출력 방어 | 제공사의 구조화 출력을 먼저 쓰고, 실패하면 응답 본문에서 JSON을 찾는다. LLM 호출은 최대 2회 |

### 1.2 도구(Tool) 및 함수 연동

| 항목 | 내용 |
|---|---|
| **구현 기능** | 조회 전용 진단 도구 7종과 LLM 연결 함수 |
| **동작 원리** | 모든 도구가 같은 순서를 거친다: 입력 검증, 호출 상한 확인, 수집, 대상 네임스페이스 확인, 마스킹, 근거 저장, 요약 반환. 네임스페이스는 입력으로 받지 않고 코드가 고정한다. 호출이 실패해도 실패를 근거로 저장한다. LLM은 `build_chat_model(모델 이름)` 한 곳에서 만들고, 연결 정보는 설정으로만 받는다 |
| **주요 기술** | Pydantic(도구 입력 스키마), httpx(네임스페이스에 묶인 HTTP 클라이언트), Kubernetes Python 클라이언트, LangChain `AzureChatOpenAI`, Azure OpenAI `gpt-6.1-sol`(Responses API) |

**도구 7종 (구현됨)**

| 도구 | 확인하는 것 | 안전 장치 |
|---|---|---|
| `get_topology` | 서비스 호출 관계, 풀리지 않는 주소 | 네임스페이스 고정 |
| `get_resource` | 리소스 핵심 필드 | Secret과 ConfigMap은 키 이름만 |
| `get_pod_logs` | 현재 또는 이전 로그 | 최대 200줄, 키워드 필터, 마스킹 |
| `get_events` | 최근 이벤트 | 최대 120분 |
| `probe` | 서비스와 Pod별 HTTP 응답 | 상태 확인 경로만, GET만, 한 번에 HTTP 20회와 30초 이하 |
| `run_api_scenario` | 로그인 후 채팅의 실패 단계 | 설정에 등록한 시나리오만, 테스트 계정은 LLM에 보이지 않음 |
| `query_app_api` | 앱 상태 API (예: 할당량) | 허용 목록 경로만, GET만 |

**네임스페이스 범위를 지키는 세 겹**

1. 도구 입력에 네임스페이스 필드를 둘 수 없다. 이런 필드가 있으면 클래스를 정의할 때 거부한다.
2. 도구는 대상 네임스페이스에 묶인 Kubernetes 클라이언트와 HTTP 클라이언트만 쓴다. HTTP 클라이언트는 그 네임스페이스의 Service 이름이나 Pod IP만 받고, 리다이렉트와 프록시 환경변수를 따르지 않는다.
3. 도구가 돌려준 결과의 대상이 `<대상 네임스페이스>/<종류>/<이름>`과 맞는지 다시 확인한다.

**LLM 연결과 키 대체 (구현됨)**: 에이전트는 역할 이름으로 LLM을 요청하고, `build_chat_model`이 설정(`LLM_PROVIDER`, 엔드포인트, 키, API 버전)으로 클라이언트를 만든다. 키 교체와 엔드포인트 변경은 Secret만 바꾸면 되고, 다른 제공사는 이 함수에 분기 하나를 더하면 된다. 모델별 제약은 `MODEL_OPTIONS` 표에 모은다.

### 1.3 데이터 및 메모리 (RAG & Context)

| 항목 | 내용 |
|---|---|
| **구현 기능** | 근거 저장소와 점검 이력, 환경 설명과 조사 지침 템플릿. 공통 지식 기반(RAG)은 W2 구현 중 |

**저장소 (구현됨)**

| 테이블 | 내용 | 쓰는 곳 |

| 점검 이력 | 점검 실행 ID, 트리거, 시각, 스냅샷 | 시간 조건 규칙(직전 스냅샷 비교), 보고서 화면의 점검 이력 |
| 관측 기록 | 규칙별 첫 관측 시각 | "15분 이상 지속" 판정, 신호판의 첫 관측 시각 |
| 근거 | 번호, 종류, 대상, 출처, 마스킹된 데이터 | 보고서 인용, 근거 검증기, 화면의 근거 보기 |

**지식 기반 (W2 구현 중)**

| 순서 | 내용 |

## 2. 주요 문제 해결 및 기술 리서치

| 이슈 구분 | 문제 상황 및 원인 | 리서치 및 해결 과정 (Reference & Solution) |
|---|---|---|
| **LLM 연동** | 진단 모델 `gpt-6.1-sol`이 temperature 0을 거부하고, 도구 호출이 기존 Chat Completions API에서 동작하지 않음 | **리서치:** Azure OpenAI의 모델별 API 지원 범위 확인. 도구 호출은 Responses API에서 되고 API 버전 `2025-03-01-preview` 이상이 필요함 (`2025-04-01-preview`로 확인). **적용:** 모델별 제약을 `MODEL_OPTIONS` 한 곳에 모아, 해당 모델이면 temperature를 보내지 않고 Responses API를 쓰게 함. 결정성은 평가에서 시나리오당 3회 반복과 다수결로 확인 |
| **LLM 연동** | 템플릿 llm-gateway는 Chat Completions와 API 버전 `2024-10-21`로 고정되어 `gpt-6.1-sol`을 쓸 수 없음 | **리서치:** llm-gateway 코드의 호출 방식 확인. **적용:** 진단 대상 서비스는 gpt-4.1을 llm-gateway에 등록하고, 진단 에이전트는 별도 배포를 직접 호출. 키도 분리해 한쪽 할당량 소진이 다른 쪽에 영향을 주지 않게 함 |
| **환경** | 사내 프록시가 TLS를 가로채 노드의 이미지 받기와 Pod 안 Azure OpenAI 호출이 인증서 오류로 실패 | **리서치:** [minikube 사내 인증서 등록 문서](https://minikube.sigs.k8s.io/docs/handbook/untrusted_certs/), `SSL_CERT_FILE`이 기본 인증서 저장소를 대체한다는 점 확인. **적용:** 노드는 `--embed-certs`로 사내 CA 등록. Pod는 공개 CA(certifi)와 사내 CA를 합친 번들을 시작 시 만들어 `SSL_CERT_FILE`로 지정 |
| **환경** | 템플릿 앱 기동 실패: 최신 pnpm에서 frontend 빌드 실패, 백엔드가 기동할 때 인터넷에서 패키지를 받다 실패, kustomize 순환 참조 | **리서치:** 각 오류 메시지와 템플릿 빌드 설정 확인. **적용:** 포크에서 `pnpm@9` 고정, `UV_NO_SYNC=1`, 원본 디렉터리별 `kustomization.yaml`. 기동에 꼭 필요한 수정만 하고 실행 계획서에 목록으로 남김 |
| **환경** | Phoenix가 기동하자마자 종료 | **리서치:** Kubernetes가 Service 이름으로 `PHOENIX_PORT=tcp://...` 환경변수를 자동으로 넣는다는 점 확인. **적용:** 매니페스트에서 `PHOENIX_PORT=6006`으로 덮어씀 |
| **진단 정확도** | 템플릿의 readinessProbe가 포트만 보는 방식(tcpSocket)이라, 하위 서비스 주소가 틀려 모든 요청이 실패해도 Pod는 Ready로 보임 | **리서치:** [Kubernetes probe 문서](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)로 probe 종류별 동작 확인, gateway 코드의 서비스 주소 기본값(`localhost`) 확인. **적용:** 서비스 주소가 `localhost`나 없는 Service를 가리키는지 보는 선언 규칙(S04)과, 로그인 후 채팅을 실제로 부르는 API 시나리오(증상 감지, 경로 B)를 함께 둠 |
| **진단 정확도** | 템플릿 agent는 LLM 호출이 실패해도 HTTP 200에 "오류가 발생했습니다"를 돌려줌. 상태 코드만 보면 성공으로 판정됨 | **리서치:** 템플릿 agent 응답 형식 확인. **적용:** API 시나리오 단계에 응답 본문 검사(`check.path`, `not_starts_with`)를 넣어 이 문구를 실패로 판정 |
| **보안** | Kubernetes 목록 API가 Secret 값을 함께 돌려주고, 처음 만든 ClusterRole은 모든 네임스페이스의 Secret을 읽을 수 있었음 | **리서치:** [Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/)과 [RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/) 문서 확인. **적용:** 수집 직후 정규화 단계에서 Secret 값을 버리고 키 이름만 남김(단위 테스트로 고정). 네임스페이스 리소스는 `dev` Role로만 주고 ClusterRole은 Node 조회만 남김. `kubectl auth can-i`로 쓰기 권한 없음 확인 |
| **도구 안전** | `probe`가 Pod의 아무 경로나 부를 수 있으면 업무 API를 반복 호출해 앱 상태를 바꿀 수 있음 | **리서치:** 템플릿 앱의 상태 확인 경로와 readinessProbe 설정 확인. **적용:** `/health` 계열과 대상 Pod의 readinessProbe 경로만 허용하고, 그 밖의 경로는 호출 없이 실패로 돌려줌 |
| **장애 주입** | A5를 "서비스 주소 환경변수 삭제"로 주입하면 앱 동작은 같지만 S04가 판정할 값이 없음 | **리서치:** gateway 코드의 기본값과 S04 판정 방식 비교. **적용:** 환경변수를 지우지 않고 코드 기본값(`localhost`)으로 바꾸는 방식으로 주입. 환경변수가 아예 없는 경우는 규칙 명세의 빈 곳으로 기록하고 후속 이슈로 다룸 |
| **장애 주입** | Chaos Mesh TimeChaos가 arm64에서 대상 프로세스를 종료 코드 139로 죽임 | **리서치:** [Chaos Mesh TimeChaos 문서](https://chaos-mesh.org/docs/simulate-time-chaos-on-kubernetes/)와 단일 프로세스 재시험. **적용:** 사용처가 확장 후보 C3뿐이라 핵심 범위에서 제외. C3를 진행하면 libfaketime 같은 대체 수단 검토 |
| **평가 신뢰성** | 수집이 실패하면 규칙이 "확인하지 못함"이 되어 게이트가 경로 C(정상)로 가고, 장애가 없는 것처럼 채점됨 | **리서치:** 평가 러너의 단계별 실패 경우 정리. **적용:** 주입 전 정상 기준선 확인, 증상이 실제로 나는지 확인(최대 180초 반복), 수집 실패와 예외는 모두 "무효"로 처리해 통과나 실패로 세지 않음 |
| **설계 (RAG)** | 지식 문서가 7개뿐이라 처음에는 벡터 검색 없이 전부 넣기로 했으나, 과거 처리 방식을 쌓아 다시 쓰자는 피드백을 받음 | **리서치:** 처리 이력을 지식으로 쓸 때의 위험(틀린 원인 누적, 평가 정답 누출) 정리. **적용:** 공통 지식 기반으로 바꾸고, 복구가 확인된 문제만 등록, 평가 실행 보고서는 제외, 검색 결과는 근거가 아닌 참고 자료로만 쓰게 설계 (4장) |
| **설계 (MCP)** | 외부 호출을 MCP 서버로 둘지 검토 필요 | **리서치:** 공개 Kubernetes MCP 서버(읽기 전용 모드 지원), `langchain-mcp-adapters` 확인. **적용:** 공개 서버를 그대로 쓰면 네임스페이스 고정, 마스킹, 근거 저장, 예산이 빠지므로, 우리 도구를 MCP 서버로 감싸는 방식만 비교 실험 3으로 검증. 알림과 보고서 출력은 코드가 직접 호출 (4장) |

## 3. 핵심 동작 검증

### 3.1 대표 시나리오: A5

**[검증 시나리오: `A5. gateway의 서비스 주소가 localhost를 가리켜 모든 API가 실패`]**

* **입력:** `make eval S=A5` (평가 러너가 장애를 주입하고 점검을 한 번 실행)

* **에이전트 동작:**

  1. 정상 기준선 확인: 로그인 후 채팅 성공 (H0 스모크)
  2. 장애 주입: gateway의 하위 서비스 주소 환경변수 4개(`ADMIN_SERVICE_URL`, `AUTH_VERIFY_URL`, `AGENT_SERVICE_URL`, `LLM_GATEWAY_SERVICE_URL`)를 `localhost`로 바꿈
  3. 증상 확인: front-chat을 거친 로그인이 500으로 실패. gateway Pod는 Ready로 남음
  4. 점검: Kubernetes 상태 수집, 규칙 S04(서비스 주소 설정 오류)가 gateway를 긴급으로 적발, 판정에 쓴 값을 근거로 저장
  5. 판정: 장애 신호 적발이므로 경로 A (AI 조사 대상)
  6. 채점과 원복: 기대 신호(S04)와 기대 경로(A)가 모두 맞아 통과. 원복 후 로그인 후 채팅이 다시 성공

* **최종 결과:**

[2026-10-19 실행 결과: 통과. Pod는 모두 Ready였지만 S04가 gateway의 서비스 주소 오류를 긴급으로 적발했고, 게이트가 경로 A로 열렸다. 원복 후 로그인은 401(잘못된 계정에 대한 정상 응답)로 돌아왔고 H0 스모크가 성공했다.]

이 시나리오가 보여주는 것: Kubernetes 상태(Pod Ready)만 보면 정상이지만, 선언 규칙이 원인을 바로 잡고 AI 조사 대상으로 넘긴다.
