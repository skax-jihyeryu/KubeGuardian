문제와 접근

"Pod는 전부 Ready인데 서비스는 죽어 있다"

문제

  • 서비스가 여러 조각(MSA)으로 나뉘어 있어, 한 곳의 문제가 다른 곳의 증상으로 나타남
  • Kubernetes는 "포트가 열려 있으면 정상(Ready)"으로 보는 경우가 많아, 앱이 오류를 내도 정상으로 표시됨
  • 사람이 원인을 찾으려면 여러 서비스의 설정·로그를 오래 뒤져야 함

접근

  • 규칙 우선: K8s 설정·상태만 보고 확실히 알 수 있는 장애는 정해진 규칙으로 즉시 잡음 (AI 없음)
  • 필요할 때만 AI: 아래 판정에 따라 AI 조사를 돌릴지 정함
  • 근거 강제: AI 보고서의 모든 사실에 근거 번호, 코드가 검증
  • 조회 전용: 클러스터는 바꾸지 않고 조치는 제안만
점검 결과의미다음 행동
규칙 적발K8s 설정·상태에서 장애가 보임바로 알림 → AI가 원인 조사
증상만 있음규칙은 통과했지만 로그인·채팅 같은 사용자 기능이 실패알림 → AI가 원인 조사
정상규칙 통과, 사용자 기능 정상AI 조사 안 함 (비용 절약)

환경

Mac 한 대에 실제 운영과 같은 구조

macOS
└─ Docker Desktop
   └─ minikube: Kubernetes 노드 1대
      (K8s v1.37, CPU 4 · 메모리 10GB)
      ├─ dev           진단 대상 서비스
      │                (앱 6종 + DB·캐시, Pod 10개)
      ├─ kubeguardian  진단 에이전트, 실행 추적 도구
      ├─ chaos-mesh    장애 주입 도구
      └─ kube-system   Kubernetes 자체 부품

네임스페이스 = 클러스터 안의 칸막이

  • dev: 사내 AI 서비스 템플릿(채팅 화면·관리자 화면·API 중계·관리·AI 에이전트·LLM 중계)을 그대로 띄운 곳. 장애는 여기에만 넣음
  • kubeguardian: 우리가 만드는 진단 에이전트. 진단 대상이 고장 나도 영향받지 않게 분리
  • chaos-mesh: 네트워크 차단·오류 응답 같은 장애를 일부러 만드는 오픈소스 도구
  • kube-system: Kubernetes가 스스로 쓰는 부품이 있는 곳. 서비스 이름을 주소로 바꾸는 DNS, Pod 사이 네트워크, CPU·메모리 사용량 수집기 등. 우리가 만든 것은 없음
사내 프록시 인증서를 노드와 Pod에 넣어야 외부(LLM API) 호출이 됨 · LLM은 두 경로로 분리: 진단 대상 서비스는 gpt-4.1, 진단 에이전트는 gpt-6.1-sol
규칙

LLM 없이 판정하는 규칙 13종

분류규칙언제 적발하나
노드·Pod노드 장애 · 이미지 받기 실패 · Pod 반복 재시작 · 메모리 부족 종료상태가 15분~1시간 계속되면 (메모리 부족은 즉시)
배포떠 있어야 할 Pod 수 부족 · 새 버전 배포가 멈춤15분 계속되면
서비스 연결Service가 고를 Pod 없음 · 요청 받을 준비된 Pod 없음 · 포트 불일치 · 서비스 주소 설정 오류설정 비교는 즉시, "준비된 Pod 없음"은 15분
설정참조하는 설정(ConfigMap)·비밀(Secret)이 없음즉시
개선 권고준비 상태 검사가 포트만 봄 · CPU·메모리 한도 미설정즉시 (장애 아님, 알림 없음)

근거

업계 표준 알림 규칙(kubernetes-mixin), 설정 점검 도구(Polaris), K8s 공식 문서의 조건·지속 시간을 따름

"설정만 봐도 안다"

설정 비교 규칙은 트래픽이 없어도 바로 적발. 예: 서비스 주소가 localhost를 가리키면 즉시

판정 4가지

적발 · 관찰 중(아직 15분 전) · 통과 · 확인하지 못함(수집 실패를 정상으로 오판하지 않음)

끝까지 도는 테스트 (E2E)

실제 클러스터에서 확인한 3가지

① 진단 대상이 정상인가

채팅 화면을 거쳐 테스트 계정으로 로그인 → 채팅 → 실제 gpt-4.1 응답까지 자동 확인

명령: make smoke

약 2초 · 성공

② 진단 에이전트가 LLM을 부를 수 있나

클러스터 안 Pod에서 사내 인증서를 넣고 gpt-6.1-sol 호출. 일반 답변·정해진 형식 답변·도구 호출 확인

명령: run.sh gpt-6.1-sol

약 3초 · 성공

③ 장애를 넣으면 규칙이 잡나

정상 확인 → 장애 주입 → 증상 확인 → 규칙 점검 → 채점 → 되돌리기 → 복구 확인을 사람 손 없이 반복

명령: make eval S=<시나리오>

평가용 장애 7가지

장애사용자가 겪는 증상K8s에서 보이나지금 결과 (규칙만)
정상 (비교 기준)없음—조용함 · 통과

LLM 사용 한도 초과채팅만 실패안 보임증상 감지 필요 (2주차)

"K8s에서 안 보이는" 장애가 AI 조사가 필요한 이유 · 규칙만으로 잡히는 장애와 잡히지 않는 장애를 모두 넣어 둘을 비교

장애를 어떻게 넣나

실제 운영에서 일어나는 실수·고장을 재현

Service 이름표 오타

AI 에이전트 서비스의 Service가 Pod를 찾는 이름표 값 끝에 글자 하나(agent → agentx)를 붙임. Pod는 그대로 살아 있지만 Service가 아무 Pod도 못 찾아 요청이 갈 곳이 없어짐

서비스 주소 설정 누락

API 중계 서비스가 다른 서비스를 부르는 주소 설정 4개를 localhost로 바꿈. 템플릿 원본(주소 설정이 없으면 localhost로 호출)과 같은 상태. 중계 서비스가 자기 자신을 부르게 되어 모든 요청이 실패

없는 버전으로 배포

AI 에이전트 서비스의 이미지를 존재하지 않는 주소·버전으로 바꿔 새 버전 배포. 새 Pod가 이미지를 못 받아 배포가 멈춤. 이전 버전 Pod 3개는 계속 동작

Pod 3개 중 1개만 오류

장애 주입 도구(Chaos Mesh)로 AI 에이전트 Pod 3개 중 무작위 1개의 응답을 HTTP 500으로 바꿈. Pod는 Ready 그대로라 K8s는 정상으로 봄

캐시(Redis) 연결 차단

장애 주입 도구로 관리 서비스 ↔ Redis 사이 네트워크만 끊음. 모든 Pod가 정상이고 로그에도 오류가 없어 K8s로는 보이지 않음

LLM 사용 한도 초과

장애 주입 도구로 LLM 중계 서비스의 채팅 요청 응답만 "429 한도 초과"로 바꿈. 로그인·화면은 정상, 채팅만 실패

모든 장애는 원래 값을 따로 저장해 두고 자동으로 되돌림 · 되돌린 뒤 로그인 → 채팅이 다시 성공해야 그 평가를 인정

만들면서 알게 된 것

실제로 돌려 보고 확인한 4가지

1. Pod가 Ready여도 서비스는 죽어 있을 수 있다

본 것이름표 오타·주소 누락 장애 모두 Pod는 전부 Ready, 사용자는 모든 요청 실패 이유템플릿의 준비 상태 검사가 "포트가 열려 있는가"만 봄 그래서K8s 상태만 보는 모니터링으로는 부족. 설정 비교 규칙 + 실제 로그인·채팅 확인을 같이 씀

2. 설정만 비교해도 잡히는 장애가 있다

본 것주소가 localhost를 가리키는 것은 요청이 하나도 없어도 바로 적발 한계주소 설정이 아예 없으면(원본 템플릿) 비교할 값이 없어 못 잡음 그래서시나리오는 localhost로 바꾸는 방식으로 재현, "설정 없음" 적발은 후속 과제

3. "성공(200)" 응답 안에 실패가 숨어 있다

본 것LLM 호출이 실패해도 템플릿은 HTTP 200에 "오류가 발생했습니다"라는 답을 돌려줌 그래서상태 코드만 보면 정상으로 오판. 응답 내용까지 확인하도록 점검·평가를 만듦

4. "15분 지속" 규칙은 평가 방식도 바꾼다

본 것배포 멈춤 장애는 한 번 점검으로는 "관찰 중"에 머묾. 5분마다 점검하니 약 26분에 적발 그래서평가도 실제 운영처럼 5분 주기로 반복 점검. 이 시간이 곧 "장애 감지 시간" 지표가 됨
