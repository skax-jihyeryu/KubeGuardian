# 사람처럼 조사하기와 "반드시 장애 / 의도일 수 있음" 경계 설계

> 작성 2026-10-21 · 상태: **확정 (2026-10-21, 사용자 승인 — D2~D6 추천안)**
> 관련: 기획서 §6.2·§7·§8, [규칙 점검 명세](../../05-rules.md), [#60](https://github.com/skax-jihyeryu/KubeGuardian/issues/60), [#62](https://github.com/skax-jihyeryu/KubeGuardian/issues/62)
> 리뷰 반영 2026-10-21: PR #66 리뷰와 사용자 결정으로 S01 replicas 0 예외를 철회했다(D3), `required_config` 규칙 ID는 C05, 등급은 §2 표 열이 아니라 §0.1.1 등급 표(ID 접두사로 결정)로 정했다.
> 초안 1에서 바뀐 점: 그래프가 단계를 강제하던 "4단계 절차"를 뺐다. 사람이 원래 하는 조사 방식을 그대로 지시하고, 너무 일찍 멈추지 않게 하는 쪽으로 바꿨다(사용자 결정).

## 1. 왜 바꾸나

W2 실측(PR #61)과 사용자 검토에서 두 가지 문제가 드러났다.

1. **에이전트가 사람처럼 조사하지 않는다.** 사람은 장애를 볼 때 구동 상태 → 설정 → 리소스·연결 → 로그 순서로 훑는다. K8s 공식 디버깅 문서와 learnk8s 트러블슈팅 순서도도 같은 순서다. 지금 에이전트가 이렇게 하지 않는 이유는 세 가지다.
   - **가설부터 쫓는다.** 프롬프트(`investigate.md`)가 "판별력이 가장 높은 도구 하나"를 고르게 한다.
   - **너무 일찍 멈춘다.** "서로 다른 출처의 근거 2개면 멈춘다"는 규칙이 있다. A3는 이벤트와 Pod 상태 두 개를 얻고 도구 4회 만에 멈췄다. 그래서 원인이 있는 Deployment 이미지 설정은 끝내 보지 않았고, 결론이 "레지스트리 DNS 실패"라는 증상 수준에 머물러 채점이 흔들렸다(#62).
   - **무엇을 봤는지 영역별로 남지 않는다.** `not_checked`가 자유 문장이라, 설정을 안 봤다는 사실이 드러나지 않는다.
2. **설정이 없으면 결함이라고 전제한다.** 실제 서비스는 설정을 일부러 두지 않는 경우가 많다. 예를 들면 다음과 같다.
   - Secret이 필요 없는 서비스
   - ConfigMap 없이 설정을 Deployment env에 직접 적은 서비스
   - 기본값으로 충분한 서비스

   그런데 지침에는 "주소 env가 없으면 정상이 아니다"라고 적혀 있다. 정답 파일도 "반드시 잡을 신호"만 적고 "잡혀도 되는 신호"와 "잡히면 오탐인 신호"는 구분하지 않는다.

## 2. 목표 · 비목표 · 반목표

| 구분 | 내용 |
|---|---|
| 목표 | 에이전트가 사람의 조사 방식(구동 → 설정 → 연결 → 로그)을 기본으로 따른다. 원인으로 지목한 리소스의 설정을 직접 보기 전에는 멈추지 않는다 |
| 목표 | 보고서가 네 영역별로 "확인함 / 확인하지 못함"을 남겨, 무엇을 안 봤는지 드러나게 한다 |
| 목표 | 규칙과 AI 결론이 "반드시 장애", "의도일 수 있음", "개선 권고"를 구분한다. **설정이 없다는 사실만으로는 장애로 보지 않는다** |
| 목표 | 정답 파일이 "반드시 잡을 것 / 잡혀도 됨 / 잡히면 오탐"을 구분한다 |
| 비목표 | 그래프가 단계를 강제하는 것(단계별 예산, 단계 완료 선언). 순서는 지시하고, 코드는 멈춤 조건과 빈 영역만 검사한다 |
| 비목표 | 감지기 추가, 앱 코드 정적 분석 |
| 반목표 | 형식적으로 채운 영역. 근거 id 없이 "로그 확인함"만 적힌 경우 |
| 반목표 | L1 시나리오의 조사 시간이나 도구 호출이 2배 넘게 느는 것. 예산(문제당 8회, 전체 20회, 150초)은 그대로다 |

## 3. 사람처럼 조사하기

### 3.1 조사 방식 (지시하는 내용)

시스템 프롬프트와 지침에 기본 조사법을 적는다. 순서는 권장 순서이지 강제가 아니다. 신호가 가리키는 곳이 분명하면 그 영역부터 볼 수 있다. 다만 아래 네 영역은 모두 확인하거나, 확인하지 않은 이유를 남긴다.

| 영역 | 사람이 보는 것 | 주로 쓰는 도구 |
|---|---|---|
| 구동 | 대상과 상·하위 서비스의 Pod 상태: phase, Ready, 재시작, 대기 사유, 롤아웃 진행, 최근 이벤트 | `get_resource`(Pod·Deployment), `get_events` |
| 설정 | 문제 워크로드의 spec: 이미지 참조, env·envFrom 값, 참조하는 ConfigMap·Secret, probe, **이전 revision과의 차이** | `get_resource`(Deployment·ReplicaSet·ConfigMap) |
| 연결 | Service selector·EndpointSlice·포트, 토폴로지(주소 엣지), 하위 의존, 앱 동작 | `get_resource`(Service·EndpointSlice), `get_topology`, `probe`, `run_api_scenario`, `query_app_api` |
| 로그 | 문제 서비스(필요하면 상·하위 서비스)의 현재·이전 로그: 오류 문구, 실제 호출 대상 | `get_pod_logs` |

### 3.2 멈춤 조건 (코드가 검사)

지금 조건은 "서로 다른 출처의 근거 2개가 모이고 나머지 후보가 배제되면 멈춘다"이다. 여기에 두 조건을 더한다.

1. **원인 리소스의 설정을 직접 봤다.** 1순위 원인으로 지목한 리소스의 spec을 `get_resource`로 조회한 근거가 있어야 한다. 예: A3의 agent Deployment, A1의 agent Service, A5의 gateway Deployment.
2. **로그를 봤거나, 볼 필요가 없는 이유가 있다.** 예: 새 Pod가 시작되지 않아 로그가 없다.

조건을 채우지 못한 채 LLM이 "조사 완료"를 선언하면, 코드가 빠진 영역을 알려 주고 한 번 더 조사하게 한다. 지금 있는 "결론 근거가 없으면 보고서를 다시 쓰게 하는" 루프와 같은 방식이다. 예산이 남아 있을 때만 그렇게 하고, 예산이 없으면 보고서의 해당 영역에 "확인하지 못함 (예산 소진)"을 적는다.

### 3.3 보고서

- 지금의 `not_checked` 자유 문장을 네 영역별 `coverage`로 바꾼다: 영역마다 `{status: 확인함|확인하지 못함|해당 없음, summary, evidence_ids}`.
- 근거 검증기가 다음을 검사한다.
  - `확인함`인데 근거 id가 없으면 `확인하지 못함`으로 내린다(지금의 강등 규칙과 같다).
  - `확인하지 못함`과 `해당 없음`은 사유가 필수다.
- Mac 실행에서 HTTP 도구가 실패하면 연결 영역은 "확인하지 못함 (클러스터 밖 실행)"이 된다.

### 3.4 지침

지침 6개의 "먼저 확인할 사실" 표에 영역 열을 추가한다. "원인 후보와 판별법" 표에는 후보마다 **어느 영역의 무엇을 봐야 확정되는지**를 적는다.

예를 들어 "이미지 받기 실패"는 다음 두 가지를 봐야 확정된다.
- 설정: Deployment의 이미지 참조와 이전 revision의 차이
- 구동: Pod의 대기 사유

## 4. 판정 경계: 세 등급

### 4.1 등급 정의

| 등급 | 뜻 | 판정 기준 | 게이트·알림 |
|---|---|---|---|
| **반드시 장애** | 선언된 참조나 의존이 깨져 K8s나 앱이 정상 동작할 수 없다 | 무언가가 **가리키고 있는데** 대상이 없거나 맞지 않는다 | 경로 A, 알림 |
| **의도일 수 있음** | 설정이 없거나 관례와 다르지만 일부러 그랬을 수 있다 | **아무것도 가리키지 않는다.** 그 자체로는 판정하지 않는다 | 게이트를 열지 않는다. AI 조사에서 원인 후보로 올릴 수 있다(§4.3) |
| **개선 권고** | 장애는 아니지만 운영 위험 | H 규칙 | 알림 없음 (지금과 같음) |

원칙: **"없다"는 결함이 아니다. "가리키는데 없다"가 결함이다.**

### 4.2 사용자 예시와 규칙에 적용하기

| 상황 | 등급 | 이유와 현재 동작 |
|---|---|---|
| Secret이 아예 없거나 참조하지 않는 서비스 | 의도일 수 있음 | 참조가 없으니 판정하지 않는다. C01은 참조가 있을 때만 판정하므로 지금도 맞다 |
| 설정을 ConfigMap 없이 Deployment env에 직접 적음 | 의도일 수 있음 | ConfigMap이 없다는 것은 판정 대상이 아니다. S04는 값의 출처와 상관없이 값만 보므로 지금도 맞다 |
| `envFrom`이 가리키는 ConfigMap이 없음 (optional 아님) | 반드시 장애 | 가리키는데 없다 (C01) |
| 주소 env가 아예 없음 | 의도일 수 있음 | 기본값으로 동작하도록 만든 서비스일 수 있다. 규칙으로는 적발하지 않는다(#60). 로그의 호출 대상이 증거다 |
| 주소 env 값이 없는 Service를 가리킴 | 반드시 장애 | 가리키는데 없다 (S04) |
| 주소 env 값이 `localhost` | 반드시 장애. **단, 같은 Pod의 다른 컨테이너가 그 포트를 열면 정상** | 사이드카 패턴에서는 localhost가 정상이다. 지금 S04에는 이 예외가 없다 → **결정 D3** |
| Service selector에 맞는 Pod 0개 | 반드시 장애. replicas 0 예외는 두지 않는다 (알려진 한계: 의도적 replicas 0도 적발) | 실수로 0으로 줄이면 S01·W01·S02 어느 것도 잡지 못하는 구멍이 생기므로 철회 → **결정 D3** |
| readinessProbe·resources 없음 | 개선 권고 | H01·H02, 지금과 같음 |
| 이미지 받기 실패, 롤아웃 정체, CrashLoop | 반드시 장애 | 상태 규칙, 지금과 같음 |

### 4.3 "의도일 수 있음"이 원인이 되는 조건 (AI 조사)

설정이 없다는 사실은 다음 증거 중 **하나 이상과 함께** 있어야 원인 후보가 된다. 확정하려면 기존 기준대로 서로 다른 출처의 근거 2개가 필요하다.

| 증거 | 예 | 영역 |
|---|---|---|
| 사용 증거: 앱이 그 설정을 실제로 찾는다 | 로그의 `localhost:8001 connection refused`, `KeyError: 'X'`, `X is not set` | 로그 |
| 변경 증거: 이전 revision에는 있었는데 사라졌다 | 직전 ReplicaSet의 env에 `ADMIN_SERVICE_URL`이 있음 | 설정 |
| 증상 증거: 그 서비스가 속한 사용자 경로가 실패한다 | 로그인 시나리오 502 | 연결 |

증거가 없으면 보고서에 "의도일 수 있음: ○○ 설정 없음 (원인 근거 없음)"으로만 적는다. 결론이나 1순위 문제로는 올리지 않는다.

### 4.4 운영자가 "반드시 있어야 할 설정"을 선언하기 (선택)

`kubeguardian.yaml`에 선택 항목을 두고, 기본값은 비운다.

```yaml
required_config:            # 선언한 것만 부재를 적발한다 (규칙 C05, C01 확장, 즉시·선언 규칙)
  gateway: [ADMIN_SERVICE_URL, AGENT_SERVICE_URL]
```

#60의 (b)안을 다듬은 것이다. 선언하지 않은 부재는 계속 "의도일 수 있음"으로 둔다. → **결정 D4**

## 5. 시나리오 정답 파일 확장

### 5.1 새 필드

```yaml
must_signals: [W02]          # 기존 expected_signals. 반드시 적발돼야 한다
allowed_signals: [P03]       # 잡혀도 오탐이 아니다 (관찰 중 포함)
forbidden_signals: [P06]     # 잡히면 오탐이다. H0는 장애 신호 전체
must_check:                  # 사람이라면 반드시 봤을 사실. 보고서 coverage에 근거가 있어야 한다
  config: "agent Deployment 이미지 참조가 이전 revision과 다르고 받을 수 없는 주소"
  run: "새 agent Pod가 이미지 받기 실패로 대기 중, 이전 버전 Pod 3개 Ready"
not_a_cause:                 # 결론에 원인으로 올리면 실패하는 "의도일 수 있음" 미끼
  - "llm-gateway 외 서비스에 Secret이 없음"
```

- 채점 규칙
  - `forbidden_signals`가 적발되면 실패다.
  - `allowed_signals`는 기록하지 않는다.
  - 나머지 기대 밖 적발은 지금처럼 "오탐 후보"로 기록만 한다(`eval/scoring.py`).
- `must_check`는 시나리오마다 1~2개만 적는다. judge가 보고서 `coverage`를 보고 항목마다 "확인함 / 놓침"을 판정한다. 통과 조건에 넣을지는 → **결정 D2**
- #62(A3 채점 흔들림)도 함께 풀린다.
  - 멈춤 조건 때문에 에이전트가 Deployment 이미지 설정을 직접 보게 된다.
  - judge는 결론 한 문장만이 아니라 `must_check`도 함께 본다.

### 5.2 경계를 시험하는 시나리오 2개 추가 (제안)

| ID | 내용 | 기대 |
|---|---|---|
| **H1** 부재 정상 | 진단 대상에 설정 없이도 정상인 서비스를 둔다. Secret 참조 없음, ConfigMap 없이 env 직접 기재, 주소 env 없이 기본값이 맞는 구성. 앱은 정상 | 경로 C, 알림 없음. 강제로 조사해도 `not_a_cause`를 원인으로 올리지 않는다 |
| **A6** 부재 원인 | gateway의 주소 env 하나를 **지운다** (A5는 값을 localhost로 바꾼다) | 규칙으로는 적발되지 않는다. 증상 감지가 경로 B를 열고, AI가 설정(이전 revision에는 있었음)과 로그(localhost 호출)로 원인을 확정한다 |

같은 "설정 없음"이 상황에 따라 정상일 수도, 원인일 수도 있음을 보여 주는 쌍이다. A6는 증상 감지(W2 남은 작업)가 있어야 eval할 수 있다. → **결정 D5**
