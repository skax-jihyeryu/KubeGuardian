# ADR-002: 직접 점검도 기존 이슈·비동기 조사 흐름을 사용

- 상태: 채택
- 날짜: 2026-11-03
- 관련: #173

## 배경

직접 점검은 이력을 남기지만 새 이슈를 열지 않아 화면에서 발견한 장애를 주기 점검까지 기다려야 했다. UI 정의서 F3의 조사 연결 설명과도 맞지 않았다. 사용자는 직접 점검에서 장애를 발견하면 AI 조사와 연결된 이슈 결과·알림을 확인하도록 요청했다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 기존 추적·큐·worker 재사용 | 주기/직접 점검 간 중복 제거와 알림 정책 공유 | 직접 점검도 신규 장애 알림을 보냄 |
| 직접 점검 전용 동기 조사 | 요청 안에서 결과 완료 | 긴 요청, 중복 조사·별도 상태 처리 발생 |

## 결정

UI/CLI kg check는 schedule과 동일하게 opened/continued/changed/resolved를 기록하고 새 장애·변경만 기존 큐에 넣는다. 첫 알림을 시도한 뒤 예약하며 알림 실패도 조사를 막지 않는다. UI는 점검 이력을 먼저 반환하고 조사 상태·이슈 링크를 보여준다. kg investigate의 명시적 동기 조사 계약은 유지한다. 리마인더는 버튼이 강제하지 않고 worker의 기존 시간·확인 정책에 맡긴다.

## 결과

정상·개선 권고는 조사하지 않고 확인 불가를 장애/복구로 간주하지 않는다. 같은 지문은 직접/주기 실행을 바꿔도 이슈·조사·첫 알림이 중복되지 않는다. 실패한 조사는 점검/이슈에 보존한다. 공유 잠금·1분 간격·규칙 선택과 기존 복구 정책은 유지한다. 새로운 프롬프트나 조사 엔진은 추가하지 않는다.
